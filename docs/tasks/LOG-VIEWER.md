# LOG-VIEWER — перегляд лога плагіна всередині Obsidian

> Спека, узгоджена з власником 2026-10-07 (TODO.md п.44). Код — ПІСЛЯ перегляду цієї спеки.
> Канон для: `src/log-viewer/*`, кнопки «View log» у Settings, підписки логера.

## 1. Навіщо

Лог (`<vault>/git-easy-sync.log`, JSONL) — інструмент відлагодження. Obsidian не відкриває
`.log`, а сирий JSONL важко читати. Потрібне вікно, де лог видно як таблицю, його можна
відфільтрувати, шукати в ньому і копіювати записи — на desktop і на телефоні.

## 2. Рішення власника

| # | рішення |
|---|---|
| 2.1 | **Власне вікно, жодного файлу.** Не тимчасовий `.md`: у vault він індексується, видимий і редагований; у `.runtime/` Obsidian його не відкриє (приховані теки не індексуються). |
| 2.2 | **Весь лог у пам'яті.** `adapter.read` читає файл лише цілим — інакше не вийде, і це нормально: лог — інструмент відлагодження, зазвичай вимкнений. |
| 2.3 | **Ліміт 10 МБ.** Розмір — через `stat` ДО читання. Більший файл → лише повідомлення «Лог-файл надто великий (N МБ) — відкрийте його засобами операційної системи». |
| 2.4 | **Малюємо лише видиме** (віртуальна прокрутка) — і з урахуванням фільтра. Прокрутка — по рядках тексту, як у редакторі; висота запису — скільки треба. |
| 2.5 | **CodeMirror 6 (лише для читання)** як основа: віртуальна прокрутка, виділення, копіювання і пошук — вбудовані. CM6 уже є в бандлі (diff2). |
| 2.6 | **Таблиця, а не блоки тексту.** Колонки: `дата \| час \| рівень \| повідомлення`. Дані запису (`additional_data`) — під повідомленням, у ТІЙ САМІЙ колонці, відформатований JSON на скільки треба рядків; рядки продовження мають порожні колонки зліва. Між записами — горизонтальний роздільник. Автоперенос рядків ВИМКНЕНИЙ (інакше зламались би колонки) — довгий рядок прокручується вбік; JSON розбиваємо на рядки самі. |
| 2.7 | **Рівень — кольором:** INFO / WARN / ERROR різними кольорами, з CSS-змінних теми Obsidian (світла й темна теми). У коді є всі три рівні (info 101, warn 60, error 43 виклики); у чистому лозі майже все INFO — WARN/ERROR з'являються, коли щось іде не так. |
| 2.8 | **Спершу фільтр, потім пошук.** Фільтр ВИКИДАЄ записи, що не відповідають умові. Пошук лише ПІДСВІЧУЄ й переходить уперед/назад — і лише серед відфільтрованого. |
| 2.9 | **Фільтр: синтаксис колонок через `\|`.** Шматки між `\|` шукаються в РІЗНИХ колонках, у ТОМУ Ж порядку зліва направо; колонки можна пропускати. `2026 \| pulled` → дата … повідомлення(дані); `info \| drain done` → рівень \| повідомлення. Без `\|` — у будь-якій колонці. Колонка «повідомлення» містить і дані. |
| 2.10 | **Перемикачі фільтра — як у пошуку:** регістр, ціле слово, regexp. У режимі regexp кожен шматок між `\|` — окремий вираз. Невірний вираз НЕ кидає помилку — фільтр показує «невірний вираз» і нічого не відкидає. **Уточнено при реалізації (2026-10-08):** `\|` — це буквальний `\|` усередині шматка (у regexp-режимі — «або» всередині одного виразу); порожні шматки (`\| error`) ігноруються; «ціле слово» рахує літери будь-якої абетки (`\b` знає лише ASCII, а користувачі пишуть кирилицею); у regexp `^`/`$` працюють по рядках (колонка повідомлення містить рядки даних). |
| 2.11 | **Пошук — вбудований у CodeMirror** (підсвічування, наступний/попередній, регістр, ціле слово, regexp). Про колонки не знає — колонки вміє лише фільтр. |
| 2.12 | **Динамічно:** фільтр перераховується під час набору (пауза ~150 мс після останньої літери). |
| 2.13 | **Наживо:** відкрите вікно отримує нові записи логера одразу. Якщо користувач унизу — прокрутка йде за новими; якщо прокрутив угору — не заважаємо. |
| 2.14 | **Останній запис — з пам'яті логера, не відкидається.** Логер тримає кільцевий буфер останніх ~200 записів: точний рядок, як у файлі, + порядковий номер (лише в пам'яті). Відкриття: (1) підписатись на логер; (2) прочитати файл, розібрати ПОВНІ рядки, обірваний хвіст відкинути; (3) вирівняти буфер із файлом: буфер — це вікно на КІНЕЦЬ усього записаного, файл — його ПОЧАТОК, тож береться найдовший початок буфера, що дослівно збігається з кінцем файлу (уточнено при реалізації 2026-10-07: так два однакові рядки не плутаються), а все, що в буфері після цього збігу, дописується; (4) далі — підписка; номер не дає показати запис двічі. Збігу нема (власник, 2026-10-07): якщо перший запис буфера НОВІШИЙ за останній запис файлу — файл прочитано надто давно, а буфер не дотягнувся назад; буфер усе одно частина лога, тож показуємо файл, рядок-склейку «…» і весь буфер, а вікно ОДИН раз у фоні перечитує файл і пробує злити знову — знайшовся збіг → вміст тихо замінюється, склейка зникає. Буфер НЕ новіший (старий буфер, файл замінено вручну) або час не читається → лише файл, без вигадок і дублів. Справді зіпсований рядок посеред файлу — показується як є, з позначкою. |
| 2.15 | **Копіювання:** звичайне виділення CodeMirror + кнопка «копіювати відфільтроване». |
| 2.16 | **Відкриття — ЛИШЕ з Settings, група «Logging»** (власник, 2026-10-07): кнопка «View log» поруч із «Clean logs», видима лише з увімкненим логуванням. Команди в палітрі НЕМАЄ. |
| 2.17 | **Відкладено:** нечіткий пошук за шаблонами (правила записані в §5 — не втратити). |

## 4. Не робимо

- Тимчасовий файл у vault чи в `.runtime/` (§2.1).
- Показ «останніх N записів» — показуємо весь лог (§2.2, §2.4).
- Колонки в пошуку (§2.11).
- Команду в палітрі для відкриття (§2.16).

## 5. Відкладено: нечіткий пошук (правила власника, 2026-10-07)

- Запит ділиться на шаблони за пробілами.
- `слв` — літери в тому ж порядку, з пропусками, будь-де в слові («СЛоВо», «СоЛоВей», «багатоСЛіВний»).
- `Слв` — перша літера на початку слова (не знайде «багатоСЛіВний»).
- `СЛВ` (усі великі) — усі літери поспіль від початку слова: `БУК` = «БУКви», не «БрУньКи».
- Кілька шаблонів розподіляються по РІЗНИХ словах так, щоб кожен отримав своє (паросполучення): `слв баг` → «баг» бере «БАГатослівний», «слв» — «СЛоВотворець».
- Порядок слів — дискусійний (схилялись до «будь-який»).
