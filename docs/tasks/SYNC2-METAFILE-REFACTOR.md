# SYNC2-METAFILE-REFACTOR — сховище метаданих для великих vault-ів

> **Статус:** дизайн-документ. ТІЛЬКИ про **сховище** метаданих для vault-ів масштабу
> 2k–20k+ файлів: **hot-файл** (кілька глобальних sync-параметрів, atomic) + **cold-кошики**
> (per-file baseline; hash-buckets + MRU-кеш) проти **write-amplification**, crash-safe через
> наявний `atomic-write.ts`. Реалізація — ІНКРЕМЕНТАЛЬНО, кожен шар gated виміром (§4).
>
> **Область — вузька (ЯК ЗБЕРІГАТИ), не сканування й не алгоритм:**
> - **Двигун** (commit change-detection + drain/pull/push + конфлікти + diff3) → [`SYNC-FIX.md`](./SYNC-FIX.md).
> - **Dot-простір** (ЯКІ dot-файли/теки синкати + `readRootGitignore`/`walkDotDir` + on-device
>   виміри) → [`SYNC2-DOT-FILES-REFACTOR.md`](./SYNC2-DOT-FILES-REFACTOR.md).
> - **Цей файл** — лише як зберігати на диску (a) кілька глобальних параметрів, (b) per-file
>   baseline-мапу, щоб зміна одного файлу не переписувала все й переживала краш, і
>   (c) freshness-мітки керованих `.gitignore` (§6 — окремий per-device файл у `.runtime/`).

## 1. Що це за дані й чому їх складно зберігати

Плагін тримає `Sync2Metadata` (`src/sync2/snapshot-store.ts`). Це **дві РІЗНОРІДНІ породи**
даних — саме тому потрібне розділення.

### A. Глобальні sync-параметри («hot») — кілька крихітних, критичних

`lastSyncCommitSha`, `lastSyncTreeSha`, `lastCommitMtime` (watermark), `remoteIdentity`
(owner/repo/branch), `conflictBranch`, `heldPluginUpdates` (див.[`PLUGIN-UPDATE-COMPAT.md, п.5.5`](./PLUGIN-UPDATE-COMPAT.md#55-форма-запису)). 
Разом — кількасот байт. **Незамінні:** втрата = плагін «забув, де він» відносно 
GitHub → перезалив увесь vault / насипав фальш-конфліктів. Окремо: **`lastSyncTreeSha` — 
це ще й ЯКІР до merge-баз** (див. B).

### B. invariantState

`invariantState` — **НЕ в hot і НЕ в cold: власний файл у `.runtime/`** (рішення власника,
2026-08-02; повна специфікація — §6).

**Призначення** (уточнено власником): це мітки «коли плагін востаннє записав свій
**константний блок**» у керовані `.gitignore`. Потрібні, щоб на кожному commit **дешево**
(`stat`, без читання й хешування) виявити, що файл хтось зачепив, і **відновити блок**.
Тобто це не «кеш заради швидкості взагалі», а freshness-облік конкретних керованих
областей.

**Стан коду на сьогодні:** поле пишеться, але **не читається** — short-circuit знято
(`void recorded;` у всіх трьох `enforce*`). Причина зняття важлива й лишається чинною:
при апгрейді плагіна змінюється сама **КОНСТАНТА** блоку, а файл на диску не рухається →
`mtime`+`size` збігаються → перевірка сказала б «свіжо» і нові канонічні рядки **ніколи
не доїхали б**. ⚠️ Тому відновлення short-circuit **вимагає** третього поля — відбитка
канонічного блоку (§6.3). Без нього це буде регрес до вже виправленого багу.

Класифікація: за формою це НЕ hot (не глобальний sync-параметр) і НЕ cold (не per-file
baseline) — це per-device службовий облік, чиє джерело істини — локальний диск, а не
GitHub. Втрата = один зайвий повний прохід відновлення, не втрата даних.

### C. Per-file baseline-мапа `files{}` («cold») — багато, per-file, і ЗОВСІМ не disposable

`{ path → { remoteSha, mtime, size } }` — стан кожного файлу **на момент останнього синку**
(НЕ поточний стан файлу в local Vault!). ~2.6 МБ на 20k, і **зростатиме** (dot-простір тепер
теж сюди — §3; rewrite drain додасть). Ключове:
- **`remoteSha` — це BASE для diff3.** Спільний предок у `mergeText(ours, BASE, theirs)`
  (pull-side, `pullIfNeeded` Case 3, `sync2-manager.ts:2081`, `base`←`previousRemoteSha`
  ←`files.remoteSha`). Тобто `files{}` — **сховище merge-баз**, а НЕ «дешевий кеш».
  ⚠️ **Кваліфікація:** `files.remoteSha` — це база для **pull-merge** і для **ПЕРШОГО**
  reconcile шляху; для **послідовних batch-ів того самого файлу** база НЕ `snap.remoteSha`,
  а **rolling** (SYNC-FIX П3/П4-refutation — саме тому snapshot тут — хибна база). Тобто
  «files.remoteSha IS the diff3 base» — не безумовно; деталі rolling-бази — у SYNC-FIX.
- **`mtime`/`size` — captured-AT-SYNC**, не поточні. `getFiles()` дає ПОТОЧНІ — інші для
  будь-якого редагованого-після-синку файлу (на цьому й тримається детекція змін).

**Два споживачі `files{}`:**
1. **commit** (детекція змін, `change-detector.ts` §40): reference «чи змінився?» = остання
   закомічена версія шляху = найновіший queued batch (`peekLatestPathSha`) **?? `files.remoteSha`**
   (fallback, коли файлу нема в жодному batch у `.runtime/push-queue/`). `getFiles()` тут —
   лише вхід Pass 1 (поточний mtime vs watermark), а НЕ джерело збережених значень.
2. **drain** (3-way merge): `files.remoteSha` → **BASE** у `diff3(BASE, local, remote)`.

### Проблема сховища — write-amplification

Сьогодні все лежить в ОДНОМУ `<configDir>/github-easy-sync-metadata.json`, повністю в RAM,
переписується **ЦІЛКОМ** (сирий `adapter.write`, не atomic) ~щобатч → **~2.6 МБ перезапис на
КОЖНУ зміну ОДНОГО файлу**, росте з розміром vault (виміри — DOT-FILES §14).

### Recovery — НЕ локальний рескан (виправлення попередньої тези)

Оскільки `files{}` — це baseline + merge-бази, чиє **джерело істини — GitHub**, втрата мапи
відновлюється НЕ пересканом vault, а **ре-деривацією з remote**: дерево@`lastSyncTreeSha`
→ per-file base-sha (+ `getBlob` за вмістом бази) + локальний скан для НОВОГО mtime/size.
Наслідок: **hot священний** — він і незамінний, і **ключ до відновлення cold**. Втрата hot
(`lastSyncTreeSha`/`lastSyncCommitSha`) → нема якоря до merge-баз → 3-way merge неможливий
→ **шторм фальш-конфліктів** (дані цілі, I2 тримає, але UX руйнується).

⚠️ **Precondition:** ре-деривація можлива, ЛИШЕ доки коміт `lastSyncTreeSha` ще досяжний на
remote. Після force-push / history-rewrite / GC його нема — і `pullIfNeeded` уже це ловить
(гілка 404-on-compare, `sync2-manager.ts:~1188`, просуває `lastSync` на живий head). Тоді
cold з СТАРОГО дерева не ре-деривується взагалі: падаємо в повний adoption проти поточного
head **без бази** — тобто саме випадок, коли теза «cold recoverable» не виконується.

## 2. Дизайн сховища

> **«hot/cold» — про ФОРМУ даних** (кілька-глобальних-разом vs багато-per-file), обране
> заради crash-ізоляції + write-amplification. **НЕ про важливість:** cold так само
> критичний (merge-бази §1.C) — просто його багато й воно per-file.

### Hot — 2-слотовий ping-pong із `seq` (ВИРІШЕНО 2026-08-05)

Глобальні sync-параметри (§1.A) → **ОКРЕМИЙ малий файл**, але записаний **не** через
`atomicWriteFile`, а **двома слотами по черзі** — тим самим протоколом, який уже працює для
позиції курсора в diff-редакторі (`src/diff2/cursor-store.ts`, DIFF-EDITOR §2.9).

**Протокол.** Два слоти `metadata-a.json` / `metadata-b.json`, кожен несе монотонний `seq`.
Кожен запис починається з читання ОБОХ слотів — із них одразу виводяться і ціль, і наступний
`seq`:

| що прочиталось | `seq` для запису | куди пишемо |
|---|---|---|
| обидва валідні | `max(seqA, seqB) + 1` | слот із **меншим** seq (нічия → `a`) |
| валідний один | `seqВалідного + 1` | **невалідний** — він читається як `−1`, отже він і є менший |
| жодного | `0` | `a` |

Далі — звичайний `adapter.write` (без staging, без rename). Читання при відновленні: слот із
**найбільшим ВАЛІДНИМ** `seq`; торн-слот не парситься і програє.

Третій рядок таблиці дає корисну властивість задарма: **побитий слот сам стає ціллю наступного
запису** й полікується. Саме тому його й не треба видаляти окремо.

⚠️ **Інваріант: слот із max-seq не пишеться НІКОЛИ.** Плоский `adapter.write` тут crash-safe
рівно тому, що сусідній слот лишається цілим і слугує fallback-ом.

**Ціль запису й наступний `seq` завжди виводяться з ДИСКА, ніколи з памʼяті.** Тримати
«який слот стейлий» у RAM заради економії на двох читаннях — не робимо: hot пишеться на кожен
запушений batch, а між двома записами лежить повний REST-раунд до GitHub, тож два читання
малих файлів на цьому тлі не міряються (а без виміру оптимізацій не робимо). Причина при цьому
НЕ в довговічності — перечитування її не доводить (потрапляє в той самий page cache; `fsync`
адаптер Obsidian не дає). Причина в тому, що диск — **єдине джерело істини про те, який слот
зараз fallback**, а стан там міг змінитися способом, про який RAM не знає: торн-слот після
краху, видалена reset-ом тека `.runtime/` ([`RESET-PLUGIN.md`](./RESET-PLUGIN.md)), слот із
бекапу, перезапуск плагіна між записами.

**Успішність запису = відсутність винятку. Read-back НЕ робимо.** Перечитувати записане й
звіряти не потрібно, бо невдалий запис тут — **уже оброблений випадок, а не стан відмови**:
слот із max-seq лишився цілим, відновлення прочитає його, і ми втратимо найсвіжіший стан
(наприклад, `lastSyncCommitSha` відстане на один batch — наступний sync дожене), а не
цілісність. Виняток же просто йде вгору до викликача: відкочувати нічого, бо в памʼяті ми
нічого не змінювали, а наступна спроба перечитає диск і обере ту саму ціль.

Тест на цю пару потрібен свій — `cursor-store.test.ts` пінить інваріант «max-seq слот ніколи
не є ціллю запису» для курсора, hot-парі потрібен еквівалент.

**Чому не `atomicWriteFile`** — менше рухомих частин на найкритичнішому файлі:

| | `atomicWriteFile` | ping-pong |
|---|---|---|
| rename | 2 (+`exists`+`remove` на Capacitor — там rename не перезаписує) | **0** |
| staging / marker-файли | `.sync-tmp`, `.sync-bak`, marker | **0** |
| участь у `AtomicWriteRecovery.sweep` | потрібна | **не потрібна** — відновлення вбудоване в шлях читання |
| вікно, коли цільового файлу нема | є (mobile: між `remove` і `rename`) | **нема** |

Вимір уже є в коді, новий не потрібен: `cursor-store.ts:9` фіксує `rename p95≈28ms` плюс
вікно без файлу — саме тому там свого часу й відмовились від temp+rename.

#### Дискримінатор — лічильник, а НЕ годинник

Розглядався варіант писати замість `seq` власний час (wall clock мінус офсет, знятий на
старті). Відхилено; причина важлива, бо інакше її переграють наново.

Схема з годинником має дві діри: (а) **рівні значення** — `Date.now()` має мс-роздільність,
а нічия в 2-слотовій схемі робить питання «який свіжіший» **невідповідальним**, і tie-break
запише слот, який може бути єдиною цілою копією; (б) **офсет заморожений на старті** — тож
захист діє лише проти годинника, який був неправильний ДО сесії, а не проти NTP-степу
назад ПОСЕРЕД неї (звичайний мобільний сценарій: пристрій завантажився офлайн зі старим
годинником, потім зʼявилась мережа). Обидві діри закриває клемп `max(prev+1, clock-offset)`
— це коректна HLC-конструкція, але після клемпа гарантію несе виключно `+1`-лічильник, а
годинникова складова стає прикрасою на дискримінаторі.

**Ключова відмінність від решти двигуна, і причина, чому саме тут це критично.** Двигун
ніде не питає «чи цей час ПІЗНІШЕ за той» — він питає «чи цей stat ВІДРІЗНЯЄТЬСЯ від
записаного». Перевірка на різницю не залежить від напрямку годинника; перевірка на порядок
— залежить. Аудит підтверджує: `change-detector.ts:211` — **єдине** порівняння часу на
порядок в усіх `src/sync2/` + `src/diff2/`, і навіть воно не є визначальним (пропуск при
`mtime <= watermark` вимагає ТОЧНОГО збігу stat із записаним baseline, `:218-222`; не
збіглося — `// Fall through` на `read`+SHA). Решта `now()` — це штампування в поле запису
(`conflict-classifier.ts:216,220`, `conflict-store.ts:242`,
`pending-deletions-store.ts:147`), жодне з них ні з чим не звіряється.

Ping-pong-слоти — **єдина** конструкція в дизайні, де питання за природою є питанням
ПОРЯДКУ («який із двох свіжіший») і де немає baseline, з яким можна звірити різницю. Тому
годинник як дискримінатор створив би тут вразливість, якої в проєкті більше ніде немає.

#### Решта форми запису

- **Один блоб на весь hot, не по полях.** Групує не розмір (кількасот байт — вартість це
  syscall на слот, не байти), а те, **що мусить бути взаємно узгодженим при читанні**:
  `lastSyncCommitSha` + `lastSyncTreeSha` + `lastCommitMtime` — це один якір до merge-баз, і
  скіс між ними = якір показує на не те дерево = катастрофа §1.A. Побічно це **покращення**
  проти сьогоднішнього: `setLastSync` і `setLastCommitMtime` зараз два окремі виклики
  (`sync2-manager.ts:3822-3823`).
- **`savedAt` (ISO) — окремим полем, суто діагностика.** Дає те, заради чого й спокушав
  годинник: подивився у файл — бачиш, коли писано. ⚠️ **Читати його як дискримінатор
  заборонено** — відновлення дивиться ТІЛЬКИ на `seq`.
- **`seq` продовжується з диска** на старті (max валідних, обидва невалідні → `−1`) — на
  відміну від `cursor-store`, де він задокументований як per-session (`:27`).
- **Побитий слот НЕ видаляємо.** Він читається як `seq = −1` і сам стає ціллю наступного
  запису; видалення додало б ФС-операцію на шляху відновлення і знищило б доказ, якби
  впали обидва слоти.
- **Міграція:** одноразове читання старого `github-easy-sync-metadata.json` → засів слота
  `a` зі `seq: 0`.
- **Контрольна сума не потрібна:** `JSON.parse` + перевірка форми (як `cursor-store.readSlot`)
  для малого JSON достатньо — торнутий запис не парситься.

**Write-rate (для виміру §4 крок 2):** hot-файл пишеться **на КОЖЕН запушений batch**
(`setLastSync`+`setLastCommitMtime`, `sync2-manager.ts:3822-3823`) + на pull / зміну
conflict-branch. Тобто 10-batch drain = **~10 записів hot-файлу** — але кількасот байт
кожен, тож дешево; §4 крок 2 міряє саме проти цієї частоти.

### Cold — hash-кошики + MRU-кеш

- **Hash-кошики.** `files{}` розбита на **N кошиків** за `hash(path)`; ім'я файлу кошика =
  `<hash>.json`. N — TBD (32 / 64 / …).
- **In-memory MRU-кеш ≤ ~5 кошиків.** Потрібен новий кошик → **найстаріший (LRU)
  витісняється** з кешу.
- **Write-through:** щойно кошик змінено — flush на диск **якнайшвидше** → у кеші dirty
  кошиків бути НЕ повинно → витіснення старішого = просто **викид з кешу** (нічого писати).
- **Fallback (усі кошики в кеші виявились dirty):** перед витісненням найстаріший
  **пишеться на диск** тим самим `atomicWriteFile` (`.sync-tmp`/`.sync-bak` staging +
  recovery/rollback на рестарті), і лише тоді викидається.
- Зміна метаданих 1 файлу = atomic-write **ЛИШЕ його кошика** → write-amplification
  O(vault)→O(bucket); торн зачіпає 1 кошик, не всю мапу.

### Dot-простір — теж у ці кошики (§3)

Per DOT-FILES: dot-файли + normal-файли в дозволених dot-теках отримують записи в `files{}`
(тобто в кошики) → відслідковуються при commit і merge-аться в drain **як ordinary-файли**.
Зараз цього нема (dot-простір поза `files{}` → ні change-tracking, ні коректний diff3 для них).

### Розташування на диску (поточне → майбутнє)

**Зараз:** усе (hot + cold) в ОДНОМУ файлі `<configDir>/github-easy-sync-metadata.json`
(`SYNC2_MANIFEST_FILE_NAME`; виключений із синку в `isSyncable`).

**Майбутнє — у per-device `.runtime/`** (`<configDir>/plugins/<plugin-id>/.runtime/` — уже
hardcoded-excluded зі синку як per-device runtime-стан, `change-detector.ts:45`):
- **hot** → `.runtime/metadata-a.json` + `.runtime/metadata-b.json` (ping-pong пара, див. вище).
  Окремого правила виключення зі синку **не потрібно**: гейт стоїть на КОРЕНІ `.runtime/`
  (`change-detector.ts:45` — префіксна перевірка, за коментарем «covers every current AND
  future runtime artifact without a per-item list»), тож обидва слоти під нього підпадають
  автоматично. Це умова працездатності, а не гігієна: якби один слот виїхав на GitHub і
  приїхав на інший пристрій, він приніс би з собою чужий `seq`;
- **cold** → каталог `.runtime/file-baselines/` з файлами-кошиками `<hash>.json`.

> **Назва cold-каталогу** (власник просив «кращу для розуміння»): пропоную **`file-baselines/`**
> — точно описує вміст (per-file baseline = diff3-база), і уникає плутанини `metadata.json`
> (файл) vs `metadata/` (каталог) з однаковим стемом. Прийнятна альтернатива-пара —
> `files-metadata/`. Фінальна назва — за власником.

---

## 3. Сильні боки

- **Bucketing** — write-amplification O(vault)→O(bucket); RAM-ощадно (у пам'яті ≤~5 кошиків,
  не вся 2.6 МБ+ мапа).
- **Crash-ізоляція:** торн зачіпає 1 кошик; його baseline ре-деривується з remote
  (дерево@`lastSyncTreeSha`) — не глобальна втрата.
- **Hot окремо:** якір до merge-баз (`lastSyncTreeSha`) НЕ їде в одній «фурі» з великою
  мапою → торн cold ніколи не вбиває `lastSync`.
- **Жодного нового crash-протоколу:** hot іде ping-pong-ом (уже працює в
  `diff2/cursor-store.ts`), dirty-кошик — наявним `atomicWriteFile` + `AtomicWriteRecovery`
  (sync-tmp/sync-bak, sweep на onload). Обидва механізми в проєкті вже є й перевірені.

---

## 4. Рекомендований порядок (інкрементально, gated виміром)

НЕ будувати все одразу; кожен шар — коли попередній виміряно недостатнім:
1. **Зараз (KISS):** atomic (`atomicWriteFile`) для поточного суцільного маніфесту; прибрати
   no-op idle save; коалесувати не-crash save.
2. **Hot/cold split:** винести глобальні параметри (§1.A) в окрему ping-pong пару слотів
   (§2). → міряти.
3. **Bucketing + MRU:** якщо cold-мапа janks на 20k (а з dot-простором — тим паче) → кошики
   + MRU-кеш (§2). → міряти.

## 6. `invariantState` — окремий файл у `.runtime/` (ВИРІШЕНО 2026-08-02)

> **Рішення власника.** Не hot, не cold, не викидати — **власний малий файл**.
> Тут — тільки СХОВИЩЕ (область цього документа). Що саме сканується й що
> відновлюється — [`SYNC2-DOT-FILES-REFACTOR.md`](./SYNC2-DOT-FILES-REFACTOR.md) §3.1.2.

### 6.1 Що це і навіщо

Мітки «коли плагін востаннє записав свій **константний блок**» у керовані `.gitignore`.
Мета — на старті commit і drain **дешево** (`stat`) зрозуміти, що файл зачепили, і
відновити блок, не читаючи й не хешуючи кожен файл щоразу.

### 6.2 Множина файлів більше НЕ фіксована

Раніше було три слоти (`configDirGitignore` / `selfPluginGitignore` / `rootGitignore`).
Тепер це **мапа за шляхом**, бо додаються `.gitignore` СТОРОННІХ плагінів — вони
з'являються і зникають разом із плагінами:

| шлях | існує завжди? | режим володіння |
|---|---|---|
| `<vault>/.gitignore` | так (`enforce()` створює) | splice блоку, юзерський вміст цілий |
| `<configDir>/.gitignore` | так (`enforce()` створює) | splice блоку + нижня керована пара |
| `<configDir>/plugins/<self>/.gitignore` | так | **повний перезапис** константою |
| `<configDir>/plugins/<інші>/.gitignore` | **тільки якщо вже є** | чіпаємо ЛИШЕ kill-switch-пару |

Наслідки для схеми: (а) записи для зниклих файлів треба **прибирати** (плагін видалили),
(б) поява нового чужого `.gitignore` — це просто відсутній запис → повний шлях
`read+splice+write`, (в) `Sync2InvariantState` перестає бути трьома опційними полями.

### 6.3 ⚠️ Запис МУСИТЬ містити відбиток канонічного блоку

`{ mtime, size }` **недостатньо**. Це рівно та конструкція, яку колись зняли з коду
(`void recorded;` у трьох `enforce*`). Нижче — чому, простою мовою.

**Спершу термінологія, бо вона плутає.** «Константа» — це рядок **у коді плагіна**, не на
диску: `ROOT_INVARIANT_BLOCK` (`gitignore-invariants.ts:93`), те, що повертає
`configDirInvariantBlock()` (`:44`), і `SELF_PLUGIN_GITIGNORE` (`:80`). Вони вшиті в
`main.js` і приїжджають разом із новою версією плагіна. «Канонічні рядки» — просто рядки
з цих констант, які `enforce()` вставляє у `.gitignore` на диску.

**Сценарій по кроках.**

Плагін 1.0 — у коді константа = блок **A**:

```
*.conflict-from-*
*.sync-tmp*
```

`enforce()` записує A у `<vault>/.gitignore` і запам'ятовує `mtime=10:00`, `size=200`.

Юзер оновлює плагін до 2.0 — ми дописали в константу два рядки, тепер це блок **B**:

```
*.conflict-from-*
*.sync-tmp*
.*              ← нове
.*/             ← нове
```

А файл на диску **ніхто не чіпав**: юзер його не редагував, ми його не переписували. Там
і досі блок A, і досі `mtime=10:00`, `size=200`. Перевірка «тільки mtime+size» каже:

```
записано:  mtime=10:00  size=200
на диску:  mtime=10:00  size=200
збіглося → «свіжо, нічого робити» → вихід
```

І блок **B ніколи не потрапляє у файл**. Юзер оновив плагін, а `.*` / `.*/` у нього так і
не з'явились — уся нова фіча на цьому пристрої мовчки не працює, доки хтось випадково не
торкне файл.

**Чому так виходить.** `mtime+size` відповідає на питання «чи хтось чіпав ФАЙЛ?». Але
застаріти файл може двома різними способами:

| як файл стає неправильним | mtime/size рухаються? | `mtime+size` ловить? |
|---|---|---|
| юзер відредагував `.gitignore` | так | ✅ |
| **ми змінили думку** — у новій версії плагіна інша константа | **ні** | ❌ |

Другий випадок перевірка не бачить у принципі: диск справді не змінився, змінилось те,
чого ми **хочемо** від цього диска. Саме на цей баг колись наступили і прибрали
short-circuit ЦІЛКОМ, замість полагодити (коментар `gitignore-invariants.ts:288-300`).
Ми повертаємо дешевий шлях — отже мусимо полагодити те, що тоді просто вимкнули.

**Що дає третє поле.** Записуємо **SHA + довжину** того блоку, який ми **тоді** вставили:

```
{ mtime, size, blockSha, blockLen }
```

На перевірці рахуємо SHA блоку, який **зараз хочемо** (тобто поточної константи для
поточного стану):

```
плагін 1.0:  blockSha == SHA(бажаний A)  → усі три збіглись → пропускаємо      ✅ дешево
плагін 2.0:  blockSha(A) != SHA(бажаний B) → розійшлось     → read+splice+write ✅ блок доїхав
```

Тобто третє поле відповідає на ДРУГЕ питання: «чи те, що ми колись записали, — це все ще
те, що ми хочемо записати?». Short-circuit спрацьовує **лише коли збіглися всі три**;
розійшовся будь-який — повний `read + splice + compare`, як зараз. Так наявний фікс
зберігається, а дешевий шлях повертається.

**Навіщо ще й `blockLen`** (рішення власника): SHA сам по собі відповідає лише «збіглось /
не збіглось» — ним нічого не **знайдеш** у файлі. Пара «довжина + SHA» це вміє:
відступити від маркера на `blockLen`, порахувати SHA цього відрізка й переконатися, що
це саме наш старий блок, — і аж тоді його вирізати. Це і є ремонт при пошкоджених
маркерах (DOT-FILES §3.1.3). Зберігати сам ТЕКСТ для цього не потрібно: ~45 байт на
запис проти кількох сотень.

**`blockSha`/`blockLen` міряються від ТІЛА БЕЗ маркерів** — так за специфікацією власника,
і це не деталь оформлення, а умова працездатності: якщо юзер видалив рядок `END`, то при
маркер-інклюзивному вимірі відрізок довжини `blockLen` від `BEGIN` захопив би тіло **плюс
шматок юзерського тексту** → SHA не збігся б → нотиця саме тоді, коли ремонт і потрібен.
Тіло без маркерів знімає це повністю.

⚠️ **Наслідок для КОДУ, а не для схеми:** сьогодні окремого значення «тільки тіло» не
існує. Самі маркери вже є окремими замороженими константами (`INVARIANT_BEGIN`/
`INVARIANT_END`, `gitignore-invariants.ts:11-14`) — злита **композиція**:
`configDirInvariantBlock()` (`:50-59`) і `ROOT_INVARIANT_BLOCK` (`:93-105`) інтерполюють
їх усередину шаблону й віддають готовий `marker+body+marker`. Треба виділити тіло в
самостійне значення, а склейку з маркерами робити на місці запису. Повне обґрунтування
(і чому це головна причина, а не наслідок виміру) — DOT-FILES §3.1.3.

⚠️ **Одиниці виміру пінити явно.** `blockLen` і `blockSha` мусять рахуватися над ОДНИМ
представленням. Рекомендація: працювати в байтах UTF-8 (маркери містять `—`, тіло теж
може бути не-ASCII), і брати наявний `calculateGitBlobSHA` — він і так прив'язує довжину
всередині preimage (`blob <len>\0`), тож `blockLen` не можна підробити окремо від SHA.
Якщо ж різати рядок через `substring`, то й довжина має бути в JS-символах. Змішати
одне з іншим = ремонт мовчки не спрацьовує ніколи.

**Бонус — kill-switch не потребує власного поля.** Відбиток рахується від блоку,
БАЖАНОГО для поточного стану, а не від фіксованого тексту. При `syncConfigDir=false`
бажаний вміст включає пару `# syncConfigDir=false` + `*`, при `true` — ні. Отже юзер
клацнув тумблер → бажаний блок інший → відбиток інший → розійшлось → перезаписали.
Перемикач інвалідує кеш сам собою: не треба ні окремого поля «чи має зараз стояти
kill-switch», ні ловити момент перемикання (DOT-FILES §3.1.1).

### 6.4 Розташування й формат

- **Файл:** `<configDir>/plugins/<self>/.runtime/gitignore-invariants.json`.
- Чому `.runtime/`: він **hardcoded-excluded зі синку** (`change-detector.ts:45`), а ці
  дані **принципово per-device** — `mtime` локальний і на іншій машині безглуздий.
  Синхронізувати їх було б активною шкодою.
- Пишеться через `atomicWriteFile` — але **не заради даних**: втрата файлу коштує рівно
  один зайвий повний прохід відновлення. Атомарність тут лише щоб торн-JSON не змушував
  ловити parse-помилку; будь-яка непрочитана/побита версія трактується як «порожньо».
  ⚠️ Не плутати з атомарністю **самих `.gitignore`** — вона обов'язкова з іншої, серйознішої
  причини (обрізаний файл ламає scope) і специфікована в DOT-FILES §3.1.2.
- **Коли пишеться:** після кожного проходу, який щось змінив (як `refreshState` сьогодні).
  ⚠️ Обов'язково **re-stat ПІСЛЯ запису** цільового `.gitignore` — інакше записаний
  `mtime` буде дорейтовий, наступний прохід побачить «змінено» і перезапише знову
  (нескінченний rewrite). Наявний `refreshState` (`gitignore-invariants.ts:400-412`) уже
  так робить — цю властивість зберегти.
- **Прибрати:** `Sync2Metadata.invariantState` разом із його гілкою в `migrate()`
  (`snapshot-store.ts:115-131`) — поле переїжджає, а не дублюється. Тести
  `tests/sync2/gitignore-invariants.test.ts:198/233/295` пінять старий шлях і поїдуть
  разом із ним.
