# SYNC2-METAFILE-REFACTOR — сховище метаданих для великих vault-ів

> **Статус:** дизайн-документ (не готовий план). ТІЛЬКИ про **сховище** метаданих
> (per-file SHA/mtime/size) для vault-ів масштабу 2k–20k+ файлів: hash-кошики +
> write-through LRU + hot/cold split проти **write-amplification**. Реалізація —
> ІНКРЕМЕНТАЛЬНО, кожен шар gated виміром (§4).
>
> **Область — вузька (сховище), не сканування:**
> - **Двигун** (drain/pull/push + конфлікти) → [`SYNC-FIX.md`](./SYNC-FIX.md).
> - **Dot-простір** (ЯКІ dot-файли/теки синкати + рекурсивний `walkDotDir` + on-device
>   виміри вартості скану) → [`SYNC2-DOT-FILES-REFACTOR.md`](./SYNC2-DOT-FILES-REFACTOR.md).
>   Тут цього НЕМАЄ (перенесено; попередня «depth/Model-B»-концепція ВІДХИЛена там).
> - **Цей файл** — лише як ЗБЕРІГАТИ на диску мапу метаданих, щоб зміна одного файлу не
>   переписувала всю мапу.

---

## 1. Проблема — write-amplification (виміряно)

Поточне сховище: один `<configDir>/github-easy-sync-metadata.json`, повністю в RAM,
переписується **ЦІЛКОМ** (сирий `adapter.write`, не temp+rename) ~щобатч. На 20k файлів
це **~2.6 МБ перезапис на КОЖНУ зміну одного файлу** → write-amplification, що росте з
розміром vault. Це — єдина проблема, яку лікує цей документ.

Джерело даних мапи — безкоштовне й НЕ вузьке місце: метадані regular-файлів беруться з
`getFiles()`-індексу (~5 мс на 20k, нуль adapter-I/O; `adapter.stat` заборонений —
~2000× повільніше; повні числа — DOT-FILES §14). Тобто **сканування** дешеве; лікуємо
саме **запис**.

---

## 2. Дизайн — buckets + write-through LRU + hot/cold split

**П2. Hash-кошики (16/32/64).** Файли розкидані по N кошиках за `hash(filepath)`. Зміна
метаданих одного файлу = **atomic-write (temp+rename) ЛИШЕ його кошика**, не всієї мапи.
→ write-amplification падає з O(vault) до O(bucket); crash-ізоляція (торн 1 кошик, не вся
мапа).

**П3. In-memory write-through LRU (~5 кошиків).** Тримаємо кілька кошиків у RAM; при
потребі завантажити новий — найстаріший вивантажується. **Write-through:** зміна в кошику
одразу flush-иться на диск → вивантаження старого = завжди просто **викид ЧИСТОГО**
кошика (нічого писати).

**Hot/cold split (crash-критичне НЕ в кошиках).**
`lastSync`/`lastSyncTree`/watermark/`conflictBranch`/`remoteIdentity` — **crash-критичні
й малі** — лишаються в ОКРЕМОМУ малому atomically-written **hot-файлі**, НЕ в кошиках.
Per-file SHA-мапа → **cold-кошики**. Дизайн має це розвести явно (інакше торн-кошик міг
би зачепити crash-критичний стан).

---

## 3. Сильні боки

- **Bucketing + write-through LRU** розв'язує write-amplification (виміряно) з
  clean-eviction — елегантно.
- **Atomic-per-bucket** → крихка crash-ізоляція: торн зачіпає 1 кошик, не всю мапу.
- **Hot/cold split** тримає crash-критичний стан малим і окремо атомарним — торн cold-мапи
  не втрачає `lastSync`/watermark.

---

## 4. РЕКОМЕНДОВАНИЙ порядок (інкрементально, gated виміром)

НЕ будувати все одразу. Кожен шар — коли попередній виміряно недостатнім:

1. **Зараз, безумовно (дешеве, KISS):** `temp+rename` для маніфесту; прибрати no-op idle
   save; коалесувати не-crash save.
2. **Hot/cold split (§2):** малий hot-файл (crash-критичне) + велика cold-мапа. → міряти.
3. **Bucketing + write-through LRU (§2):** якщо cold-мапа janks на 20k → кошики. → міряти.

---

## 5. Відкриті питання (рішення власника)

- Кількість кошиків (16/32/64) + розмір LRU — тюнити виміром.
- Точна межа hot/cold (що саме crash-критичне).
- Windows/Linux baseline для hot/cold — ще не міряно.
