## 1. Контекст — ЧОМУ (виміряно 2026-07/08)

Поточне сховище: один `<configDir>/github-easy-sync-metadata.json`, повністю в RAM,
переписується цілком (сирий `adapter.write`, не temp+rename) ~щобатч. Проблеми
(проблеми — §4 нижче) + **виміряні** числа (dev-бенчмарк, 2000-тек дерево × 22k файлів):

| метрика | macOS (desktop) | Android (Capacitor) |
|---|---|---|
| рекурсивний `adapter.list` walk (2001 тек) | ~1.9 с | **~22 с** (16-34 с, мінлива) |
| `adapter.stat` per-file (20k regular) | 1.2 с (~0.06 мс) | **~59 с** (~2.94 мс) |
| ті самі regular через `getFiles()`-індекс | 19-30 мс | 30 мс |
| **index vs adapter.stat (regulars)** | **~64×** | **~1966×** 🔥 |
| `adapter.list` бачить dot-файли? | 2000/2000 ✅ | 2000/2000 ✅ |
| dir-mtime бампає на create/delete/rename? | RELIABLE ✅ | **RELIABLE ✅** (modify — ні) |
| **`vault.on` спрацьовує для dot-файлів?** | **НІ ❌** | **НІ ❌** |

**⚠️ ВИРІШАЛЬНА знахідка (event-тест, macOS+Android 2026-08):** `vault.on`
create/modify/delete **СЛІПИЙ до dot-простору на ОБОХ платформах** (контроль-regular дає
всі 3 події; `.dotfile` і `.dotdir/inside.md` — **нуль** подій). Причина: `vault.on`
прив'язаний до індексу Obsidian, який dot-простір виключає. **→ Журнал подій (§2 П4)
НЕ МОЖЕ трекати dot-простір** — його головне виправдання зникає (для regulars він
надлишковий, §4.3). **Дизайн СПРОЩУЄТЬСЯ: журнал (П4-П6) ВИКИДАЄМО** — див. §4.6.

**✅ getFiles()-скан (реальна hot-path findChanges Pass 1) — БЕЗКОШТОВНИЙ:** ітерація
20k файлів із порівнянням mtime = **macOS 3.4 мс / Android 5.4 мс** (~0.2 µs/файл, нуль
adapter-I/O). vs `adapter.stat` тих самих 20k = 59с Android → індекс **~10 000× швидше**.
**Регулярний per-commit change-scan — НЕ bottleneck.**

**✅ dot-scan cost vs ГЛИБИНА (для settings-параметра §2.0):**

| depth | dirs | dots | macOS | Android |
|---|---|---|---|---|
| **0** (default) | 1 | 0 | 1 мс | 9 мс |
| 1 | 9 | 8 | 18 мс | 91 мс |
| 2 | 73 | 72 | 103 мс | 554 мс |
| 3 | 585 | 584 | 718 мс | ~4 с |
| 4 (повне) | 2001 | 2000 | ~2 с | ~10 с |

Лінійно за к-стю тек (~0.9 мс/тека macOS, ~4 мс/тека Android-IPC); кожен +1 рівень ≈ ×8.
**depth 0 = ~безкоштовно → дефолт правильний.** Android-`adapter.list` дуже мінливий
(8-34с для 2000 тек — cache/thermal).

**Тверді висновки, що диктують дизайн:**
- **Повний `**/.*` walk щокоміт — неможливий на mobile** (~10-22 с лише list).
- **`adapter.stat` на sync-шляху — заборонено** (Android ~59 с; index ~10 000× швидше).
  Regular-файли → ЗАВЖДИ `getFiles()`-індекс (~5 мс/20k).
- **Adapter-I/O прив'язаний до MAIN-потоку** (worker не має доступу до `vault.adapter`,
  правило `sync2-engine.md`); async-yield → не жорсткий фриз, але повільна операція.
  Єдиний важіль — **мінімізувати adapter-виклики**.
- **dir-mtime RELIABLE на macOS+Android** → пруніг обходу можливий (за probe; Windows
  ще не міряно; екзотичні ФС/синк-шари крихкі → потрібен backstop).
- **Write-amplification:** зміна 1 файлу → перезапис усього маніфесту (2.6 МБ на 20k) →
  bucketing/hot-cold це лікує.

## 2.0 ✅ ФІНАЛЬНЕ РІШЕННЯ (власник, 2026-08) — 8 кроків СКОРОЧЕНО до 3

Після виміру (event-тест: `vault.on` сліпий до dots; §1) 8-крокову архітектуру
**скорочено**. Лишається:

- **П2 — hash-кошики** (16/32/64), ключ `hash(filepath)`, atomic-write цілого кошика.
- **П3 — LRU-кеш кошиків** (~5), write-through (clean-eviction).
- **НОВЕ — settings-параметр «глибина сканування dot-простору», default = 0.**
  Depth 0 = лише root + `.obsidian/` + `.obsidian/plugins/*` (як зараз). Глибше — dot-теки
  на рівні > 0 **не виявляються й не синкаються**. Хто потребує — збільшує число з
  **попередженням про падіння продуктивності** (рекурсивний `adapter.list`-walk, §1:
  ~22с/скан на Android для 2000 тек). Тобто дорогий deep-dot-walk — OPT-IN і обмежений.

**ВИКИНУТО:** П1 (dir-mtime probe), П4-П6 (event-journal — vault.on не бачить dots),
П7-П8 (dir-mtime-pruned/background dot-scan — не потрібні при depth=0 за замовчуванням).
Regulars — завжди `getFiles()`-індекс (ніколи adapter.stat, §1: ~2000× різниця).

Нижче (§2 повний) — оригінальні 8 кроків для історії/контексту; §3-§7 — аналіз.

## 2. ЗАПРОПОНОВАНА архітектура (8 кроків власника — ІСТОРИЧНО; див. 2.0)

> Записано як подано; актуальне рішення — §2.0. Аналіз — §3–§7.

**П1. Probe dir-mtime на першому запуску, кеш у `data.json`.** При першому старті
плагіна на конкретному vault перевіряємо, чи ця ФС бампає mtime каталогу на
create/delete/rename (як dev-mtime-тест). Результат зберігаємо в `data.json`.
Припущення: vault створюється й живе на одній версії ФС.

**П2. Hash-кошики (16/32/64).** Файли розкидані по N кошиках за `hash(filepath)`.
Зміна метаданих одного файлу = **atomic-write ЦІЛОГО файлу-кошика** (temp+rename).

**П3. In-memory LRU-кеш кошиків (напр., 5).** Тримаємо кілька кошиків у RAM; при
потребі завантажити новий — найстаріший вивантажується. **Write-through:** зміна в
кошику одразу flush-иться на диск → вивантаження старого = завжди просто **викид
чистого** кошика (нічого писати).

**П4. Слухачі подій `ondelete`/`onmodify`/`oncreate` з ПЕРШОГО старту.** Вносять
зміну в hash-table змінених файлів (ключ = `hash(filepath)`). Сотня змін того самого
файлу нічого не додає/віднімає (ідемпотентно). Кожен НОВИЙ запис **інкрементально
append-иться** на диск миттєво (як undo-redo-лог у diff-editor). → унікальний список
змінених файлів і в RAM, і на диску; при перезапуску відновлюється майже миттєво.

**П5. При перезапуску — все одно `getFiles()`-скан regular-файлів** для тих, що
змінились після останнього запису з hash-table (П4). Найшвидше доповнення; це ~98%
потрібних даних.

**П6. Dot-файли/каталоги в hash-table (П4) → в окрему таблицю-файл.** При відновленні
ця таблиця відновлюється з ФС; ці файли перевіряються адресно (файли — напряму,
dot-каталоги — скануванням). Прискорює старт.

**П7. Єдина непокрита ситуація — dot-файли/каталоги, що з'явились МІЖ вимкненням і
вмиканням** → вимагає повного обходу. Оптимізація: **якщо dir-mtime діє** (П1), обходимо
дерево, шукаючи каталоги з mtime, зміненим після останньої операції П4, і ЛИШЕ в них
скануємо dot-файли/каталоги, що з'явились після тієї mtime; шукаємо їх у кеш-кошиках;
не знайшли → новий файл.

**П8. Якщо dir-mtime НЕ діє** → ті самі дії (П7), але скануючи **весь vault**
(`dot-files/dot-dirs/**`). АЛЕ керування ініціалізацією передаємо **одразу після
відновлення hash-table (П4)**; решта — у ФОНІ, скільки треба. **Ризик:** якийсь час
(хвилини) деякі (переважно dot-файли/файли з dot-тек) вважаються немодифікованими й
не потраплять у перші коміти; після завершення скану стають доступними для комітів
(квієсценція, як очікується).

## 3. Аналіз — сильні боки

- **Bucketing + write-through LRU (П2-3)** розв'язує write-amplification (виміряно) з
  clean-eviction — елегантно. Atomic-per-bucket → крихка crash-ізоляція (торн 1 кошик,
  не вся мапа).
- **Події + startup-scan (П4-5,7-8)** — це **валідний гібрид**, що знімає
  polling-заперечення: події = швидкий шлях поки увімкнено; startup-scan = **backstop**
  для «поки вимкнено». Принцип «poll авторитетний» дотримано.
- **dir-mtime pruning gated на probe (П1,7)** — поважає знахідку про платформну
  крихкість (не вживаємо там, де не reliable).
- **Background dot-scan + рання передача керування (П8)** — старт швидкий; повільний
  walk у фоні; квієсценція I3 (файли стають доступні згодом, нічого не втрачено).

## 4. Аналіз — застереження й РИЗИКИ (з advisor)

### 4.1. ⚠️ БЛОКУЮЧЕ — journal і watermark мусять просуватися АТОМАРНО разом
Truncation журналу (П4) — це НЕ лише про розмір, це **коректність**. Якщо журнал
обрізали після коміту, а watermark не просунули (чи навпаки) — відновлений
changed-set і базис скану (П5) **розійдуться**, і файли **проваляться в щілину** — рівно
пастка, доведена в `SYNC-FIX.md` §10.7 (base=lastSync). **Правило:** будь-яке
скидання/обрізання журналу прив'язати до ТІЄЇ САМОЇ атомарної точки, що й
persistence `lastSync`/watermark — **один durable-крок, не два.** Це — головний
коректнісний ризик усього дизайну.

### 4.2. ⚠️ Журнал — ЧЕТВЕРТИЙ писар у спільний стан (нова concurrency-поверхня)
Ми вже знайшли: Phase B (`enqueueSynthetic`) робить drain третім appender-ом у
push_queue (`SYNC-FIX.md` §8.7 п.2). Журнал подій **append-иться з `vault.on`
колбеків** — у ДОВІЛЬНИХ точках, можливо ПОСЕРЕД drain/commit. Тож треба визначити,
який лок/бар'єр керує append-ом журналу відносно commit/drain-бар'єра (`SYNC-FIX.md`
§6 R3). Інакше це нова гонка без протоколу.

### 4.3. Журнал для REGULAR-файлів — майже надлишковий (але НЕ scope-ати до dots)
Для regular-файлів getFiles-скан (П5) і так ловить усе (індекс, дешево), а кандидати
все одно ре-хешуються (`change-detector.ts:290`) — журнал не робить скан дешевшим;
його реальна робота для regulars — це лише **watermark + while-running set**, а
watermark у нас ВЖЕ є (`lastCommitMtime`). **АЛЕ:** НЕ scope-ати журнал лише до
dot-простору — тоді буде ДВА changed-set шляхи (журнал для dots, watermark для
regulars), які треба тримати узгодженими = гірше за обидва. **Або один уніфікований
журнал, або жодного.**

### 4.4. Події ЛОВЛЯТЬ не все — скан лишається авторитетним (точне формулювання)
Obsidian власним watcher-ом оновлює індекс і для ЗОВНІШНІХ змін → `getFiles()`/`f.stat`
їх **бачить**. Тож щілина подій ВУЗЬКА: (а) **dot-простір** (ніколи не в індексі),
(б) вікно, поки watcher не помітив. Журнал (П4) — **підказка/оптимізація**, скан
(П5/7/8) — **авторитет**. Док і реалізація мусять це тримати явно, інакше майбутній
implementer занадто довіриться подіям.

### 4.5. Probe-припущення «один FS» (П1) має межу
Vault може спанити mount-и/симлінки/мережеві теки → dir-mtime reliable у корені, але
НЕ в симлінкованому підбранчі. Тоді пруніг (П7) пропустить зміни там. Потрібен
backstop: періодичний повний скан, або probe кількох точок, або деградація до П8 при
сумніві. Windows dir-mtime (NTFS історично примхливий) — ще не міряно.

### 4.6. ✅ ВИРІШЕНО ВИМІРОМ — журнал (П4-П6) ВИКИДАЄМО
Event-тест (§1, macOS+Android) довів: **`vault.on` сліпий до dot-простору на обох
платформах.** Отже журнал подій НЕ МОЖЕ трекати dots (його головна робота), а для
regulars він надлишковий (§4.3, getFiles+watermark і так покривають). **Висновок:
журнал П4-П6 не будуємо взагалі.** Це СПРОЩУЄ дизайн і **знімає** §4.1 (блокуючу
атомарність journal+watermark) та §4.2 (concurrency-поверхню) — обидва більше не
актуальні.

**Dot-простір — ТІЛЬКИ через скан** (getFiles не бачить, vault.on не спрацьовує,
лишається `adapter.list`-walk): startup + background full-scan (П7/П8), dir-mtime-pruned
де reliable. Dot-зміни рідкісні → background-скан прийнятний (квієсценція I3).

### 4.7. Hot/cold — crash-критичне НЕ в кошиках
`lastSync`/`lastSyncTree`/watermark/`conflictBranch`/`remoteIdentity` — **crash-критичні
й малі** — лишаються в ОКРЕМОМУ малому atomically-written hot-файлі, **не в кошиках**
(hot/cold split — §5 п.2). Per-file SHA-мапа → кошики. Дизайн має це розвести явно.

## 5. РЕКОМЕНДОВАНИЙ порядок (інкрементально, gated виміром)

НЕ будувати всі 8 кроків одразу. Кожен шар — коли попередній виміряно недостатнім:

1. **Зараз, безумовно (дешеве, KISS):** temp+rename для маніфесту;
   прибрати no-op idle save; коалесувати не-crash-save.
2. **Hot/cold split (§4.7):** малий hot-файл (crash-критичне) + велика cold-мапа.
   → міряти.
3. **Bucketing + write-through LRU (П2-3):** якщо cold-мапа janks на 20k → кошики.
   → міряти.
4. ~~Event journal (П4-6)~~ — **ВИКИНУТО** (§4.6): vault.on сліпий до dots, для regulars
   надлишковий. Не будуємо.
5. **dir-mtime pruning (П1,7)** — ОСТАННІМ; потребує Windows-probe + backstop §4.5.
   + **cycle-detection у будь-якому рекурсивному walk** (visited-set / depth-cap) —
   robustness-вимога незалежно від симлінків (§симлінки-аналіз).
6. **Background dot-scan (П8)** — ОСНОВНИЙ шлях для dot-простору (не fallback):
   startup передає керування рано, dot-скан у фоні; на не-dir-mtime ФС — повний.

## 6. Відкриті питання (рішення власника)
- ~~§4.1 / §4.2 / §4.3 (журнал)~~ — **ЗНЯТО**: журнал викинуто (§4.6, event-тест).
- **§4.5** backstop для probe-припущення (multi-FS/симлінки); **Windows dir-mtime вимір**.
- Кількість кошиків (16/32/64) + LRU-розмір — тюнити виміром (dir count домінує вартість walk).
- cycle-detection у walk (§5 п.5) — закласти навіть у поточний `walkConfigDir` (робастність).

## 7. Симлінки / soft-links — небезпеки (аналіз; тест desktop-only)
Симлінк можна створити лише через Node `fs` (desktop; на mobile Obsidian-vault у
пісочниці без симлінків). Небезпеки:
1. **mtime симлінка = час створення ЛІНКА, не змін цілі** → dir-mtime pruning (П7) тихо
   пропустить зміни в симлінкованому підбранчі. → симлінк-теки завжди повнорозсканувати.
2. **Цикл симлінків** (`a/link→a`) → рекурсивний walk **зациклюється** (hang/OOM). Наш
   `walkConfigDir` cycle-detection НЕ має → **MUST-FIX** (visited-set/depth-cap), незалежно
   від pruning.
3. **Інша FS за симлінком** → probe «один FS» (П1) невірний там → backstop (§4.5).
4. **adapter follow vs lstat** — невідомо, чи `adapter.stat` йде за лінком; треба перевірити
   (desktop-тест) якщо будуємо pruning.

> **Наступний крок — НЕ будувати, а завершити ВИМІР:** Windows/Linux dir-scan + dir-mtime
> (macOS/Android є; event-тест — dots невидимі обом ✅). hot/cold split baseline. Числа
> визначать, які з §5-шарів взагалі потрібні. Симлінк-тест — desktop, низький пріоритет.
