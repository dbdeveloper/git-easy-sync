# SPIKE — ліміт кількості записів у `POST /git/trees` (Фаза 3 п.0)

> **Статус: PROBE ПРОГНАНО 2026-08-30 проти живого GitHub.** Блокер холодного старту ЗНЯТО;
> знайдено окремий факт про READ-бік, який стає вимогою до Фази 3 п.1. Probe — ПОСТІЙНИЙ
> regression-тест [`tests/integration/trees-entry-limit.test.ts`](../../tests/integration/trees-entry-limit.test.ts)
> (`pnpm vitest run --config vitest.integration.config.ts tests/integration/trees-entry-limit.test.ts`),
> не одноразовий scratch — не видаляти.

## 1. Питання

Холодний старт (MASTER-PLAN §Фаза 4.0 + NEW-DRAIN §II.15) робить ОДИН батч на весь vault —
одне дерево на ~20k записів. Якщо `POST /git/trees` має ліміт на кількість записів нижчий за
це — холодний старт заблоковано, і розбиття батчів стає обов'язковим у tree-акумуляторі
(count-флаш поруч із наявним size-флашем `MAX_INLINE_BYTES`). До прогону probe ліміт був
**невідомий** — план прямо забороняв вигадувати число.

## 2. Метод

Той самий, що спрацював для compare-300: живий API, наростаючі розміри, числа з прогону.
Записи посилаються на ОДИН попередньо створений blob за `sha` на різних шляхах — тіло запиту
росте повільно відносно кількості записів, тож міряється саме вісь КІЛЬКОСТІ, а не вісь
розміру вмісту. Дерева лишаються dangling навмисно (без коміту й гілки) — чистити нічого,
недосяжні об'єкти прибирає GC GitHub-а.

**Ліміту кількості на нашому стелевому масштабі НЕ існує** (або він вищий за 20k). Час росте
~лінійно з кількістю (×20 записів → ×4.5 часу) — прихованої квадратичності немає. Тіло 2.8 МБ
прийнято без заперечень.

## 4. Висновки

1. ✅ **Блокер холодного старту знято:** одне дерево на 20k записів — робоча операція.
   Count-флаш у tree-акумуляторі НЕ потрібен; єдиним тригером флашу лишається наш власний
   `MAX_INLINE_BYTES` (~1 МБ inline-вмісту, §II.15) — вісь розміру капнута нашою константою,
   вісь кількості перевірена цим probe.
2. ⚠️ **Знахідка READ-боку — стає вимогою до Фази 3 п.1.** Документація GitHub ("Get a tree",
   live-читано 2026-08-30): рекурсивна відповідь обмежена **100 000 записів АБО 7 МБ** —
   і наш замір показує, що на 20k-vault ми вже на **~80% від 7 МБ** (278.5 Б/запис ×
   реальна довжина шляхів може бути гіршою). Тобто стеля `truncated=true` для
   `fullTreeDiffAgainstColdBaseline` лежить не на далеких 100k, а орієнтовно на **~25k
   записів** при probe-профілі шляхів. Compare-300 probe D уже зафіксував, що наш
   `getRepoContent` прапорець `truncated` ІГНОРУЄ — тепер це не «прогалина в прозі», а
   пряма вимога: **Фаза 3 п.1 зобов'язана читати `truncated` і на `true` падати ГОЛОСНО**
   (тихе продовження = мовчазна втрата файлів понад зріз — рівно клас дефекту A).
   Названий запасний хід на майбутнє, якщо стеля стане тісною: некурсивний обхід
   по-каталожно (по одному `GET /git/trees/{sha}` на рівень) — без 7 МБ-стелі; рішення
   потребуватиме власника, зараз НЕ будуємо (YAGNI до першого реального vault >20k).
3. 📌 Профіль probe: sha-референси (~137 Б/запис у запиті). Холодний старт шле inline-вміст
   для текстових файлів — але це вісь РОЗМІРУ, вже капнута флашем §II.15; для бінарних
   (sha-референси на завантажені blob-и) форма запиту точно та, що в probe.
