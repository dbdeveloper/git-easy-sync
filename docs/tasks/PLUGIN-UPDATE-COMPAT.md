# PLUGIN-UPDATE-COMPAT — оновлення плагінів між пристроями з різними версіями Obsidian

> **Статус:** дизайн-документ, НЕ реалізовано. Дві незалежні фази.
>
> **Проблема.** Пристрої, що синхронізують один vault, майже завжди мають РІЗНІ версії
> Obsidian, і це нормальний стан, а не збій: оновлення застосунку опційне, користувач має
> право вимкнути автооновлення і залишитись на старій версії назавжди. Коли з іншого
> пристрою прилітає оновлення плагіна, розраховане на новіший Obsidian, у нас ламаються
> дві різні речі — і лише одна з них справді наша провина.
>
> **Область:**
> - **Фаза 1 (§4)** — чесний авто-релоад. Не вивантажувати працюючий плагін, якщо не можемо
>   гарантовано повернути його назад; не рапортувати успіх, якщо його не було. Мала,
>   самодостатня, ні від чого не залежить.
> - **Фаза 2 (§5)** — `heldPluginUpdates`: утримання несумісного оновлення, поки Obsidian не
>   доросте. Стан живе В МЕТАФАЙЛІ поруч із per-file baseline — див.
>   [`SYNC2-METAFILE-REFACTOR.md`](./SYNC2-METAFILE-REFACTOR.md); цей документ описує
>   ПОВЕДІНКУ, той — сховище.
>
> **Поза областю:** загальний механізм відкладеного застосування для будь-яких файлів
> (§8.1 — розглянуто й відхилено), поведінка diff2, конфлікти.

## 2. Перевірені факти про Obsidian (первинне джерело)

Ця секція — фундамент решти документа. Дві поширені й правдоподібні тези виявилися
хибними; обидві були перевірені не за пам'яттю, а грепом по бандлу застосунку.

Бандл — це **версійований asar у `~/Library/Application Support/obsidian/`**
(`obsidian-<version>.asar`), а НЕ `/Applications/Obsidian.app/Contents/Resources/app.asar`
(той лише завантажувач). Старі версії доступні як релізні асети
`obsidianmd/obsidian-releases` (`obsidian-1.12.7.asar.gz`, ~8 МБ). Файл — один довжелезний
рядок, тому `grep -c` рахує рядки, а не входження; тіла методів дістаються так:

```bash
grep -a -o -E "prototype\.enablePlugin=function.{400}" obsidian-1.13.4.asar
```

### 2.1 `minAppVersion` НЕ перевіряється при завантаженні плагіна

Рядок `minAppVersion` трапляється в усьому бандлі **рівно двічі**: (a) у version-picker
завантажувача community-плагінів, який при несумісності тягне `versions.json` плагіна і
відкочується до найсвіжішого сумісного релізу; (b) як захардкоджений літерал при створенні
манифесту **теми**. Оскільки входжень лише два, жоден інший шлях (включно з `isDeprecated`)
до цього поля дотягнутися не може.

Реальні гейти `enablePlugin`, по порядку: `isDeprecated(manifest)`; іменний чорний список
(`cmdr` ≤0.5.4, `obsidian-image-toolkit` ≤1.4.3, `settings-search`, `better-pdf-plugin`
1.4.0); `!isDesktopApp && manifest.isDesktopOnly`. Порівняння версій немає.

Наслідок: **підняття `minAppVersion` у `manifest.json` невідтворюване як відмова
завантаження** — ні на 1.12.7, ні на 1.13.4. Спроба відтворити інцидент цим шляхом
приречена.

Наслідок для дизайну: наша перевірка `minAppVersion` — **евристика, а не дзеркало правила
Obsidian** (§5.1).

### 2.2 Справжня причина падіння Templater

Templater 2.24.3 містить оголошення класів на верхньому рівні модуля:

```js
var an = class extends ft.SettingPage      { … }
var Ji = class extends Zr.ConfirmationModal { … }
```

`SettingPage` у бандлі Obsidian 1.12.7 — **нуль входжень**; у 1.13.4 присутній.
Звірка по типах з npm (опубліковані версії розріджені; 1.12.3 — остання перед 1.13.0):

| символ | 1.12.3 | 1.13.0 |
|---|---|---|
| `AbstractInputSuggest` | є | є |
| `SettingGroup` | є | є |
| `SettingPage` | **немає** | є |
| `ConfirmationModal` | **немає** | є |

`class extends undefined` кидає `TypeError` **при обчисленні модуля, до `onload()`**. Жоден
обробник помилок усередині плагіна цього спіймати не може.

### 2.3 `enablePlugin` повертає `false`, а не кидає

```js
try { this.loadingPluginId = e; await this.loadPlugin(e, t) }
catch (i) {
  this.loadingPluginId = null;
  new Notice(msgFailedToLoadPlugin({plugin: e}));
  console.error("Plugin failure: " + e, i);
  return false;                       // ← НЕ throw
}
```

Тому `reloadPluginById(...).then(() => log("done"))` дає **гарантований хибний зелений**.
Ідентично в 1.12.7 і 1.13.4.

### 2.4 `reloadPlugin` не існує

Нуль входжень і в 1.12.7, і в 1.13.4. Наш feature-detect у `reloadPluginById`
(`src/main.ts:152-168`) завжди провалюється в гілку `disablePlugin` + `enablePlugin` —
на десктопі теж. Окремої «десктопної» поведінки немає. Не використовувати й не перевіряти
існування `reloadPlugin`, одразу завжди використовувати `disablePlugin` + `enablePlugin`.

### 2.5 Стан увімкненості губимо НЕ ми

Персистять лише варіанти `...AndSave`:

```js
disablePluginAndSave(id) { enabledPlugins.delete(id); requestSaveConfig(); await disablePlugin(id,true) }
enablePluginAndSave(id)  { if (await enablePlugin(id,true)) { enabledPlugins.add(id); requestSaveConfig() } }
```

Ми викликаємо голі `disablePlugin`/`enablePlugin` — вони не чіпають ні `enabledPlugins`, ні
файл конфігу (`didChange()` — це дебаунснутий `trigger("changed")`, не запис).

**Хто саме переписав `community-plugins.json` в інциденті — не встановлено.** Записати міг
лише один із варіантів `...AndSave`, а їх викликає UI налаштувань, не ми. Точна послідовність
кліків нез'ясована й тут не домислюється.

**Тому «відновлення втраченого стану увімкненості» в цьому документі НЕМАЄ.** Нема чого
відновлювати: наш код цього стану не торкається.

### 2.6 На холодному старті невдале завантаження стан НЕ руйнує

Стартовий шлях менеджера плагінів:

```js
this.enabledPlugins = new Set(await readConfigJson("community-plugins"));
await this.loadManifests();
… цикл по плагінах …
catch (h) { console.error(h); }     // залогував і пішов далі
… this.didChange();                 // подія, НЕ запис
```

Ніде в цьому шляху немає ні `enabledPlugins.delete`, ні `requestSaveConfig` — персистять
лише варіанти `...AndSave` (§2.5). Отже якщо на диску лежить несумісна версія, Obsidian на
кожному старті намагатиметься її завантажити, показуватиме «Failed to load plugin» і йтиме
далі, **не втрачаючи запису про увімкненість**. Коли застосунок дожене потрібну версію,
плагін підніметься сам.

**Це те, що робить несумісні файли на диску інертними, а не «міною»** (§3): найгірший
наслідок — повторюване повідомлення про помилку, і стан самолікується. Саме тому Фаза 1
може дозволити собі просто НЕ чіпати плагін: вона нічого не «сподівається» від
завантажувача, вона лише не руйнує те, що вже працює в пам'яті.

### 2.7 Уся ця поверхня — недокументована

`unloadPlugin` = 0 входжень у публічних типах; `app.plugins` = 0 входжень. Наш власний
коментар (`src/main.ts:118-120`) це визнає. Все з §2.3–§2.6 — **спостережена поведінка двох
версій, а не контракт**. Звідси вимога §4.2: не спиратися на жоден одиничний сигнал.

## 4. Фаза 1 — чесний авто-релоад

Мала, самодостатня, робиться незалежно від рішення щодо Фази 2. Закриває клас «тиха втрата
із зеленим рапортом» **для будь-якої причини відмови**, включно з тими, які евристика
Фази 2 не спіймає ніколи.

### 4.1 Пропуск релоаду за евристикою

**Спершу — як файли плагіна взагалі потрапляють на диск** (без цього наступна вимога
читається неправильно). Усередині `pullIfNeeded`, для кожного файла з `compare(base…head)`,
що пройшов `checkSyncable`:

1. **Локальний файл не змінений** відносно baseline → віддалена версія застосовується прямо.
2. **Локальний файл теж змінений** → Case 3 (`src/sync2/sync2-manager.ts:2066`):
   `attemptAutoMerge`, а для файлів у папці плагіна попередньо збирається `pluginResolve`
   (`readPluginResolveContext`, `:2368`) — версії з манифестів обох сторін плюс mtime бандла.
   Сторона «ours» береться з `pullBundleSnapshots`, знятого **до** циклу (`:1277`), щоб уже
   застосований сусідній файл не спотворив картину. `.js` і `manifest.json` ніколи не
   мержаться текстово (`src/sync2/plugin-js.ts` — 3-way по мініфікованому бандлу дає
   нежиттєздатний гібрид), і **конфлікт для файлів папки плагіна не реєструється ніколи**
   (§28): резолвер завжди обирає сторону.
   - `atomic / ours` → **нічого не пишеться**; snapshot лишається на старому SHA, і
     наступний push відправить локальну версію в репо;
   - `atomic / theirs` → `writeBinaryRemote` → перезапис.
3. **Запис** (`writeBinaryRemote`, `:2234`): наш власний плагін іде marker-протоколом
   self-update, решта — через `atomicWriteFile` (sync-tmp → swap → backup). І лише **після**
   успішного запису викликається `maybeMarkPluginAffected(path)` (`:2260`).
4. Накопичений `affectedPluginIds` наприкінці drain іде в `handlePluginsAffectedReload`.

**Тобто до вирішення «хто виграв» поверх локального `manifest.json` нічого не лягає**, і
присутність плагіна в списку релоаду вже означає «щось на диску змінилося» — окремо це
перевіряти не треба.

Сама перевірка. У `handlePluginsAffectedReload` (`src/main.ts:1951`), поруч із наявною
перевіркою «плагін увімкнений», додати другу: прочитати `manifest.json` плагіна **з диска на
момент релоаду** і

```ts
if (!requireApiVersion(manifest.minAppVersion)) → релоад ПРОПУСТИТИ
```

- ⚠️ Читати саме **з диска, а не з `app.plugins.manifests[id]`** — той кеш заповнюється при
  старті Obsidian, і `enablePlugin` бере саме його (§2.1). Це логічний висновок, не вимір —
  перевірити на живому запуску.
- **Не «щойно записаний», а «той, що зараз на диску».** Манифест міг цього drain'у взагалі
  не писатися (змінився лише `main.js`; або для манифесту переміг «ours»), і це не має
  значення: диск завжди тримає переможця, тобто рівно ту версію, яку Obsidian прочитає при
  завантаженні. Саме її і треба перевіряти.
- `requireApiVersion` (`obsidian.d.ts:3526`) і `apiVersion` (`:378`) — публічний API. Своє
  порівняння версій НЕ писати: обрізання до `major.minor` дає хибний пропуск (плагін просить
  `1.13.4`, у нас `1.13.0` → обидва згортаються в «1.13» → не спрацює).
- `manifest.json` відсутній, битий або без `minAppVersion` → **не релоадити** і залишити
  запис у лозі. Ціна помилкового пропуску — користувач перезапустить Obsidian; ціна
  помилкового релоаду — інцидент §1.
- **`isDesktopOnly` перевіряється нарівні з `minAppVersion`** — на мобільному
  `!isDesktopApp && manifest.isDesktopOnly` теж означає «релоад пропустити». Це не
  перестраховка: конкретний випадок — плагін БУВ увімкнений і працює, а нова версія
  **додала** прапорець. Він у `enabledPlugins`, тож фільтр «пропускати вимкнені» не спрацює,
  і релоад уб'є працюючий плагін. Розбір — §5.1.

> **Не плутати з Фазою 2 — це різні механізми в різні моменти.**
>
> | | Фаза 1 (§4.1) | Фаза 2 (§5) |
> |---|---|---|
> | коли | наприкінці drain | під час drain |
> | стан диска | файли **вже записані** | ще **нічого не записано** |
> | джерело манифесту | **диск** (переможець §28) | **репо** (`safeFetchContents`) |
> | дія | пропустити релоад | не писати файли взагалі |
> | результат для користувача | стара версія працює до рестарту | стара версія працює **і далі** |
>
> **Якщо Фазу 2 буде побудовано, гейт §4.1 майже перестане спрацьовувати:** несумісне
> оновлення просто не дійде до диска, плагін не потрапить у список зачеплених, і релоаду не
> буде. Це нормально — §4.1 лишається другою лінією для випадків, які Фаза 2 не морозить
> (у зміні немає `manifest.json`, тобто версія не мінялася). А от **§4.2 і §4.3 потрібні
> завжди** й від Фази 2 не залежать: вони ловлять відмову з БУДЬ-ЯКОЇ причини, а не лише
> через версію.

### 4.2 Перевірка постумови — подвійна

`reloadPluginById` (`src/main.ts:152-168`) відкидає значення, які повертають `reloadPlugin`
і `enablePlugin`. Перестати їх відкидати. Але жоден одиничний сигнал не надійний (§2.7):

```
відмова  =  (результат === false)  АБО  (pm.plugins?.[id] відсутній)
```

- **boolean** — правильний сигнал сьогодні (§2.3), але це внутрішня деталь, завтра може
  стати `void`;
- **`pm.plugins[id]`** — має власну дірку: `loadPlugin` робить `this.plugins[e] = n`
  **до** `await n.load()`, тож при падінні саме в `onload()` запис лишається заповненим.

Хибних тривог кон'юнкція не дає: якщо плагін справді завантажився, обидві умови хибні.

⚠️ **НЕ перевіряти `enabledPlugins.has(id)`** — голі `disablePlugin`/`enablePlugin` цю
множину не чіпають (§2.5), перевірка завжди читатиме `true`.

### 4.3 Чесне повідомлення

При виявленій відмові: `logger.error`, а в Notice — те, що користувач може зробити
(«Templater не вдалося перезавантажити — перезапустіть Obsidian»). Поточний Notice
«N plugins updated» показується **до** результату релоаду — перенести або уточнити.

### 4.4 Наш власний плагін

**Чому bootloader не місце для гейта — «курка і яйце».** Bootloader виконується лише тоді,
коли наш код успішно завантажився, тобто працююча версія **за визначенням сумісна** з цим
Obsidian. Питати там «чи я сумісний?» безглуздо: відповідь завжди «так». А поки плагін НЕ
запущено, ми взагалі нічого не знаємо про стан файлів у папці — жодного нашого коду не
виконується.

Єдине, що bootloader МІГ БИ перевіряти, — сумісність **відкладених** файлів, які він
збирається застосувати. Але відкладена пара `sync-tmp` + marker виникає лише після краху
drain'у, а drain застейджив би несумісну версію тільки за відсутності гейта §4.1 / Фази 2.
Тобто це третя лінія оборони для крашового вікна всередині події, якої не має бути. **Не
будуємо.**

**Друге правдоподібне заперечення — що працюючий екземпляр не може вимкнути сам себе, тож
проблеми немає взагалі. Може, і робить це сьогодні.** `applySelfUpdateOwnFile`
(`src/sync2/sync2-manager.ts`, кроки 3-4) виконує підміну **прямо під час drain**, не при
наступному старті, і додає власний id у `affectedPluginIds`:

```js
await adapter.rename(path, bakPath);      // Steps 3-4: atomic swap
await adapter.rename(tmpPath, path);
…
this.affectedPluginIds.add(this.selfPluginId);
```

`handlePluginsAffectedReload` це підтверджує коментарем: *«Self is treated the same as any
other plugin: the new main.js is already on disk (the marker swap completed), so
disable+enable loads the new code»*, а `setTimeout(500)` існує саме щоб *«the drain stack
frame unwinds before a self-reload tears this instance down»*. Тобто ми штатно робимо
`disablePlugin(self)`, і якщо новий код несумісний — падаємо.

**Наслідок приємний: окремого механізму не потрібно.** Самооновлення йде ТИМ САМИМ шляхом
релоаду, тож §4.1 і §4.2 покривають його автоматично. Bootloader
(`src/sync2/plugin-update-bootloader.ts`, виклик із `src/main.ts:309`) — вужчий випадок:
він застосовує ВІДКЛАДЕНУ підміну після обірваного drain'у, тобто лише крашове вікно.

**Але наслідок відмови для нас важчий, ніж для чужого плагіна.** Пропуск релоаду (§4.1)
залишає нові файли на диску; при наступному старті Obsidian спробує їх завантажити і, якщо
ще зарано, покаже помилку й піде далі (§2.6). Для стороннього плагіна це прийнятно. Для нас
це означає, що **синхронізація тихо мертва** до оновлення застосунку.

Тому справжня відповідь — **Фаза 2, що морозить і нашу папку теж** (§7): несумісна версія
взагалі не лягає на диск, підміни немає, пари sync-tmp+marker немає, bootloader'у нема чого
застосовувати. Стара версія працює далі, доки Obsidian не дожене.

**Залишковий ризик у DRAIN-сценарії — ПРИЙНЯТИЙ (рішення власника, 2026-08-02).** Якщо
несумісне самооновлення все ж ляже і ми впадемо, жоден наш механізм не спрацює: нічого нашого
не виконується — ні гейт, ні заморозка, ні лог. Але **ми не єдиний механізм в Obsidian, і це
не катастрофа.** Наш плагін ставиться через BRAT / Community Plugins, а обидва звіряються з
`versions.json` і беруть найсвіжішу СУМІСНУ версію (§2.1 — той самий version-picker). Файл у
нас є, `version-bump.mjs` дописує в нього рядок на кожному релізі. Тож користувач, помітивши,
що синхронізація стоїть, перевстановлює плагін звичайним шляхом і отримує робочу версію.

Сьогодні все одно латентно — наш `minAppVersion` = 1.7.7 і під нашим контролем. Правило
лишається пунктом чеклиста, а не блокером: **перед підняттям нашого `minAppVersion`
перевірити, що або Фаза 2 покриває нашу папку, або гейт §4.1 на місці** — щоб не змушувати
користувачів до зайвого клацання.

⚠️ **Але в BOOTSTRAP-сценарії ця оцінка не діє: там «один клік» не тримається.** Розбір —
§5.9.1. Прийняття ризику вище стосується випадку, коли несумісна версія прилітає в звичайному
drain на працюючому пристрої; сценарій першого налаштування влаштований інакше.

## 5. Фаза 2 — `heldPluginUpdates`

**Мета:** поки Obsidian на цьому пристрої не доріс до вимог нової версії плагіна —
несумісні файли на диск **не потрапляють узагалі**, і стара робоча версія продовжує
працювати, зокрема **через перезапуски**. Коли застосунок доріс — оновлення застосовується
автоматично.

Це та частина, яка потрібна користувачам із назавжди замороженим Obsidian: без неї плагін
працює лише до першого перезапуску, а далі зламаний назавжди.

### 5.1 Умова заморозки — евристика, і це треба знати

`minAppVersion` — не вимога Obsidian (§2.1), а **заява автора плагіна**: «моєму коду
потрібен щонайменше такий застосунок». Корелює добре — Templater підняв поле до `1.13.0`
рівно тому, що взяв `SettingPage`, який з'явився в 1.13.0.

Режими промаху:
- **автор забув підняти поле** → морозити не станемо, плагін впаде. Ловиться Фазою 1
  (чесний звіт замість «done»);
- **автор перестрахувався** → заморозимо без потреби. Шкоди нема: стара версія працює,
  оновлення приїде, коли застосунок дожене.

Якщо Obsidian колись почне виконувати `minAppVersion` сам — евристика стане точним
дзеркалом його правила, тобто **надійнішою**. Цей сценарій для дизайну нейтральний.

#### `isDesktopOnly` — умовою заморозки НЕ є (рішення 2026-08-02)

Desktop-only плагіни неминуче потрапляють у репо з десктопа. Спокуса морозити їх на
мобільному є — телефон би не тягнув бандли, які там не запрацюють. **Не морозимо.**

Що тут інакше, ніж із `minAppVersion`. Це **справжнє правило Obsidian, а не наша евристика**:
`!isDesktopApp && manifest.isDesktopOnly → return false` в `enablePlugin` (§2.1, перевірено
в бандлі). На мобільному такий плагін просто ніколи не вмикається — мовчки, без падіння.
Тобто його файли на телефоні **інертні**: займають місце й нічого не роблять.

Чому заморозка тут — погана угода:

| | `minAppVersion` | `isDesktopOnly` |
|---|---|---|
| тривалість | тимчасова | фактично постійна |
| що знімає | **локальна** подія: Obsidian оновився | **віддалена**: автор прибрав прапорець |
| як дізнаємось | `requireApiVersion()` офлайн на кожному onload | ніяк: заморожений шлях відфільтрований з кожного `compare` |

Друге — замкнене коло: щоб дізнатися, що плагін став мобільним, треба прочитати новий
манифест; щоб прочитати — треба розморозитися. Розірвати його можна лише періодичним
опитуванням репозиторію по заморожених шляхах — цілим новим механізмом, який для
`minAppVersion` не потрібен узагалі.

**Ціна відмови від заморозки — тільки місце на диску й трафік.** Взамін: жодного нового
механізму, жодного одностороннього капкана, і плагін лишається **актуальним**. Коли автор
колись прибере прапорець, файли вже на місці й свіжі — користувач просто вмикає плагін
руками. За заморозки він на телефоні не з'явився б ніколи.

**Але одна перевірка в §4.1 таки потрібна**, і не «про всяк випадок». Випадок конкретний:
плагін БУВ увімкнений на мобільному й працює, а в новій версії автор **додав**
`isDesktopOnly`. Тоді він у `enabledPlugins`, тож наявний фільтр «пропускати вимкнені» його
не врятує: релоад зробить `disablePlugin` успішно, а `enablePlugin` відмовить за прапорцем —
і працюючий плагін помре посеред сесії. Рівно шкода Фази 1. Тому §4.1 перевіряє
`isDesktopOnly` вхідного манифесту нарівні з `minAppVersion` і пропускає релоад.

Для протилежного випадку — плагін desktop-only від початку — робити нічого не треба: Obsidian
його на мобільному ніколи не вмикав, у `enabledPlugins` його немає, і
`handlePluginsAffectedReload` його й так пропускає.

### 5.2 Момент рішення й одиниця заморозки

Одиниця — **папка плагіна цілком**, не окремий файл.

- Рішення ухвалюється на **згрупованій по плагіну** порції вхідних змін, ДО запису
  будь-якого файла: `main.js` і `manifest.json` можуть приїхати різними батчами, а
  вирішувати треба до запису `main.js`.
- `minAppVersion` береться з **вхідного** `manifest.json`. Якщо `manifest.json` у зміні
  немає — версія не мінялася, морозити не треба.
- **`data.json` теж морозиться.** Він в алловлисті й синхронізується (є у віддаленому
  дереві). Новий конфіг нової схеми під старим `main.js` — другий спосіб зламати робочий
  плагін. Відрізняється від bootloader'а, який `data.json` виключає свідомо: свій ми з
  remote не тягнемо взагалі.

**Взаємодія з §28.** Заморозка спрацьовує на рівні `checkSyncable`, тобто **раніше**, ніж
атомарний резолвер §28 узагалі побачить файл (§4.1, крок 2). Конфлікту між двома механізмами
немає — вони на різних поверхах, — але саме тому заморозка мусить бути на рівні папки: якщо
відфільтрувати частину файлів бандла, решта дійде до §28, і той обиратиме переможця,
не знаючи про утримані файли.

Готовий будівельний блок: вхідний манифест дістається `safeFetchContents(manifestPath,
headRef)` — той самий виклик, яким §28 уже читає віддалену версію в
`readPluginResolveContext` (`src/sync2/sync2-manager.ts:2368`). Нового мережевого шляху
винаходити не треба.

⚠️ **Другий шлях запису — `bootstrapFromRemote`.** Перше в житті завантаження і відновлення з
remote йдуть **не через `pullIfNeeded`** і обходять як §28, так і гейт Фази 2. Механіка там
відрізняється в трьох місцях — окремий розділ **§5.9**.

### 5.3 Заморожений шлях невидимий В ОБИДВА БОКИ

`isSyncable` (`src/sync2/change-detector.ts:22`) — **єдиний симетричний предикат**: push
питає його через `findChanges` внутрішньо, pull — через `checkSyncable`
(`src/sync2/change-detector.ts:467`) у `pullIfNeeded`. Тому заморожений шлях достатньо
зробити несинхронізовним — існуючим і протестованим кодом.

Симетрія тут не побічний ефект, а **вимога**: якщо користувач вручну поставить сумісну
стару версію плагіна, вона не поїде в репо і не відкотить оновлення на здорових пристроях.

### 5.4 ⚠️ Baseline МУСИТЬ зберігатися в записі — інакше даунгрейд

Не самоочевидний дефект, знайдений при розборі. Pass 2 детектора
(`src/sync2/change-detector.ts:353-363`):

```ts
//   - seenIgnored: file exists on disk but is now ignored → silent
//     cleanup (gitignore is a two-way mute).
if (seenIgnored.has(path)) {
  this.store.remove(path);        // ← baseline ВИДАЛЯЄТЬСЯ
  continue;
}
```

Послідовність без збереження baseline:

1. морозимо → перший же drain **стирає baseline** усіх файлів папки;
2. минають місяці, Obsidian оновлюється, знімаємо заморозку;
3. шляхи знову синхронізовні, але baseline немає → Pass 1 бачить `store.get(path) === undefined`
   → файли виглядають як нові/змінені;
4. → **push старої локальної версії в репо** і даунгрейд на всіх пристроях.

Тому в записі зберігається baseline кожного файла папки — за формою снапшота
`{path, remoteSha, mtime, size}` (`src/sync2/snapshot-store.ts:149`), — і **першою** дією
розморозки повертається на місце.

### 5.5 Форма запису

Живе в метафайлі поруч із per-file baseline, ключ `heldPluginUpdates`. **Не окремим
файлом:** запис і baseline мусять змінюватися узгоджено (стерли baseline → мусимо мати
копію; відновили → мусимо зняти запис). Два файли дали б вікно неузгодженості при збої;
один — один атомарний запис і один шлях відновлення.

```
heldPluginUpdates: {
  "<plugin-id>": {
    minAppVersion: string,        // умова зняття
    heldVersion:   string,        // тільки для лог-рядка; може застаріти — див. §7
    frozenBeforeCommit: string,   // база для compare при розморозці (§5.6)
    baselines: Array<{ path, remoteSha, mtime, size }>   // §5.4
  }
}
```

⚠️ **`frozenBeforeCommit` — це `expectedHead`, а НЕ `currentHead`.** Рішення про заморозку
ухвалюється всередині `pullIfNeeded` під час обходу `cmp.files`, тобто коміт з оновленням
плагіна лежить УСЕРЕДИНІ діапазону `compare(expectedHead … currentHead)`. Якщо записати
`currentHead` («коміт на момент заморозки» — саме так це прочитається інтуїтивно), то при
розморозці `compare(currentHead … newHead)` матиме потрібний коміт **позаду бази** й не
побачить його. Це рівно та відмова, від якої існує §5.6, лише поверхом нижче. Тому поле
названо `frozenBeforeCommit` і присвоюється явно:

```ts
entry.frozenBeforeCommit = expectedHead;   // база ДО pull-у, що спричинив заморозку
```

### 5.6 Розморозка — транзакція, запис знімається ОСТАННІМ

На кожному onload плагіна пройти `heldPluginUpdates`; для кожного запису, де
`requireApiVersion(entry.minAppVersion) === true`:

1. **відновити baseline** у снапшоті (§5.4);
2. **явно підтягнути зміни** з репо (нижче) і застосувати;
3. **лише тепер зняти запис** із `heldPluginUpdates`;
4. релоад плагіна через шлях Фази 1 (з його перевіркою постумови).

**Порядок не косметичний — він робить збій безпечним за побудовою.** Заморожений шлях
несинхронізовний саме тому, що запис існує. Поки запис на місці, відновлені baseline нікому
не шкодять: push їх не побачить (шлях заморожений), а найближчий drain просто зітре їх
знову тим самим `store.remove` (§5.4) — і наступний onload повторить спробу з чистого
аркуша. Якщо ж зняти запис ДО того, як довантаження справді лягло на диск, і крок 2 впаде
(мережа, 404, перерваний drain), ми залишимося з розмороженим шляхом, baseline від старої
версії та іншим вмістом на диску — і наступний drain відправить цей вміст у репо. Той самий
даунгрейд, лише в новій обгортці.

**Чому крок 2 не станеться сам собою:**

`pullIfNeeded` — **diff-орієнтований, не state-орієнтований** (`src/sync2/sync2-manager.ts:1172`):

```ts
cmp = await this.client.compare({ base: expectedHead, head: currentHead });
for (const f of cmp.files) { if (await this.detector.checkSyncable(f.filename)) … }
```

Кандидати — дельта між двома комітами; `checkSyncable` лише **відсіює** з неї. Наприкінці
успішного pull вказівник просувається (`sync2-manager.ts:1461`):

```ts
this.store.setLastSync(currentHead, headCommit.tree.sha);
```

Коміт, у якому плагін оновився, лишається **позаду нової бази**. Знімай фільтр чи ні — у
наступній дельті цього файлу немає. Аналогія з `git` тут ламається: `git status` порівнює
**стани** (робоча тека проти індексу), тому un-ignore спливає сам; наш pull застосовує
**різницю** між комітами.

> Збиває з пантелику `tree?recursive=1` у лозі drain'у: він викликається лише щоб
> просумувати розміри й вирішити, чи показувати прогрес-нотіс (`isHeavyPull`). Виявленням
> змін не займається. Повний обхід дерева живе в `bootstrapFromRemote` — шлях першої
> синхронізації та відновлення, не звичайного drain.

Тому: `compare(entry.frozenBeforeCommit … head)`, обмежене шляхами цього плагіна, і результат у
штатний шлях застосування. **Чому compare, а не «забрати файли з head»:** compare повідомляє
ще й ВИД зміни, тож випадки «плагін за час заморозки видалили з репо» і «оновився кілька
разів» обробляються коректно, а не як «поточний вміст».

**Фолбек.** За місяці заморозки база може стати недосяжною (force-push, GC) — `compare`
віддасть 404. Рушій уже вміє це ловити для глобальної бази (`sync2-manager.ts` ~1186); тут
фолбек — забрати шляхи з `head` як є.

Далі — штатний релоад плагіна через шлях Фази 1 (з його перевіркою постумови).

### 5.7 Локальні зміни файлів плагіна під час заморозки

Плагін можна оновити локально повз нас — через BRAT або Community Plugins. Окремої перевірки
диска для цього **не потрібно**: заморожений шлях несинхронізовний в обидва боки (§5.3), тож
будь-яка локальна зміна просто лишається локальною. Це не побічний ефект, а бажана
поведінка — інакше локально встановлена сумісна (тобто СТАРІША) версія поїхала б у репо й
відкотила оновлення на здорових пристроях.

Ручна установка з Community Plugins — **підтриманий вихід, а не обхідний маневр**: Obsidian
візьме `versions.json` плагіна і поставить найсвіжішу сумісну версію (той самий механізм, що
й наш `versions.json` + `version-bump.mjs`). Нашкодити вона не може.

Що з цього випливає:

- **Утримане оновлення від локальної зміни не застаріває.** Локально можна поставити лише
  сумісну (старішу) версію — та, що в репо, лишається найновішою і при розморозці
  правильною до застосування.
- **Розморозка перезапише локальну ручну установку** версією з репо. Це коректно (репо —
  джерело правди), але користувач може здивуватися. Фіксуємо як відому поведінку.
- **Локальне видалення плагіна під час заморозки не пошириться**, а при розморозці плагін
  повернеться з репо. Так само коректно і так само може здивувати.
- Плагіни, які НЕ заморожені, поводяться як завжди: локальне оновлення виявляється і
  пушиться. Нічого не змінюється.

власника: користувач комфортно працює з локальними плагінами, хай і старіших версій, і
вільно оновлює їх через BRAT/Community Plugins — просто наш механізм для цих плагінів
недоступний, і це нормальний стан, а не аварія.

Наслідок, який фіксуємо явно: **при відновленні порожнього vault-а на старому Obsidian
заморожений плагін не з'явиться взагалі** — базових файлів немає, папка не створюється, і
користувач не дізнається, що плагін мав бути. Лікується ручною установкою, коли він це
помітить.

Що все ж варто робити — **запис у лог** (це не UI): рядок при заморозці та при знятті, з
id плагіна, утримуваною версією і потрібним `minAppVersion`. Сьогоднішній розбір інциденту
цілком тримався на лозі; без сліду про заморозку майбутнє розслідування «чому на цьому
пристрої стара версія» починатиметься з нуля.

### 5.9 Заморозка на етапі bootstrap

`bootstrapFromRemote` (`src/sync2/sync2-manager.ts:1701`, виклик із `:1675` при
`lastSyncCommitSha === null`) — це і перше в житті завантаження в порожній vault, і
відновлення з remote. Він обходить повне дерево і пише напряму через `writeRemoteText` /
`adapter.writeBinary` (внутрішньо — `adoptionPullAndRecord`, `:1933`), тобто **повз
`pullIfNeeded` і повз гейт §5.2**.

Стосується лише випадку, коли синхронізація `<configDir>/` **увімкнена**: при вимкненому
`syncConfigDir` уся піддиректорія й так симетрично закрита (`isSyncable`), і плагінів у
bootstrap просто немає.

**Процедура.** Обхід дерева групується по папках плагінів. Для кожної папки **спершу**
читається `manifest.json` (він в алловлисті й буде завантажений однаково — питання лише в
порядку), і якщо `!requireApiVersion(minAppVersion)`:

- створюється запис у `heldPluginUpdates`;
- **уся папка плагіна не завантажується.** Порожню директорію теж не створювати: папка без
  `manifest.json` для Obsidian не існує, тож порожня тека нічого не дає, лише сміття.

Порядок тут значущий: рішення має передувати завантаженню `main.js` — саме він великий, і
саме заради нього все затіяно.

**Три відмінності від шляху drain'у** — їх легко проґавити, якщо реалізовувати «за аналогією»:

1. **`baselines: []` — зберігати нічого.** Уся проблема §5.4 (заморозка стирає baseline,
   тому їх треба врятувати) у bootstrap не виникає: baseline ще не існує. Порожній масив тут
   не недогляд, а правильне значення.
2. **`frozenBeforeCommit` немає.** База відсутня за визначенням — `lastSyncCommitSha === null`,
   тому й bootstrap. Записувати `null`; при розморозці `compare` неможливий, і працює
   **той самий фолбек, що вже описаний у §5.6** для недосяжної бази — забрати шляхи з `head`.
   Нового коду це не потребує.
3. **Манифест береться з дерева bootstrap'у**, а не через `safeFetchContents(path, headRef)`:
   повне дерево вже на руках, окремий запит зайвий.

**Чому не можна просто пропустити bootstrap**, хоча захищати в порожньому vault-і нічого:
bootstrap записав би несумісну версію **і її SHA в baseline**. Далі користувач, не побачивши
плагіна в списку, ставить сумісну старішу версію руками — диск розходиться з baseline,
детектор бачить локальну зміну і **пушить даунгрейд у репо**. Той самий механізм, що в §5.4,
лише зайшов з іншого боку.

**Що бачить користувач:** плагіна на цьому пристрої просто немає. Це рівно той наслідок, який
зафіксовано в §5.8 як прийнята ціна рішення «без UI».

#### 5.9.1 Наш ВЛАСНИЙ плагін у bootstrap — найгостріший випадок

> Нижче спершу розібрано, що станеться **БЕЗ** гейта — це обґрунтування, а не прогноз.
> Результат **З** гейтом — наприкінці підрозділу, і він тривіальний.

Порядок створення vault-а з репо «з нуля» жорстко фіксований, і з нього випливає неочевидне:

1. на пристрої створюється порожній vault;
2. ставиться BRAT, і з нього — наш плагін. **BRAT бере сумісну версію** через `versions.json`;
3. у налаштуваннях прописуються token / owner / repo / branch;
4. і **лише тепер** робиться перший sync.

Тобто на момент bootstrap наш плагін **уже встановлений, запущений і за визначенням
сумісний** — інакше кроку 3 просто не було б кому виконати. А в репо може лежати НОВІША,
несумісна з цим Obsidian версія.

⚠️ **`bootstrapFromRemote` спецобробки нашої папки НЕ має.** `isOwnPluginRecoverableFile`
викликається лише з `writeBinaryRemote` (`src/sync2/sync2-manager.ts:2248`) і `:2909`;
bootstrap пише напряму. Тож без гейта відбудеться таке:

1. BRAT поставив сумісну `v2` — працює;
2. перший sync → bootstrap перезаписує `<self>/main.js` версією `v3` з репо **простим
   записом** (повз marker-протокол, без релоаду) і кладе SHA `v3` у baseline;
3. одразу нічого не ламається — `v2` уже в пам'яті;
4. наступний старт Obsidian → `v3` не вантажиться → **синхронізація мертва**;
5. користувач перевстановлює з BRAT → на диску знову `v2`, але baseline каже `v3` →
   детектор бачить локальну зміну → наступний sync **пушить `v2` у репо**, відкочуючи наш
   плагін на ВСІХ пристроях. Або pull перетирає `v2` знову — залежно від того, що спрацює
   першим.

**Тобто тут «один клік» не тримається**: перевстановлення або перетирається, або
відкочує репо. Прийняття залишкового ризику з §4.4 стосувалося drain-сценарію на працюючому
пристрої й на цей випадок НЕ поширюється.

**А з гейтом усе стає тривіальним** — власне, заради цього абзацу й написано попередній:

1. BRAT поставив сумісну `v2` — працює;
2. перший sync → bootstrap читає манифест `<self>/` з дерева, бачить
   `!requireApiVersion(v3.minAppVersion)` → **папку не чіпає взагалі**, створює запис у
   `heldPluginUpdates`;
3. на диску лишається `v2`, baseline на неї не вказує (при bootstrap baseline узагалі
   порожній, §5.9) → пушити нема чого, перетирати нема чим;
4. запис висить, доки користувач не оновить Obsidian; тоді розморозка (§5.6) підтягує `v3`
   і перезавантажує плагін.

Ручне оновлення через BRAT / Community Plugins лишається доступним увесь цей час: заморозка
не заважає ставити, вона лише не пускає локальну версію в репо (§5.7).

⚠️ **Одна деталь реалізації, специфічна саме для `<self>/`:** на кроці 4 розморозки запис
файлів має йти **marker-протоколом** (`applySelfUpdateOwnFile` через `writeBinaryRemote`), а
не простим записом. Ми перезаписуємо код, що виконується; крах посеред запису без marker'а
лишить побитий `main.js`, який bootloader не зможе відновити — а це рівно той стан, з якого
нема автоматичного виходу.

Це найсильніший аргумент за те, щоб Фаза 2 включала `<configDir>/plugins/<self>/` (§7) — і
щоб починати саме з bootstrap, а не з drain.

### 5.10 Межі — як несумісна версія все ж може опинитися на диску

Навіть коли обидві фази реалізовано, лишаються перелічувані шляхи. Список вичерпний
настільки, наскільки нам відомі шляхи запису — і саме тому він тут, а не в голові.

**Гейт не спрацював, бо не було на чому:**

1. **У зміні немає `manifest.json`** — читати `minAppVersion` нема звідки, морозити не
   станемо (§5.2). Спирається на припущення «нема манифесту → версія не мінялася». Це
   припущення, не гарантія: пряме редагування `main.js` у репо його порушує.
2. **Автор не підняв `minAppVersion`** (§5.1) — головний режим промаху. Ми читаємо ЗАЯВУ
   автора, а не факт.

**Інші шляхи запису:**

3. **`bootstrapFromRemote`** — окремий шлях; закривається §5.9. Якщо його там НЕ
   реалізувати, це найширша з дірок: перше завантаження в порожній vault принесе всі
   несумісні плагіни разом із їхніми baseline.
4. **Наш власний плагін** (§4.4). Самооновлення підмінює файли ПРЯМО в drain і йде звичайним
   шляхом релоаду, тож §4.1/§4.2 його покривають — але лише пропуском релоаду: файли все одно
   на диску й спробують завантажитись при наступному старті. Сьогодні латентно (наш
   `minAppVersion` = 1.7.7).

**Поза нашим контролем:**

5. **Користувач або BRAT** ставить несумісну версію руками. Ми до цього не причетні; при
   активній заморозці вона принаймні не поїде в репо (§5.7).
6. **Файли, що вже лежать на диску до впровадження Фази 2** — ретроспективно не морозяться.
   Питання міграції: чи робити разовий прохід при першому запуску з новою версією плагіна.

**Інше, що Фаза 2 не робить:**

- падіння `onload()` з причин, не пов'язаних із версією (битий `data.json`, баг автора) —
  евристика мовчить, ловить тільки Фаза 1;
- нову версію офлайн не застосувати: вона лишається в репо, а не на диску — при розморозці
  потрібна мережа. Свідомий компроміс (§8.1).

### 6.8 Чого автотести НЕ покривають

- **Поведінку самого Obsidian** (§2). Наші тести перевіряють НАШУ реакцію на мокнутий
  плагін-менеджер; вони не можуть довести, що `enablePlugin` справді повертає `false`. Ці
  факти перевіряються грепом по бандлу (процедура — початок §2) і мусять переперевірятися
  при мажорних оновленнях Obsidian. Страхувальна сітка на випадок зміни — кон'юнкція 6.1.4.
- **Реальне падіння плагіна.** Один ручний прогін на пристрої з фікстурою — плагіном, чий
  `main.js` падає на обчисленні модуля:

  ```js
  class Boom extends undefined {}        // або: throw new Error("boom")
  ```

  Відтворює точний режим відмови Templater 2.24.3 і **не залежить від версії Obsidian**, тож
  знижувати застосунок не треба. ⚠️ Спроба відтворити інцидент підняттям `minAppVersion` не
  спрацює на жодній версії (§2.1) — перевірено на живому Obsidian.
- **Інтеграційний рівень.** Сценарії Фази 2 вимагають керованого `apiVersion`, якого на
  реальному Obsidian не підмінити. Тому Фаза 2 лишається на unit/manager-рівні; в
  `tests/integration/` іде щонайбільше перевірка, що звичайне (сумісне) оновлення плагіна
  проходить наскрізь без регресій.

Якщо колись знадобиться справжній старий Obsidian: asar-и лежать у релізах
`obsidianmd/obsidian-releases`; застосунок вантажить **найновіший** `obsidian-*.asar` з
`~/Library/Application Support/obsidian/`, тож для відкату треба покласти туди старий,
**прибрати новіший** і вимкнути автооновлення. Тільки на тестовому vault-і.

## 7. Відкриті питання (рішення власника)

- **Чи робити Фазу 2 взагалі.** Фаза 1 закриває те, що однозначно наша провина. Фаза 2
  потрібна лише для пристроїв із назавжди старим Obsidian. Ціна відома (§5), користь
  вузька.
- **Чи морозить Фаза 2 НАШУ власну папку** (§4.4). Не «окремий шлях через bootloader» —
  таким його робити не треба, самооновлення й так іде звичайним шляхом релоаду. Питання
  вужче: чи включати `<configDir>/plugins/<self>/` у заморозку. Для нас ставки вищі, ніж для
  чужого плагіна. У DRAIN-сценарії ризик прийнято: перевстановлення через BRAT дає сумісну
  версію (§4.4). Але в **BOOTSTRAP-сценарії (§5.9.1) перевстановлення не тримається** —
  наступний sync або перетирає його, або пушить стару версію в репо як даунгрейд для всіх
  пристроїв. Це найсильніший аргумент «за», і він каже починати з bootstrap.
- ⚠️ **НЕПЕРЕВІРЕНЕ, поза областю цього документа, але помічене при розборі §4.1.** Шлях
  прямого застосування (локальний файл не змінений) резолвера §28 не питає взагалі. Тобто в
  теорії можлива розбіжність бандла: `manifest.json` локально не чіпали — його перезаписує
  віддалена версія; `main.js` локально змінений — §28 обирає «ours». На диску опиняється
  новий манифест зі старим бандлом. `pullBundleSnapshots` захищає **вхідні дані резолвера**
  від такого перекосу, але чи захищає воно сам **результат** — я не перевіряв. Якщо це
  реальна дірка, вона існує вже сьогодні, незалежно від Фаз 1 і 2, і має розбиратися окремо.
- ~~Чи морозити desktop-only плагіни на мобільному.~~ **ВИРІШЕНО (2026-08-02): НЕ морозимо —
  §5.1.** Ціна — місце й трафік; взамін не потрібен новий механізм опитування репо, і плагін
  лишається актуальним на випадок, коли автор прибере прапорець.
- **Заморожений плагін не бачить жодних змін у репо, поки заморожений** — його шляхи

## 8. Розглянуто й відхилено

### 8.1 `.sync-new` — карантинні файли поруч із живими

Утримувати нову версію на диску у файлах `main.js.sync-new` тощо (окремий суфікс, щоб
bootloader і `AtomicWriteRecovery` їх не застосували); порівняння для цього шляху
перенаправляти на карантинний файл в обидва боки.

Механіка коректна, і `atomicWriteFile` з нею працює без змін (`main.js.sync-new`
стажується через `main.js.sync-new.sync-tmp`, що підпадає під наявний `*.sync-tmp*`).
Дає одну перевагу над §5: застосування **офлайн**.

**Чому не зараз — асиметрія зворотності.** `heldPluginUpdates` → `.sync-new` це чисте
розширення: запис уже називає, який плагін утримано, додати збережений вміст пізніше —
надбудова над наявним. Зворотний перехід так не працює: файлова конвенція, її семантика
відновлення й погрупований по плагіну apply доведеться нести завжди. Складність, узята
наперед, повертається щодня; складність, яку дешево додати потім, — це не інвестиція,
а «потім».

Аргумент «правила завантаження можуть стати жорсткішими» цей вибір **не розрізняє**: обидва
варіанти читають те саме поле і морозять ті самі оновлення (§5.1).

### 8.2 Рядок у `.gitignore` замість запису в метафайлі

`.obsidian/.gitignore` **синхронізується** (є у віддаленому дереві). Рядок, доданий на
одному пристрої, заморозив би плагін і на здоровому. Відкидається.

### 8.3 Не просувати `lastSyncCommitSha`, поки щось заморожене

Прецедент у коді є — `anyOverlapDeferred` (`src/sync2/sync2-manager.ts:1213`, `:1357`)
навмисне лишає `lastSync` на місці, щоб наступний прохід зайшов у reconcile. Але він
розрахований на короткий конфлікт «до наступного push». Заморозка триває місяцями: база
лишиться древньою, кожен синк перезавантажуватиме й перевідкидатиме ту саму дельту, reconcile
вмикатиметься постійно.

### 8.4 Відкат на `.sync-bak` після невдалого релоаду

Виявити відмову і повернути старі файли з бекапу атомарного запису. Мертве двічі: відновлені
старі файли розійдуться з baseline і поїдуть у репо як даунгрейд (§5.4, той самий механізм),
а шкода й так обмежена одним перезапуском — відкат купив би години.

### 8.5 Відновлення втраченого стану увімкненості

Знято: ми його не втрачаємо (§2.5).
