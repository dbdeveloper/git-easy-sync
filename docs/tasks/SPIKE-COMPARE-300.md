> **Статус: РІШЕННЯ ПРИЙНЯТО (2026-08-28).** Це spike (дослідження + емпірика), перетворений на
> ground-truth після ухвалення власником. Фінальний стан — §6. Перенесено в
> [`SYNC2-NEW-DRAIN.md` §VII.1](./SYNC2-NEW-DRAIN.md), знято блокування з

## 1. Проблема (нагадування)

`GET /repos/{o}/{r}/compare/{base}...{head}` — джерело "що змінилось на remote" для pull-фази
нового drain (§I.2 `SYNC2-NEW-DRAIN.md`). За **офіційною документацією GitHub** (`docs.github.com`,
"Compare two commits", live-перевірено 2026-08-28), `files[]` у відповіді обрізається на **300**
записах, дослівно: *"The list of changed files is only shown on the first page of results, and it
includes up to 300 changed files for the entire comparison."* Документація не пояснює причину
й не пропонує офіційний workaround для списку понад 300 — і **без жодного прапорця "обрізано"** у
самій відповіді. Сценарій "дні чи тижні без мережі" (власна передумова нового drain-алгоритму —
саме заради нього й будується вся batch/chain-machinery) — це якраз той випадок, де вікно
`base→head` найширше й поріг найімовірніший. Файли понад 300-ту позицію ніколи не потрапляють у
`TrackedFiles`, `base` просувається до нового `head_hash`, ніби все синхронізовано — **мовчазна,
назавжди втрата частини remote-змін**, без жодного конфлікту чи помилки.

**Стабільність числа 300 — контрактна, не лише ймовірнісна.** Наш клієнт шле
`X-GitHub-Api-Version: 2022-11-28` на кожен виклик (`src/github/client.ts:92`). Live-перевірено
2026-08-28 проти офіційної документації API-версіонування (`docs.github.com`, "API Versions"):
*"Any additive (non-breaking) changes will be available in all supported API versions"* —
breaking-зміни (видалення/перейменування поля чи операції) виходять ЛИШЕ під новою версією,
яку клієнт має явно підключити через заголовок. Тобто для запінченої версії `2022-11-28` GitHub
контрактно НЕ МОЖЕ змінити 300 (ні вгору, ні вниз) без нашої явної згоди на нову версію — це не
"ймовірно стабільно", а гарантія моделі версіонування. Це і є підстава для фінального рішення §6:
без адаптивного самокалібрування, звичайна константа.

**Housekeeping, не ризик даних:** версія `2022-11-28` підтримується до **10 березня 2028** —
документація ОБІЦЯЄ, що після цього непереведені запити отримають `410 Gone` (голосно, одразу,
для ВСІХ викликів), не тиху зміну поведінки. **Це неперевірене живцем твердження** — жодна
версія GitHub REST API ще не встигла закінчитись, тож `410` неможливо спостерігати напряму.
Живий probe (тепер ПОСТІЙНИЙ regression: `tests/integration/api-version-limit.test.ts`,
2026-08-28) перевірив
НАЙБЛИЖЧИЙ доступний сурогат — недійсний (не застарілий, а просто неіснуючий) рядок версії
`"2015-01-01"` — і отримав **`400 Bad Request`**, тіло:
`{"message":"Bad Request","errors":"The version you specified in the \"X-GitHub-API-Version\"
request header, \"2015-01-01\", is not a supported version. The following versions are
currently supported: \"2026-03-10\" (most recent) and \"2022-11-28\".", ...}`. Тобто ЖИВА,
підтверджена форма помилки для нерозпізнаної версії — `400` зі списком підтримуваних версій у
тілі; `410` лишається задокументованою, але поки що неспостережуваною обіцянкою для сценарію
"версія БУЛА підтримувана і перестала". Рантайм-детектор (нижче) має ловити ОБИДВІ форми, не
лише задокументовану. Вартий рядка в TODO ("мігрувати на новішу `X-GitHub-Api-Version` до
2028"), не архітектурного рішення зараз — на момент цього спайку вже існує новіша `2026-03-10`.

### 2.1 Роль `compare()` №2 — детектор force-push (чому його не можна просто замінити на tree-diff)

`compare()` у поточному (pre-rewrite) pull-шляху (`sync2-manager.ts:1170-1199`) робить не лише
"дай список змінених файлів" — його 404-відповідь **є** єдиним детектором розбіжності історії
(force-push, GC'd commit):

```ts
try {
  cmp = await this.client.compare({ base: expectedHead, head: currentHead, retry: true });
} catch (err) {
  // compare returns 404 when the base commit is unreachable
  // (force-pushed history, GC'd commit, manifest corruption...)
  if (status === 404) {
    // base недосяжний — diff-ити нема з чим, стрибаємо lastSync прямо на head
    /* ... */
  }
}
```

`GET /git/trees/{head}?recursive=1` **структурно не може дати цей сигнал** — цей ендпоінт не
приймає `base` взагалі, лише один SHA; він відповідає на питання "яке дерево на цьому коміті",
не "чи є мій старий `base` предком цього коміту". Це і є причина, чому `compare()` лишається
обов'язковим першим викликом у будь-якому варіанті нижче, незалежно від того, чи потрібен нам
його `status`/`files[]` для чогось ще.

### 2.2 Rename-детекція `compare()`'s `status` — перевірено ЖИВЦЕМ, чи взагалі потрібна нам

Два окремі факти, обидва перевірені, не з пам'яті:

1. **Наш власний pull-код не використовує `status:"renamed"` для жодної відмінної поведінки.**
   `sync2-manager.ts:1396-1399` (коментар у коді): `previous_filename` лише дозволяє явно
   викликати `applyRemoteDeletion(previous_filename, ...)` замість покладатись на те, що зникнення
   старого шляху й так буде поміченим generic-кодом видалення. Результат ідентичний.
2. **`status:"renamed"` — це продукт схожості вмісту (similarity), а НЕ збігу SHA.** Перевірено
   пробом [`tests/integration/scratch/rename-detection-similarity.test.ts`](../../tests/integration/scratch/rename-detection-similarity.test.ts)
   (реальний GitHub, два коміти: той самий rename, різна "доза" редагування в ТОМУ Ж коміті) —
   переміщення + редагування 1 рядка з 40 (~97.5% спільного вмісту) → `status:"renamed"`,
   `previous_filename` коректний; переміщення + повне переписування (0% спільного) → окремі
   `"removed"` + `"added"`, без зв'язку. SHA різна в ОБОХ випадках (будь-яка зміна вмісту дає іншу
   SHA) — критерій rename-детекції ніколи не був "SHA збігається", завжди "вміст схожий".

**Наслідок для §3 нижче:** втрата `status`/rename-сигналу в tree-diff-based підходах — **НЕ
компроміс, а неважливий факт.** Tree-diff і так природно дає ідентичний практичний результат
(старий шлях зникає з дерева → `removed` за різницею множин; новий шлях з'являється → `added`) —
саме тим самим шляхом, яким наш код і сьогодні обробляє rename, лише без проміжного тегу.

### 2.3 Побічна знахідка — уже наявний, окремий дефект того самого класу

`GithubClient.getRepoContent()` (`src/github/client.ts:171-218`) **вже** викликає
`GET /git/trees/{branch}?recursive=1` — той самий ендпоінт, що й Probe C вище — але **не читає
поле `truncated` з відповіді взагалі** (лише `response.json.tree` і `response.json.sha`).
Тобто якщо колись реальний vault перевищить поріг обрізання ЦЬОГО ендпоінта (набагато вищий,
ніж 300, але не нескінченний), `getRepoContent()` мовчки поверне ЧАСТКОВИЙ список файлів — той
самий клас "тихої" проблеми, що й ця spike, тільки на іншому, вже написаному коді. Це
підтверджено читанням коду, окремої проби не було. **Незалежно від того, який варіант нижче
обереш для >300-fallback — вартий одного окремого TODO: додати перевірку `truncated` у
`getRepoContent()` (і кинути помилку чи інакше сигналізувати, не мовчати).**

## 3. Варіанти

> **Історія рішення (2026-08-28, стисло — деталі кожного кроку в git-історії цього файлу):**
> розглянуто commits-walk (а, відхилено — вартість/merge-commit ризик), tree-diff-як-єдиний-
> механізм (б, відхилено — не детектує force-push), hop через `commits[]` з проміжним `base`
> (г, відхилено — покладався на G9-reconcile-гейт замість структурного усунення проблеми, і
> складніший за альтернативу без переваги в типовій вартості), самоверифікація нижче 300 з
> адаптивним самокалібруванням порогу (розглянуто, відхилено — офіційна документація GitHub
> робить це паранойєю, §1). **Фінал — гібрид (в), константа 300, без самоверифікації.**

### (а) Ходити по комітах, обробляючи кожен окремо (ВІДХИЛЕНО)

Список комітів у вікні `base→head` + для кожного коміту — його власний `files[]`.

**Вартість:** ≈ `ceil(C/100..250) + C` викликів, де `C` — кількість комітів у вікні. Масштабується
з КІЛЬКІСТЮ КОМІТІВ, не файлів — тижні офлайн можуть дати C у сотні, сотні викликів **на кожну
спробу drain**.

**Структурна проблема, не лише вартість:** FINALIZE мержить conflict-branch → main (§III), тож
історія main містить merge-коміти. `files[]` GitHub-коміту для merge-коміту — це diff відносно
ПЕРШОГО батька; друга сторона merge у такому per-commit diff-і не видно без додаткової обробки.
Не перевірено живим пробом — залишається як застереження. Гібрид (в) уникає цієї проблеми
структурно (tree-diff порівнює повні знімки, не по-комітні diff-и).

### (б) Дерево на `head` проти локального cold-baseline

Один виклик `GET /git/trees/{head}?recursive=1` (Probe C, підтверджено — БЕЗ 300-ліміту, з
робочим `truncated`-прапорцем) → `path → sha` мапа. Порівняти проти вже наявної локально
cold-baseline мапи (`files{}` з `SYNC2-METAFILE-REFACTOR.md`):

- шлях є в head-дереві, нема в baseline → `added`
- шлях є в baseline, нема в head-дереві → `removed`
- sha різниться → `modified`
- sha збігається → без змін

**Вартість:** РІВНО 1 виклик. Немає merge-commit-проблеми (повні знімки, не по-комітні diff-и).

**Раніше вважалось "ціною" — спростовано (§2.2):** втрата `status`/rename-тегу — НЕ компроміс.
Наш власний код не використовує його для жодної відмінної поведінки (лише pull-side шорткат),
і природний результат tree-diff (`removed` за старим шляхом + `added` за новим) — той самий
кінцевий стан, яким наш код і сьогодні обробляє rename.

**Чому НЕ можна взяти (б) як ЄДИНИЙ, універсальний механізм (завжди, замість `compare()`):**
`GET /git/trees/{head}` не приймає `base` — структурно не може дати сигнал "чи є мій старий
`base` предком поточного `head`" (§2.1). Це наш ЄДИНИЙ детектор force-push сьогодні
(`sync2-manager.ts:1170-1199`, 404 на `compare()`). Відмова від `compare()` взагалі означала б
або втрату детектора force-push, або винесення цієї перевірки в окремий виклик — гірше й
складніше, ніж лишити `compare()` першим кроком і додати (б) лише як fallback.

### (в) Гібрид: `compare()` завжди першим + tree-diff-фолбек лише при обрізанні (РЕКОМЕНДАЦІЯ)

"Дискавері, потім обробка" — окрема, чисто читальна фаза, яка НІКОЛИ не чіпає `push_queue/` і
НІКОЛИ не просуває `base`, доки не має ПОВНОГО списку змінених файлів для поточної пари
`(base, head)`:

1. `compare(base, head)` — завжди перший виклик. Дешевий (1 запит) і обов'язковий незалежно
   від решти — це наш детектор force-push (§2.1); прибрати його не можна.
2. Якщо `files.length < 300` — довіряти результату повністю, БЕЗ звірки, дискавері завершено,
   жодного додаткового виклику.
3. **Лише якщо `files.length === 300`** (сигнал можливого обрізання — інших сигналів нема,
   Probe A: жодного "total"-подібного поля) — один додатковий виклик (б): tree-diff на той
   самий `head` проти локальної cold-baseline. Результат — ПОВНИЙ список змінених шляхів, яким
   ЗАМІНЮЄТЬСЯ (не доповнюється) часткова відповідь `compare()`.
4. Дискавері завершено — маємо повний, перевірений список змінених шляхів. Тепер, і лише тепер,
   передати його існуючому drain-коду без змін; `base` просувається ОДНИМ кроком, прямо зі
   старого значення до `head` — точно так, як і сьогодні (`sync2-manager.ts:1461`). Жодного
   проміжного стану `base` ніколи не існує зовні дискавері-фази.

### 3.4 Push-side захист — ОБОВ'ЯЗКОВИЙ, окремий від discovery-порогу (2026-08-28, четверта ревізія)

**Знахідка, серйозніша за "втрату файлів при читанні":** якщо discovery помилилось (реальний
GitHub-ліміт колись тихо зсунеться нижче 300, і `compare()` обріже список так, що якийсь шлях
`F` не потрапить у `cmp.files`) — наступний push, що торкається `F`, **не дає жодної помилки**.
Перевірено в коді (`sync2-manager.ts:3538-3563` Case 3 "fast path" + `3729-3786` побудова
коміту): Case 3 явно ПЕРЕЦІЛЮЄ `parentCommitSha` на живий `currentHead` саме щоб ГАРАНТОВАНО
уникнути 422; `createTree({tree: entries, base_tree: currentHeadTree})` накладає наші файли на
базове дерево БЕЗ жодної перевірки "чи цей шлях уже змінився" (git-примітиви такого не мають);
`updateBranchHead` — валідний fast-forward, проходить чисто. **Push мовчки затирає remote-версію
`F`, без помилки, без сліду** — і після цього наш snapshot записує `F` з НАШОЮ sha як baseline,
тож навіть МАЙБУТНІЙ tree-diff вважатиме цей шлях "синхронізованим". Дані знищено безповоротно.

**Чому pull-side захист (`queuedPaths`-overlap-deferral) цього не ловить:** він **списковий** —
звіряє батч проти `cmp.files`. Якщо `compare()` обрізаний і `F` випав зі списку, захист його
просто не бачить. Той самий клас дефекту, що вже названий у SYNC2-NEW-DRAIN.md §VIII.M.2
("fast-path пропускає reconcile", SYNC-FIX "defect A").

**Наслідок для рішення §6:** сам по собі 300-поріг + canary-тест (§6, попередня ревізія)
захищають ЛИШЕ читання (пропущений pull, виявиться і надолужиться пізніше). Вони **не захищають
запис** — а це серйозніший, безслідний клас втрати даних. Тому push-side захист — ОКРЕМИЙ,
ОБОВ'ЯЗКОВИЙ шар, не альтернатива 300-порогу і не залежний від нього:

**Механізм (владник обрав, "salvage" запропонованої ним 422-реакції — перенацілено на дію, яка
реально спрацьовує):** для КОЖНОГО шляху в батчі, ПЕРЕД його включенням у `createTree`, — один
`getContentsMetadataAtRef(path, currentHead)` (той самий метод, вже вживаний у
`reconcileBatchAgainstHead`'s SHA-first гілці — НЕ новий виклик, лише розширення того, коли він
запускається). Звірити повернуту `sha` проти НАШОЇ власної, вже записаної локально baseline-sha
для цього шляху. **Розбіжність, попри те що `expectedHead === currentHead` (тобто ми в Case 3,
"начебто все відомо") — це прямий доказ, що наше discovery для цього шляху було неповним.**
Реакція: не блокувати весь push — обробити САМЕ цей шлях через існуючу reconcile-логіку (Case 4,
`sync2-manager.ts:3945+`), а не через сліпе накладання. Побічно: коли таке спрацьовує при
`files.length` (з останнього compare()) `< 300`, це ЖИВИЙ, production-time доказ, що реальний
ліміт GitHub нижче 300 — сильніший сигнал, ніж canary, і його варто зберегти (в Settings плагіна
чи логах) для діагностики, хоч і не обов'язково як змінний поріг у самому коді.

**Вартість:** N дрібних `getContentsMetadataAtRef`-викликів на push (по кількості файлів у
батчі — типово одиниці, той самий метод і масштаб, яким щойно замінено прогрес-бар, §5) —
істотно дешевше за відхилений 100-поріг (там — до 5.5 МБ на pull), і працює НЕЗАЛЕЖНО від того,
яке значення (300 чи щось інше) discovery-код зараз вважає порогом.

**Пов'язана знахідка — той самий clobber-клас, інший тригер:** force-push handling
(`sync2-manager.ts:1188-1201`) СВІДОМО спрямовує наступний push у той самий Case-3
fast-path (коментар у коді це підтверджує) — тобто force-push-сценарій (§VII SYNC2-NEW-DRAIN.md)
МАЄ ТУ САМУ ескалацію до мовчазного clobber-у, не лише "застарілий локальний vault". Той самий
push-side механізм вище закриває обидва тригери одним кодом, не двома окремими фіксами.

---

**Довіра до 300 — константа, не самоверифікована.** Розглядався варіант тригерити tree-diff-
звірку вже нижче 300 (спершу поріг 100, потім адаптивне самокалібрування з розбіжністю
compare()/tree-diff як живим детектором зсуву) — саме щоб ловити можливий зсув реального
GitHub-ліміту ще ДО того, як він торкнеться production-довіри. **Відхилено (§1):** ліміт 300 —
задокументована, а не спостережена поведінка публічного REST API (офіційний текст, live-
перевірено 2026-08-28: *"...includes up to 300 changed files for the entire comparison"*) —
зміна цього числа була б зміною документованого контракту API, набагато менш імовірний сценарій,
ніж тиха внутрішня зміна. Самоверифікація для ЧИТАННЯ визнана зайвою складністю проти цього
ризику; регресійний захист (нижче) залишається достатнім.

**Вартість:** 1 виклик у типовому випадку (<300 файлів) — без змін проти сьогодні. 2 виклики
(compare + tree-diff) лише коли реально ≥300 — за оцінкою власника, "фанатичний" рідкісний
випадок (наприклад, масове АІ-кероване редагування vault-у), не типовий шлях користувача. Коли
≥300 спрацьовує — навмисно НЕ оптимізовано (dual-tree walk із §5 лишається задокументованою, не
реалізованою ідеєю): повний tree-diff, повільно й дорого для цього одного рідкісного pull-у,
прийнятно за власною оцінкою власника.

**Паралелізм tree-diff-виклику з чимось іншим — перевірено в коді, НЕ рекомендується.**
`src/worker/network-worker.ts` (шапка файлу, явний архітектурний вибір): "single dedicated
thread... Eliminates a whole class of 'two requests for the same resource race each other' bugs."
Ламати цей намір заради одного рідкісного tree-diff-виклику означало б повертати той самий клас
гонок, який дизайн існує, щоб унеможливити — і "дискавері, потім обробка" (§3.в) означає, що
процесити нічого не можна, доки дискавері не завершено, тож немає іншої корисної роботи, яку
можна було б чесно паралелити САМЕ в цій точці. UI лишається відповідним і без цього — дає
звичайна `async`/`await`-модель.

## 4. `remote.mtime` — ОКРЕМЕ, не нове й не специфічне для >300 питання

**Виправлення власного викладу:** попередня версія цього розділу подавала lazy-populated
`remote.mtime` як компроміс, специфічний для >300-fallback-шляху. Це неточно й саме те, що
викликало плутанину — виправляю: жоден файловий список — ні `compare()` у ЗВИЧАЙНОМУ (не
обрізаному) випадку, ні `commits[]`, ні tree-diff — **не несе дату файла напряму**. GitHub не
синтезує "дату файла" на рівні `files[]`-запису (файл міг торкнутись кількох комітів у вікні);
дата існує лише на рівні КОМІТУ (`commit.committer.date`). Тобто питання "як `remote.mtime`
взагалі заповнюється" існує **однаково для КОЖНОГО шляху, знайденого через `getChangedFilesFromGitHubRepo`,
незалежно від того, чи спрацював hop чи ні** — це не нова вартість рекомендації §3.2/§6, а вже
наявне відкрите питання всього pull-шляху, яке я помилково прив'язав лише до fallback-гілки.

`SYNC2-NEW-DRAIN.md` §VIII, нотатка 5 (рядки ~3495-3517) фіксує **строгий інваріант**:
`tracked.remote.mtime` = дата GitHub-коміту, що дав цей вміст, і сьогодні популюється одразу при
виявленні змінного файлу (вимагає окремого запиту дати за шляхом — сьогодні це
`getLatestCommitDateForPath`, вже наявний метод, використовуваний старим plugin-mtime-tiebreak-ом).

Дата для path реально споживається лише в ДВОХ місцях: sibling-naming (лише для файлів, що
СПРАВДІ в конфлікті) і `.obsidian`-mtime-tiebreak (лише для справжньої колізії, і лише коли
налаштовано git author identity — інакше OURS перемагає без потреби в mtime взагалі). Це та сама
lazy-стратегія, що вже прийнята для `device_label` (`getCommitDeviceLabelForPath`, populated
LAZILY, лише в момент народження/оновлення конфлікту, НЕ для кожного зміненого remote-файлу).

**Напрямок, що потребує підтвердження власника (загальне питання pull-шляху, НЕ рішення цього
spike):** чи можна `remote.mtime` для КОЖНОГО шляху (не лише fallback/mega-commit) популювати
ТАК САМО ліниво — `getLatestCommitDateForPath` в момент, коли шлях реально стає конфліктом чи
потрапляє в `.obsidian`-tiebreak, а не одразу при виявленні. Симетрія з `device_label` сильна, але
це зміна існуючого "завжди одразу" інваріанту (§VIII нотатка 5) — власник мав конкретну причину
для "завжди" (crash-consistency між шляхом-без-краху і шляхом-з-крахом, не просто зручність), тож
варто підтвердити, що lazy-варіант цю властивість не ламає, перш ніж закладати це в дизайн. Це
питання не залежить від того, яке рішення §6 власник обере для 300-ліміту.

## 5. Інші обмеження (не досліджено емпірично, але структурні)

- Увесь HTTP engine йде через `WorkerClient.httpRequest` (sync2-engine.md) — додатковий
  tree-diff-виклик (рідкісний, >300-випадок) мусить іти тим самим шляхом, доступним на mobile.
  Нічого нового понад те, що вже й так вимагає звичайний `compare()`.
- Rate-limit: гібрид — **щонайбільше 2 виклики на спробу drain**, незалежно від масштабу
  розбіжності (кількості файлів чи комітів у вікні). Значно дешевше за (а) (сотні викликів у
  гіршому випадку) і не потребує жодних ітерацій чи bisection, на відміну від відхиленого (г).
- Немає дешевшого сигналу "можливо обрізано" для `compare()`'s `files[]`, крім
  `files.length === 300` — перевірено Probe A (жодного `total_commits`/подібного поля). Для
  tree-diff-виклику, натомість, є робочий `truncated`-прапорець (Probe C) — див. §6, п.4.
- **Вартість tree-diff-виклику масштабується з РОЗМІРОМ УСЬОГО VAULT, не з розміром діффу.**
  `GET /git/trees/{head}?recursive=1` завжди повертає ПОВНЕ дерево репозиторію — для vault на
  20 000 файлів, коли фолбек спрацював (≥300 remote-змін), відповідь несе всі 20 000 записів.
  Виміряно живцем (не оцінка): **273 байти/запис**
  (`tests/integration/compare-api-300-limit.test.ts`, `responseBytes=83256` на 305 записів) →
  для 20 000 файлів це ≈**5.5 МБ** за один виклик, і так щоразу, коли фолбек спрацьовує (за
  оцінкою власника — рідкісний, "фанатичний" випадок, §6).
  **ВИПРАВЛЕНО (2026-08-28), окремо від цього рішення:** `sync2-manager.ts:1230-1249` — поточний
  pull-код викликав той самий `getRepoContent()` (та сама `GET /git/trees/{branch}?recursive=1`)
  **на КОЖЕН непорожній pull, без жодного розмірного гейту**, лише щоб підсумувати розміри
  файлів для прогрес-нотиса — для 20-тисячного vault це ≈5.5 МБ на кожному pull, включно з тим,
  де змінився 1 файл. Замінено на `getContentsMetadataAtRef` (той самий per-path метод, яким уже
  користується `reconcileBatchAgainstHead`) для ≤5 змінених файлів (`PROGRESS_COUNT_THRESHOLD`,
  вже наявна константа); понад 5 — прогрес одразу вважається "важким" без запиту точних розмірів
  (той самий поріг, яким код і так користувався як fallback при мережевій помилці, тепер
  застосований проактивно). `pnpm test` (1907 тестів) і `tsc -noEmit -skipLibCheck` пройшли після
  зміни. Тепер жодного повнодеревного виклику на КОЖНОМУ pull-і — вартість 5.5 МБ лишається лише
  за tree-diff-фолбеком §3.в, при ≥300.
- **Чи є в GitHub REST API легший за tree/compare спосіб дізнатись ЛИШЕ кількість змінених
  файлів (без самого списку)?** Перевірено проти того, що вже підтверджено пробами — немає:
  `compare()` не несе жодного "total files"-поля (Probe A), `stats.total` у Repos "get commit"
  API — це РЯДКИ (additions+deletions), не файли (Probe B), tree-ендпоінт не має "count-only"
  режиму взагалі. У межах REST (єдиний контракт цього плагіна — CLAUDE.md, "тільки GitHub REST
  API") відповідь: такого способу нема. (GraphQL API, за пам'яттю, не перевірено живцем, має
  `changedFilesIfAvailable` на рівні коміту — поза контрактом REST-only цього плагіна; NEEDS
  PROBE, якщо власник колись відкриє це питання окремо.)
- **Розглянута, але НЕ рекомендована зараз оптимізація — dual-tree walk замість "завжди повне
  дерево".** Замість `recursive=1` (все дерево за один виклик), можна пройти дерева `base` і
  `head` ПАРАЛЕЛЬНО й НЕРЕКУРСИВНО з кореня: базове дерево вже маємо звідки взяти без нового
  стану — `setLastSync(currentHead, headCommit.tree.sha)` (`sync2-manager.ts:1461`) вже зберігає
  tree SHA останнього sync-у. Звірити top-level entries: де `sha` піддерева збігається — все
  піддерево гарантовано ідентичне (git — content-addressed), пропустити без запиту; де
  розходиться — рекурсивно повторити на один рівень глибше лише для цього піддерева. Вартість
  ~ `O(кількість каталогів на шляху до змін)`, не `O(розмір vault)` — для 20 000 файлів,
  зосереджених у кількох теках, це на порядки дешевше за 5.5 МБ. **Чесний компроміс:** кожен
  рівень — ОКРЕМИЙ мережевий виклик (послідовний чи паралельний по гілках), а не один; на
  mobile (~0.5-1с/виклик) зміни, розкидані по багатьох різних каталогах одночасно, можуть
  зробити цей шлях повільнішим за годинник, ніж один великий запит, навіть при меншому обсязі
  байтів. Не блокує рекомендацію §6 — окремий, майбутній етап оптимізації, якщо власник вирішить,
  що 5.5 МБ (чи реальний розмір для його vault) варті того, щоб їх уникати.

## 6. Рекомендація — ФІНАЛЬНЕ РІШЕННЯ (2026-08-28)

**Два незалежні шари, не один.** Discovery (читання) і push (запис) захищені ОКРЕМИМИ
механізмами — знахідка §3.4 показала, що захист лише читання (гібрид §3.в) залишає запис
незахищеним від мовчазного clobber-у, серйознішого класу дефекту, ніж пропущений pull.

### Шар 1 — Discovery (§3.в): гібрид, константа 300, без самоверифікації

1. `compare(base, head)` — завжди перший виклик. Дешевий, і єдиний детектор force-push (§2.1) —
   прибрати не можна.
2. `files.length < 300` → довіряти результату ПОВНІСТЮ, без звірки, дискавері завершено. Це
   переважна більшість pull-ів — жодної зміни проти сьогодні.
3. `files.length === 300` (єдиний доступний сигнал можливого обрізання — Probe A, жодного
   "total"-поля) → один додатковий tree-diff-виклик (§3.б: `GET /git/trees/{head}`, без
   300-ліміту, з робочим `truncated`-прапорцем) проти локальної cold-baseline. Результат — ПОВНИЙ
   список змінених шляхів, яким ЗАМІНЮЄТЬСЯ (не доповнюється) часткова відповідь `compare()`.
4. Дискавері завершено. `base` просувається ОДНИМ кроком до `head`, лише тепер — точно як і
   сьогодні (`sync2-manager.ts:1461`). Жодного проміжного стану `base` ніколи не існує зовні
   дискавері-фази (це і усуває залежність від G9-reconcile-гейту, через яку відхилено (г) — §3.в).

**300 — звичайна константа, без адаптивного самокалібрування.** Розглядалась і відхилена
(§1, §3) окрема self-verification-схема (тригер нижче 300, з опційним живим самокалібруванням
порогу) — ліміт задокументований офіційно GitHub REST API, тож зміна була б зміною публічного
контракту, значно менш імовірною за тиху внутрішню зміну. Регресійний захист нижче лишається
достатнім для цього залишкового ризику.

### Шар 2 — Push-side per-path перевірка (§3.4): ОБОВ'ЯЗКОВА, незалежна від порогу 300

Для кожного шляху в батчі, ПЕРЕД включенням у `createTree` (включно з Case 3 fast-path, де
сьогодні НЕМАЄ жодної перевірки) — один `getContentsMetadataAtRef(path, currentHead)`, звірений
проти власної записаної baseline-sha. Розбіжність при `expectedHead === currentHead` = доказ
неповного discovery для цього шляху → обробити через наявну reconcile-логіку (Case 4), не сліпо
накласти. Закриває і 300-related, і force-push-related (той самий Case-3-маршрут, §3.4) тригери
одним кодом. Вартість — N дрібних викликів на батч (типово одиниці файлів), незалежно від
розміру vault чи від того, яке значення discovery-код вважає порогом.

**Вартість:** типовий випадок — без змін (1 виклик). ≥300 файлів (рідкісний, "фанатичний" за
оцінкою власника випадок) — 2 виклики, tree-diff масштабується з розміром УСЬОГО vault
(виміряно: 273 байти/запис, ≈5.5 МБ на 20 000 файлів) — навмисно НЕ оптимізовано зараз
(dual-tree walk, §5, лишається задокументованою, не реалізованою ідеєю).

**Відхилено, задокументовано з причиною (§3):** (а) commits-walk — O(комітів), merge-commit
ризик. (г) hop через `commits[]` з проміжним `base` — покладався на G9-гейт замість структурного
усунення проблеми; складніший (bisection, mega-commit-крайність, неперевірена на масштабі
`commits[]`-пагінація) без переваги в типовій вартості. (б) tree-diff як ЄДИНИЙ, універсальний
механізм — не може замінити `compare()` повністю (немає `base`-параметра, не детектує force-push).
Self-verification нижче 300 (з фіксованим порогом чи адаптивним самокалібруванням) — офіційна
документація GitHub робить цей ризик низькоймовірним, зайва складність, §1/§3.

**Розглянуто, не блокує, окремий майбутній етап:** dual-tree walk (§5) — оптимізація tree-diff-
виклику з `O(vault)` до `O(каталогів на шляху змін)`, якщо 5.5 МБ колись стане реальною
проблемою. Не потребує нового локального стану (base tree SHA вже зберігається).

**ВЖЕ РЕАЛІЗОВАНО, окремо від цього рішення (2026-08-28):** прогрес-бар pull-у
(`sync2-manager.ts:1230+`) раніше платив ≈5.5 МБ (повне дерево) на КОЖЕН непорожній pull, лише
щоб підсумувати розміри кількох змінених файлів — виправлено на `getContentsMetadataAtRef`
(per-path, вже наявний метод) для ≤5 файлів, "важкий" без запиту точних розмірів понад 5 (§5).
`pnpm test` (1907 тестів) + `tsc -noEmit -skipLibCheck` — зелені після зміни.

## 7. API-version end-of-support — рантайм-детектор + модал (design, не housekeeping)

Окреме від §1–6 рішення (той самий день, 2026-08-28), навмисно винесене в свій розділ: не про
300-поріг, а про те, що станеться 10.03.2028, коли підтримка запінченої `2022-11-28` закінчиться
(§1). Власник прямо попросив змоделювати це padіння ЗАРАЗ і зробити проблему одразу зрозумілою
навіть тому, хто, можливо, у майбутньому підхопить цей плагін без контексту цієї розмови.

**Що вирішено:**
- **НЕ startup-перевірка.** Власник відхилив окремий пробний виклик при завантаженні плагіна:
  зайвий мережевий запит і — гірше — гарантована помилка в лозі на КОЖЕН boot, поки версія ще
  діюча (до 2028 це завжди буде помилковий сигнал). Замість цього — **реактивний** детектор:
  ловимо помилку на БУДЬ-якому REST-виклику, який плагін і так робить (перший `drain`, перший
  push, будь-що), а не generувати штучний.
- **Дві форми відповіді, обидві мають ловитись** (§1): документована `410 Gone` (для
  ДІЙСНО застарілої версії — неспостережувана живцем) І спостережена `400 Bad Request` з тілом,
  що містить `"is not a supported version"` (§1, `api-version-limit.test.ts` Probe B) — це
  найближчий живий сурогат, і невідомо напевно, чи `410` колись справді прийде саме в цій формі.
  Детектор матчить ОБИДВІ, не лише задокументовану.
- **Одноразовий модал за сесію** (не за кожен виклик — інакше "модал-шторм", якщо помилка
  повторюється на кожному REST-виклику після справжнього expiry). Короткий текст: сама помилка +
  натяк "увімкніть лог і повторіть спробу — деталі в лозі". Без версій/дат/technical deep-dive у
  модалі (`sync2-engine.md`: UI-текст — plain English, без engine-жаргону).
  Повний діагноз (версія, дата закінчення, посилання на docs.github.com/rest/about-the-rest-api/api-versions,
  спостережена форма помилки, HTTP-статус, тіло відповіді) — у `git-easy-sync.log` (JSONL,
  `safeStringify`), саме для майбутнього мейнтейнера без контексту цієї розмови.
- **Не блокує роботу плагіна.** Версія технічно ще діє під час deprecation-вікна (якщо GitHub
  колись почне слати `Deprecation`/`Sunset`-заголовки заздалегідь, §2 нижче) — модал це сигнал
  обслуговування, не помилка, що зупиняє sync.
- **Спокуса, свідомо НЕ робимо:** парсити список підтримуваних версій із тіла `400`-помилки й
  автоматично підняти власну константу `X-GitHub-Api-Version`. Зміна версії API може міняти
  семантику десь, де плагін цього не очікує (нова версія може відрізнятись у полях, статусах,
  поведінці якогось ендпоінта) — це залишається людським рішенням, не автоматизованим.

**Регресійний захист:** `tests/integration/api-version-limit.test.ts` (постійний, не scratch;
замінив одноразовий `scratch/api-version-expiry-probe.test.ts`). Три тести: (A) baseline — пінгована
версія ще працює, `Deprecation`/`Sunset`/`Warning`-заголовки досі `null` (якщо колись стануть
непорожні — це і є перший живий сигнал наближення 2028-03-10, знахідка, не флейкі-тест); (B) жива
форма помилки для нерозпізнаної версії (`400`, тіло з переліком підтримуваних версій) — форма,
яку рантайм-детектор мусить розпізнавати; (C) CANARY без мережі — падає, якщо до 10.03.2028
лишилось менше 90 днів, задовго до реального відключення. Live-прогін 2026-08-28: усі три зелені.

**Реалізація (код):** design-only на момент цього запису — ще не реалізовано в `main.ts`/UI.
Розміщення детектора: там, де вже проходять відповіді GitHub REST-викликів (`GithubClient` /
`WorkerClient.httpRequest`, `sync2-engine.md`), не новий підклас чи окремий підпотік. Модал —
після `onLayoutReady` (не блокує `AtomicWriteRecovery.sweep()`, яка мусить встигнути ДО
layout-ready за контрактом mobile-cross-platform.md).
