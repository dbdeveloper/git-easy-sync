## 1. Симптом і два підтверджені збої

### 1.1. Дефект A — недетермінована втрата чужих змін (G9)

**Репро** (`tests/integration/scenarios/sync2/multi-device/G9-concurrent-push-mid-drain.test.ts`):
10 локальних комітів C1..C10 (по файлу: note1..note10). Під час drain, рівно
перед push-ем 6-го коміту, «інший пристрій» змінює note7, note8, note9, note10
(файли, які C7..C10 теж чіпають; note6 НЕ чіпає). Інжекція зроблена через
обгортку `client.updateBranchHead`: на 6-му виклику вона реально пише ці 4 файли
в гілку (HEAD зрушується) → наш 6-й push сам дістає 422.

**Що спостерігаємо (стабільно, 2 загартовані прогони × 3 послідовні syncAll):**

|                              | Результат                        |
|------------------------------|----------------------------------|
| remote note1–6               | `ours` ✅                         |
| remote note7–10 (чужі зміни) | **`ours` ❌ — чуже ТИХО ЗАТЕРТО** |
| зареєстровані конфлікти      | **0**                            |
| збіжність на sync #2, #3     | **немає — стан не міняється**    |

**Правильно мало б бути:** note7–10 → **конфлікт** (наше `ours 7` vs чуже
`theirs 7`, обидва розійшлись від `base 7`). А сталося мовчазне перезаписування
чужого без жодного сліду. **І три повторні sync цього НЕ виправляють.**

> **Застереження до себе (методологічне):** у першому, НЕзагартованому прогоні
> здалося, що «наші C1–5 зникли з remote (tip=base)» + каскад з 10 конфліктів.
> Це НЕ відтворилось у загартованому тесті (свіже читання на кожному sync).
> Найімовірніше — **артефакт читання застарілої GitHub-репліки** при спостереженні
> після ОДНОГО sync. Наші коміти нікуди не зникали. Урок: **один syncAll — хибний
> оракул для конкурентного сценарію** (див. інваріант квієсценції I3 нижче).

### 1.2. Прогалина B — немає взаємного виключення локальних мутацій

Підтверджено читанням коду (не теорія):

- `drain()` захищений прапорцем `running` (`sync2-manager.ts:3035` —
  `if (this.running) return`), але це блокує лише **повторний drain**.
- Статус `"running"` виставляється **всередині `drain()`** (рядок 3047), а НЕ на
  вході `syncAll`. Викликачі (`main.ts` ribbon 1258, interval-`fullSync`→`sync()`
  2105→1258) гвардять по `getDrainStatus().state === "running"` — але цей статус ще
  `"idle"` протягом **усієї commit-фази** syncAll
  (`reconcileRemoteIdentity → bootstrap → recoverPushInflight → findChanges →
  enqueueOrMerge → store.save`), і лише тоді запускається `drain()`.
- `main.ts:1857 commit()` викликає `commitOnly()` **БЕЗ жодної** перевірки статусу.

Два різні вікна гонки:

1. **`commit()` під час активного drain** — гварда немає взагалі → `commitOnly`
   мутує чергу+snapshot одночасно з drain-ом.
2. **Другий `syncAll` під час COMMIT-ФАЗИ першого** — статус ще `"idle"`, тож гвард
   викликача **пропускає**. Найреальніший тригер — interval-tick, що спрацював, поки
   ручний sync у commit-фазі. Дві commit-фази перекриваються. (Другий syncAll під час
   уже-активного drain гвард ловить — це вікно закрите.)

В обох випадках — одночасний **read-modify-write** на тих самих `.push-queue`
файлах і на snapshot-store, без жодного локу → lost-update і неузгоджена
черга/snapshot.

## 2. Інваріанти (конституція алгоритму)

Новий алгоритм тримає ці правила ЗАВЖДИ. Тести перевіряють саме їх (а не кроки
реалізації — див. розділ 7, «прив'язуй до інваріанта, не до трасування»).

- **I1 — жоден користувацький коміт не втрачається мовчки.** Кожна локальна зміна,
  зафіксована в чергу, рано чи пізно потрапляє на GitHub або стає конфліктом.
  Ніколи — тихо не зникає.
- **I2 — жодна чужа зміна не затирається мовчки.** Розходження (наше vs чуже від
  спільної бази) → **конфлікт**, ніколи не перезапис. **Це те, що ламає G9.**
- **I3 — квієсценція (збіжність).** Після скінченної кількості sync без нової
  активності стан стабілізується у ПРАВИЛЬНому (черга порожня, конфлікти явні,
  remote = очікуване). Проміжний стан після одного sync може бути «недороблений» —
  але наступний sync його добиває (контракт «поклич мене ще раз»).
- **I4 — атомарність коміту відносно drain.** Коміт, що з'явився посеред drain,
  або повністю входить у цей drain, або чисто відкладається на наступний — **ніколи
  частково** (не «половина файлів батча пішла, половина ні»).
- **I5 — черга і snapshot ніколи не спостережувано неузгоджені.** База кожного
  батча (`parent`) — реальний предок поточного HEAD. Немає «сирітських» записів
  у snapshot після push/видалення.
- **I6 — жодна операція не крутить крутилку вічно.** Будь-який ретрай/бекоф
  обмежений; при недосяжній збіжності — чистий вихід + збереження стану для
  наступного drain (а не спін чи краш).
- **I7 — crash-атомарність БАТЧА (нова парадигма, за власником 2026-07).** Кожен push
  атомарний і **потенційно готовий до збою + перезапуску в наступному SYNC**. Ми
  ОЧІКУЄМО крах після (і під час) обробки кожного батча з `push_queue`. Отже: жоден
  батч не напів-застосований; після кожного батча стан на диску консистентний;
  resume продовжує з черги+записаної голови. **Наслідок для дизайну:** алгоритм НЕ
  сміє наперед-обчислювати стан майбутніх батчів (це створює крихкі проміжні стани) —
  кожен батч обробляється у свою чергу проти живої голови. Це прямо ВИРІШУЄ «зірка vs
  ланцюг» на користь ланцюга (§10) і прибирає crash-gap §8.7 п.9 як клас.

## 3. Алгоритм ДО 4 липня — per-batch pull (`f90240e`, parent of `3a98c96`)

Прочитано на самому parent-коміті (`git show f90240e:src/sync2/sync2-manager.ts`),
а не з дифу.

### 3.1. `pullIfNeeded()` — «важка й хитра» функція

```
expectedHead = store.getLastSyncCommitSha()          # наш останній відомий head
if expectedHead == null: return null                 # ще не було bootstrap
currentHead = client.getBranchHeadSha()              # СВІЖЕ читання HEAD (без guard)
if currentHead == expectedHead: return currentHead   # нема чого підтягувати
cmp = client.compare(base=expectedHead, head=currentHead)
for кожен віддалено-змінений файл f у cmp:
    if f перекриває шлях у нашій черзі:
        anyOverlapDeferred = true                    # ВІДКЛАСТИ: не чіпати vault,
        # lastSync лишається на expectedHead                 лишити конфлікт на потім
    else:
        застосувати f у vault (add/modify/delete/rename)
        оновити per-file snapshot
if anyOverlapDeferred:
    return currentHead        # АЛЕ lastSync лишається expectedHead →
                              # processBatch увійде в Case 4 (reconcile)
else:
    # жодного перекриття: усе чуже застосовано у vault
    lastSync = currentHead    # → наступний push бачить чистий Case 3 (fast-path)
    return currentHead
```

**Що це ГАРАНТУВАЛО:** кожен виклик бачить найсвіжіший стан remote і **розводить**
чуже: неперекривне — застосовує у vault; перекривне — відкладає в конфлікт.
Затирання чужого неможливе, бо перед кожним push ми спершу підтягли і порівняли.

### 3.2. Цикл drain (ДО)

```
while (лишились батчі):                # зовнішній (tail re-check)
  while (лишились батчі):              # внутрішній
    headHint = await pullIfNeeded()    # ← КОЖЕН батч: свіжий pull + defer/apply
    ids = queue.list()
    if ids порожньо: break
    processBatch(ids[0], headHint)     # push із reconcile, якщо HEAD зрушився
  await sleep(50ms)                    # дати FS-запису «долетіти»
  if queue.list() порожньо: break      # спіймати батч, що прилетів під кінець
```

**Ціна:** один зайвий `getBranchHeadSha` (+ можливо `compare`) на КОЖЕН батч.
При 10 батчах — 10 читань HEAD. Саме ця ціна й породила §7.10 (див. 4.1).

### 3.3. Слабке місце ДО-алгоритму (те, що §7.10 намагався полагодити)

`getBranchHeadSha` — **eventually consistent READ**. Одразу після нашого ж push
відстала репліка GitHub може повернути СТАРИЙ (позаду) head. Тоді `pullIfNeeded`
бачить `currentHead != expectedHead`, робить `compare`, і **наші власні щойно
запушені коміти виглядають як чуже розходження** → `reconcileBatchAgainstHead`
безумовно пере-таргетить parent → stale parent → 422 «not a fast forward» /
«власні дані повернулись як конфлікт». Одно-пристроєвий multi-batch drain.

## 4. Поточний алгоритм — §7.10 chaining (`3a98c96`, 4 липня)

### 4.1. Три кооперативні фікси §7.10

1. **Chaining (головний).** Не перечитувати HEAD перед кожним батчем — «нанизувати»
   батчі на НАШ власний підтверджений head (`store.getLastSyncCommitSha()`).
   `pullIfNeeded` тепер біжить **лише для 1-го батча** (або після 422).
2. **422 reconcile-retry** (`REF_STALE_MAX_RETRIES=3`). Справжній 422 (конкурентний
   пристрій) — довірливий сигнал → свіжий reconcile + повтор саме цього батча,
   із бекофом `400*(attempt+1)`.
3. **Монотонний guard** (`getGuardedHead`/`recordConfirmedHead`,
   `MONOTONIC_HEAD_WINDOW_MS=10_000`). Ніколи не довіряти читанню, що збігається з
   head-ом, який ми цієї ж сесії підтвердили-й-перевершили → бекоф + перечит, поки
   репліка наздожене. Припущення: гілка append-only.

### 4.2. Цикл drain (ПОТОЧНИЙ)

```
while (лишились батчі):                 # зовнішній
  chainedHead = null
  while (лишились батчі):               # внутрішній
    headHint = chainedHead ?? await pullIfNeeded()   # ← pull ЛИШЕ для 1-го батча!
    ids = queue.list()
    if ids порожньо: break
    for attempt in 0..REF_STALE_MAX_RETRIES:
      try:
        processBatch(ids[0], attempt==0 ? headHint : null)   # null → свіжий GET у processBatch
        break
      catch 422:
        chainedHead = null                                   # свіжий перечит наступного разу
        await sleep(400*(attempt+1)); continue               # reconcile ЛИШЕ цього батча
    chainedHead = store.getLastSyncCommitSha()               # наступний будується на НАШОМУ head
  await sleep(50ms); if queue.list() порожньо: break
```

`processBatch` має 4 випадки за (`expectedHead`, `currentHead`):

- **Case 1** (null, null) → bare repo.
- **Case 2** (null, set) → перший sync / adoption.
- **Case 3** (set, matches) → **швидкий шлях, БЕЗ reconcile** (просто дерево+commit+push).
- **Case 4** (set, drifted) → `reconcileBatchAgainstHead` + пере-таргет parent.

### 4.3. Який інваріант ламає (корінь дефекту A) — порушує **I2**

Трасування G9, підтверджене емпірично:

1. C1..C5 пушаться чисто (chaining, без pull). chainedHead просувається.
2. Інжекція note7–10 → HEAD зрушився. Push C6 → **422**.
3. Retry C6: свіжий HEAD (з чужими note7–10) + reconcile **лише note6** (не повний
   pull!). note6 remotely не чіпали → чисто → C6 лягає на новий HEAD.
   `chainedHead = C6-on-new-head`.
4. Push C7: `headHint = chainedHead`. `expectedHead (=C6) == currentHead (=C6)` →
   **Case 3, fast-path, БЕЗ reconcile** → дерево C7 з НАШИМ note7 лягає поверх →
   **чужий note7 ЗАТЕРТО**. Так само C8, C9, C10.
5. Завершального повного pull, що це зловив би, немає — а якби й був, затирання
   вже сталося (це не «відкладено», це «перезаписано в історії»).

**Корінь:** 422-retry реконсайлить лише ШЛЯХИ БАТЧА, що впав (note6), а не робить
повний pull. Наступні батчі чейняться на новий head і йдуть Case 3 (fast-path),
тому **ніколи не помічають**, що note7–10 змінились у remote. До §7.10 кожен батч
робив `pullIfNeeded` → побачив би note7 як чуже перекриття → конфлікт.

> **Кандидат-фікс (не рішення, а гіпотеза для розділу 6):** відновити per-batch
> pull, але з монотонним guard §7.10 (щоб не воскресити «власні дані як конфлікт»).
> Це, схоже, лікує І дефект A, І детерміновану 9-ку одночасно. АЛЕ це треба довести
> гейтом тестів (розділ 7), а не приймати на віру — можливо, це робить розділ 3
> «реструктуризацією», а не переписуванням з нуля.

## 5. Глава local-commit (окремо) + конкурентність

### 5.1. Алгоритм `commitOnly()` (`sync2-manager.ts:913`)

```
reconcileRemoteIdentity()          # чи не змінили owner/repo/branch у Settings
recoverPushInflight()              # SYNC2 §7.9 crash-recovery ПЕРЕД findChanges
invariants.enforce()               # .gitignore-канон
sanitizeForbiddenFilenames()       # прибрати < > : " | ? * \ з імен
changes = detector.findChanges()   # обхід vault + звірка зі snapshot
if changes порожньо: store.save(); onNoLocalChanges(); return
enqueued = enqueueOrMerge(changes) # створити/злити батч(і) у чергу
fireQueueDepth(); onLocalCommitted(enqueued)
# НЕ робить drain — тільки фіксація в чергу
```

`syncAll()` = те саме + наприкінці `drain()`. Тобто commit-фаза в обох спільна.

### 5.2. Останні зміни в local-commit (можливе джерело тестів/ідей)

- **§40** (`f315bc8`, `b8b22d5`): дедуп повторного коміту звіряти з **НАЙНОВІШОЮ**
  версією у черзі (`peekLatestPathSha`), а не з найстарішою; і порівнювати зміну з
  **останнім КОМІТОМ** (локальним), а не з останнім PUSH. Причина: без цього
  ланцюжок правок v1→v2→v3→v1 або багатопакетна черга давали або задвоєні коміти,
  або втрату «реверту до попереднього». **Уся історія змін має зберігатися «як є».**
- **§26** (`fcbf756`): база tracked-конфлікту комітиться лише якщо змінилась відносно
  значення у СВОЇЙ конфлікт-гілці, а не відносно main.
- **§ commit-timestamp** (`6081a1d`): локальний час коміту вшито в тіло повідомлення
  (бо push пізніше за commit; git-дата = час PUSH, а не коміту).

Ці правки — сигнал, що логіка «що саме потрапляє в наступний коміт» тонка й уже раз
ловила баги. Новий алгоритм мусить її зберегти (інваріант I1) і покрити тестами 7.x.

### 5.3. Матриця конкурентності (сценарій власника)

Сценарій: sync уже біжить, у черзі 3 відкладені батчі; ДО кінця drain
запускається local-commit, що додає 4-й батч; а посеред drain «прилітає» ще й pull.

JS однопотоковий → «одночасність» = чергування на `await`-точках. Небезпечні
чергування (усі на СПІЛЬНОМУ стані queue+snapshot+vault):

| # | Що робить drain (на await)                            | Що встигає local-commit                                         | Ризик                                         | Інваріант |
|---|-------------------------------------------------------|-----------------------------------------------------------------|-----------------------------------------------|-----------|
| 1 | `processBatch` пушить b1, зараз видалить його з черги | `enqueueOrMerge` читає чергу `[b1,b2,b3]`, пише `[b1,b2,b3,b4]` | lost-update: drain пише `[b2,b3]`, b4 затерто | I1        |
| 2 | `recordSync` мутує snapshot                           | `findChanges` читає snapshot напів-оновленим                    | хибний набір змін у коміті                    | I1, I5    |
| 3 | `store.save()`                                        | `store.save()`                                                  | last-writer-wins, втрата оновлень             | I5        |
| 4 | `pullIfNeeded` пише файл у vault (`atomicWriteFile`)  | `findChanges` обходить vault                                    | читання файлу під час запису                  | I4        |

**Що є зараз:** внутрішній цикл drain перечитує `queue.list()` щоітерації, тож
4-й батч БУДЕ підхоплений — але **лише якщо** його запис у чергу не поборовся з
видаленням b1 (рядок 1 матриці). `commit()` не перевіряє нічого.

**Перевірено (2026-07), який рядок реально псує стан:**

- **Рядок 1 (черга) — СПРАВЖНЯ корупція.** commit пише `push_queue`, drain
  читає+видаляє → lost-update = зниклий батч (порушення I1). ← єдина ціль бар'єра.
- **Рядок 2 (snapshot)** — commit тільки ЧИТАЄ snapshot (getters, без await
  всередині); drain пише. Read-during-write in-memory → максимум зайвий кандидат,
  який §40-dedup прибирає. Самокоригується.
- **Рядок 3 (`store.save`)** — спільний in-memory `store`, дані не розходяться;
  ризик лише торн-запис файлу → атомарний save/бар'єр.
- **Рядок 4 (vault)** — `atomicWriteFile` (tmp+rename) → часткового читання нема.

**Це прогалина B, і вона ВУЗЬКА:** не «серіалізувати все», а commit-синглтон +
адаптивна мітка `.attempted` (R3a/R3b). commit консолідує лише в незаclaim-ований
каталог, інакше APPEND-ить новий — тож симетричного «і навпаки» немає. Уся
коректність зводиться до **атомарності claim-у `.attempted`** — див. ⚠️ **ВАЖЛИВУ
ЗНАХІДКУ (TOCTOU)** у §6/R3b. Це, а не «глобальний лок», — центральна точка
координації.

### 5.4. Size-first short-circuit у change-detection — ПЕРФ, не коректність

> **Статус:** пропозиція власника (2026-08-01), НЕ реалізовано. Окремо від дефекту A /
> прогалини B — це не баг, а марна робота на гарячому шляху. Поведінку зберігає **точно**
> (див. «доказ» нижче), тож не потребує нового інваріанта.

**Що є зараз.** `findChanges` уже звіряє `mtime` **І** `size` як кон'юнкцію
(`change-detector.ts:218-222`, `276-279`; `findChangeForPath` — `414-416`):

```
snap.mtime === stat.mtime && snap.size === stat.size  → однакові, вихід
інакше                                                → readBinary + calculateGitBlobSHA
```

**Чого бракує.** Немає ранньої відсічі на розходженні розміру: `size ≠ size` уже ДОВОДИТЬ,
що вміст інший, а ми все одно читаємо весь файл і хешуємо, щоб це «підтвердити».

**Доказ, що відсічка коректна.** `calculateGitBlobSHA` хешує `blob <len>\0<bytes>`
(`utils.ts:140`) — довжина ВСЕРЕДИНІ preimage. Різна довжина ⇒ різний preimage ⇒ різний SHA
(за винятком реальної SHA-1-колізії). І size, і SHA беруться з СИРИХ байтів (нормалізація
тексту тут не втручається), тож звірка like-for-like.

⚠️ **Size — дискримінатор лише в ОДИН бік:** `size ≠` ⇒ різні (доказ); `size =` ⇒ **нічого
не сказано**, хеш обов'язковий. Тобто size ніколи не ЗАМІНЮЄ SHA — він лише вбиває читання
у випадку «точно змінився».

⚠️ **Кон'юнкцію з п.1 НЕ розщеплювати** на «mtime рівні → вихід». Це був би регрес:
перезапис у той самий tick з іншою довжиною оголосився б незміненим. `mtime ∧ size`
лишається як є; додається тільки відсічка.

#### Три reference-и, з якими звіряється SHA — і чи є в них size

`findChanges` порівнює локальний SHA не з одним значенням, а з `queuedSha ?? snap.baselineSha`
(рядок 329) або з `conflictRef` (§26, рядок 317). Тому відсічка можлива лише там, де для
reference-а відомий і розмір:

| reference | звідки size | вердикт |
|---|---|---|
| `snap.baselineSha` (`files{}`) | `snap.size`, пишеться в `recordSync` зі `stat` | **вже є** |
| queued-версія (`peekLatestPathSha`) | `adapter.stat` реального файлу батча `<batchDir>/vault/<path>` (`push-queue.ts:121`, читається на 295) | **є, просто не питаємо** — зміни схеми НЕ потрібно |
| `conflictRef` (`latestPendingBranchBaseSha`) | голий SHA у `ConflictRecord` (`conflict-store.ts:533`), файлу-двійника нема | **прогалина схеми** — потрібне парне поле + новий інваріант |

**Рішення по третьому рядку: не оптимізувати.** Гілка спрацьовує лише для tracked-conflict
баз (рідко), а нове збережене поле `branchBaseSize` — це значення, яке МОЖЕ розійтися з
реальністю, а хибний size = зайвий no-op коміт (проти «зберігати всі коміти»). Перші два
рядки безпечні саме тим, що size там похідний від живого `stat`, а не збережена копія.

#### Форма зміни — переставити, а не додати роботу

`queue` у продакшені підключена **завжди** (`main.ts:892`), тож питання не «чи є черга», а
«чи має черга цей шлях». `peekLatestPathSha` викликається сьогодні так само, лише ПІСЛЯ
читання (рядок 302 проти 288-290). Перестановка не додає викликів **на гілці, де size
розійшовся**; на решті гілок порядок не змінюється взагалі (саме тому крок 2 гейтиться
розходженням розміру ПЕРЕД зверненням до черги — інакше на «size той самий, mtime зрушив»
ми б спершу питали чергу, а потім усе одно читали й хешували):

```
1. mtime ∧ size збіглись                      → однакові (як зараз)
2. size розійшовся:
     queuedSha = peekLatestPathSha(path)      # порожня черга → list() порожній → null, дешево
     якщо queuedSha === null && conflictRef === undefined
                                              → modified БЕЗ read+SHA
3. інакше                                     → read + SHA (як зараз)
```

Гірший випадок — та сама вартість (ті самі операції, інший порядок). Кращий — мінус повне
читання файлу і хеш.

**`findChangeForPath` (414-431) — безумовний виграш:** черги там немає взагалі, reference
тільки `snap.baselineSha`, тож `stat.size !== snap.size → return modified` ставиться просто так.

**Бонус усередині самої `peekLatestPathSha`:** її fallback-гілка (295-298), коли в
`meta.uploadedBlobs` нема кешованого SHA, робить `readBinary` **snapshot-файлу** батча +
`computeGitBlobSHA`. Тобто сьогодні на одне 2 МБ-вкладення можемо прочитати й захешувати
ДВА файли — живий і queued — щоб дізнатися те, що видно з двох `stat`.
⚠️ Перед реалізацією перевірити: гілка кешу (293-294) повертає SHA, не торкаючись
snapshot-файлу — треба переконатися, що файл у батчі ще існує (інакше `stat` дасть `null` →
падаємо на сьогоднішній шлях, не на помилку).

#### Чому це варте заходу — заміряно

`calculateGitBlobSHA`, десктоп (Node WebCrypto, той самий алгоритм):

```
 2 МБ →   6.3 ms
10 МБ →  22.3 ms
50 МБ → 106.8 ms   (на кожен хеш)
```

Мобільний множник НЕ міряно. Три речі, які ці числа приховують:

1. **Це головний потік.** `change-detector.ts:7` бере `calculateGitBlobSHA` з `../utils`
   напряму, тоді як `push-queue.ts:298` іде через `workerClient.computeGitBlobSHA`.
   Detection — єдине місце гарячого шляху, де хеш лишився на main → 100 ms = видимий jank.
2. **Подвійна алокація.** `utils.ts:141-143` збирає `store = header + bytes` — ще одна ПОВНА
   копія. 50 МБ вкладення = ~100 МБ транзієнтної пам'яті на main; на мобільному це
   небезпечніше за час.
3. **Плюс сам `readBinary`** (не міряно, залежить від пристрою/ФС) — його відсічка прибирає
   цілком.

**Чесний обмежувач масштабу:** відсічка працює лише для файлів, які ВЖЕ мають snapshot і в
яких змінився розмір. На першому синку (`watermark === null`, гілка `!snap`, рядки 241-266)
snapshot-а нема → читаємо й хешуємо все, економія нульова. Виграш — на кожному НАСТУПНОМУ
проході, коли 2 МБ+ вкладення перезаписали/переекспортували.

**Єдина ціна.** Відсічка перетворює «перевірено незмінний» на «припускаємо змінений». Якщо
`stat.size` збрехав (індекс Obsidian відстає) → пушимо ідентичні байти → **зайвий no-op
коміт**. Ризик вузький: сьогоднішня гілка 330-341 ловить «торкнули, але не змінили», і
переважна більшість таких випадків — mtime зрушив, size той самий, чого відсічка не чіпає.
Випадок «size інший, вміст той самий» вимагає, щоб брехав сам замір розміру.

**Тест-контракт (мінімум):**

1. 🔑 size розійшовся + шлях у черзі з ТИМИ САМИМИ байтами → **НЕ емітиться** (§40 не
   зламано). Це той тест, який червоніє, якщо крок 2 реалізують без гарду
   `queuedSha === null` — тобто саме та помилка, яку перестановка й провокує.
2. size розійшовся + черга порожня → `modified` БЕЗ жодного `readBinary` (шпигун на адаптері).
3. size той самий, mtime зрушив → SHA рахується (стара поведінка збережена).

**Де відсічка НЕ застосовна — три `.gitignore`.** Для них будь-який stat-short-circuit
повертає баг, через який його й зняли (апгрейд плагіна змінює КОНСТАНТУ блоку, файл на диску
не рухається → mtime і size збігаються → нові канонічні рядки не доїжджають). Плюс `size`
там навіть не зберігається — див. SYNC2-METAFILE-REFACTOR §5, `invariantState`.

## 6. Вимоги до нового алгоритму (виведені з інваріантів; НЕ дизайн)

- **R1 (з I2).** Перед push будь-якого батча його шляхи мають бути звірені з
  АКТУАЛЬНим remote-станом цих шляхів. Ніякого fast-path Case 3, що пропускає
  reconcile, коли між нашими push-ами прилетіла чужа зміна. (Пряме лікування A.)
- **R2 (з I3).** Проміжний недороблений стан дозволений, але має існувати
  детермінований механізм «доробити наступним sync» до збіжності — і тест на це
  (кілька syncAll підряд).
- **R3 (з I4, I5, прогалина B).** commit-фаза і drain-фаза не мутують спільний стан
  одночасно. Розкладається на три конкретні механізми, ОБРАНІ власником (нижче):
  **R3a** — commit-синглтон (commit↔commit); **R3b** — протокол `.attempted-commit`
  (commit↔drain за каталог); реальна ціль — лише `push_queue` (див. §5.3), тож
  глобального локу не треба.

  **R3a — commit є СИНГЛЕТОНОМ, НЕЗАЛЕЖНО від структур.** commit не стартує, якщо вже
  йде інший commit — грає роль лише **факт** роботи commit, а не які каталоги він
  чіпає. Двох commit паралельно бути не може й не потрібно.

  **Механізм — «дзвоник на рецепції» (coalesce / trailing-debounce).** Дві in-memory
  змінні: `commit_in_progress` (адмін зайнятий) і `restart_commit` (дзвоник — лише
  сигнал «підійди ще раз», скільки б не тиснули). Це коалесценція, а не FIFO з N
  комітів: `findChanges` при перезапуску заново сканує ВСІ зміни, тож N проходів зайві.

  ```
  onCommitTrigger():                 # клік [commit] / подія
    if commit_in_progress:
      restart_commit = true          # дзвоник — і вихід
      return
    commit_in_progress = true
    runCommitLoop()

  async runCommitLoop():
    try:
      do:
        restart_commit = false       # ← скидати ПЕРЕД проходом
        await doOneCommitPass()      # findChanges + enqueue
      while restart_commit           # дзвонили під час проходу → ще раз
    finally:
      commit_in_progress = false     # ЗАВЖДИ звільнити
  ```

  **Чому коректно:** `restart_commit` скидається ПЕРЕД проходом → будь-який клік ПІД
  ЧАС проходу фіксується й `while` його бачить. Перевірка `while` + звільнення
  `commit_in_progress` — синхронні після останнього `await` → жоден клік не влізе між
  ними (однопотоковість). Сигнал не губиться. (Якби скидали ПІСЛЯ проходу — був би
  вузький момент втрати кліку.)

  **Два краї (інакше — тихий deadlock):**
    1. **`finally` обов'язковий** — якщо прохід кине помилку, а звільнення поза
       `finally`, `commit_in_progress` залипне `true` назавжди, і всі коміти лише
       дзвонитимуть у порожнечу (як drain звільняє `running` у `finally`,
       `sync2-manager.ts:3299`).
    2. **Помилка + `restart_commit` не зациклюють** — сліпий перезапуск на стійкій
       помилці = нескінченний цикл (порушення I6). На помилці: звільнити, показати
       помилку, НЕ авто-перезапускати (хай наступний тригер спробує).

  `commit_in_progress` — in-memory, губиться на reload (і добре: свіжа сесія не в
  процесі). Крах ПОСЕРЕД запису каталогу ловить окремий механізм — `.attempted-commit`
  (R3b).

  > **Не плутати два різні механізми:** лок запуску `commit_in_progress` (R3a,
  > in-memory, як drain-івський `running`) захищає **commit↔commit**; файл-мітка
  > `.attempted-commit` (R3b, crash-visible) захищає **commit↔drain** за конкретний
  > каталог. Різні рівні — різні інструменти.

  **R3b — commit↔drain: адаптивна модель на мітці `.attempted`, «і навпаки» НЕ існує.**
  Правило (уточнено власником):
    - commit **консолідує** (пише повторно в останній каталог) ТІЛЬКИ коли drain його
      ще не забрав (немає `.attempted`);
    - як тільки `.attempted` є (drain claim-нув каталог) — commit **одразу APPEND-ить
      новий** каталог, не чекаючи;
    - тож commit **ніколи не пише в каталог, що drain уже обробляє**; drain має
      беззастережний доступ до своїх каталогів. **Жодного «і навпаки» / симетричного
      очікування немає** — commit просто адаптується (append при claim).

  > ### ⚠️ ВАЖЛИВА ЗНАХІДКА — TOCTOU на встановленні мітки `.attempted`
  >
  > Уся коректність R3b тримається на **атомарності claim-у**. Єдина реальна гонка,
  > що лишається, — момент **встановлення/перевірки** `.attempted`:
  >
  > ```
  > commit: exists(B/.attempted)? → ні → почати консолідацію (пише в B)
  > drain:               markAttempted(B) + читає вміст B для push
  > ```
  >
  > Якщо ці два чергуються, commit **дописує в каталог B, який drain уже claim-нув і
  > читає** → або зміна commit-а не потрапить у push (lost-update, порушення I1), або
  > потрапить двічі. Поточний код робить `exists()`-перевірку і запис **окремими**
  > await-кроками (`mergeIntoLatestPending` `push-queue.ts:395-398` vs
  > `markAttempted` `sync2-manager.ts:3489`) — тобто claim **НЕ атомарний**.
  >
  > **Вимога до нового дизайну:** claim каталогу і рішення commit-а «консолідувати чи
  > append» мусять бути **взаємно атомарні / впорядковані**. Обраний протокол — нижче.

  **ПРОТОКОЛ CLAIM (обрано власником, 2026-07) — двофлаговий mutex у стилі Пітерсона.**
  Дві мітки: `.attempted-commit` (прапорець commit, НОВА) і `.attempted` (прапорець
  drain — наявна мітка `markAttempted`, ставиться на старті обробки батча).

  *Commit (за ввімкненої консолідації):*
    1. Заходить в **останній** каталог push_queue і **беззастережно** ставить там
       `.attempted-commit`.
    2. Перевіряє `.attempted` (drain). **Є** → забирає свій `.attempted-commit` і робить
       **новий** каталог (append).
    3. **Нема** `.attempted` → **консолідує** в цей каталог і по завершенні **видаляє**
       `.attempted-commit`. (Лишений після краху `.attempted-commit` = сигнал для
       recovery-on-startup — видалити цей останній каталог і запустити commit ще раз — **ідемпотентно**.)
    4. *(Drain)* заходить у каталог, шукає `.attempted-commit`. **Нема** → ставить свій
       `.attempted`, **трішечки чекає**, **перечитує** `.attempted-commit`: усе ще нема →
       батч можна обробляти. З'явився → цикл-таймаут (напр. 300 мс; через 5 с —
       попередження «commit не може бути таким довгим») і чекає зникнення. Можливо якщо таке трапилось, допоможе тільки
       перевантаження плагіну — буде видалення останнього коміту і його перезапуск. УСІ ці дії мають чітко відображатись
       в логах, щоб такі помилки можна було відстежити.
    5. Коли commit створює **новий** каталог (append), він так само одразу ставить туди
       `.attempted-commit` і знімає **після** повного запису batch-data → drain тим самим
       механізмом чекає на завершення запису в цей напівдописаний новий каталог щоб включити у свій цикл.

  **Чому коректно (перевірено по чергуваннях):** повна властивість Пітерсона
  (обидва ставлять свій прапорець ПЕРЕД вирішальною перевіркою чужого: commit
  set→check; drain set→**recheck**). Lost-update неможливий: щоб commit
  консолідував, на його перевірці `.attempted` відсутній (drain ще не claim-нув); тоді
  `.attempted-commit` присутній весь час консолідації, тож drain на перечитуванні або
  бачить його (чекає), або бачить, що commit **уже завершив** (читає готовий
  вміст) — у жодному разі не пише в каталог, що drain читає. Deadlock неможливий:
  commit ніколи не блокується (відступ = новий каталог), а `.attempted-commit`
  завжди знімається (крок 2 або 3). Однопотоковість (чергування лише на `await`
  одного рантайму, локальна ФС) робить мітки надійними.

  **Краї (не ламають протокол, але потрібні):** (i) crash-recovery через лишений
  `.attempted-commit` має **завершити/переробити** commit ідемпотентно; (ii)
  exists-guard у commit після кроку 1 на випадок «drain уже `rmdir`-нув останній
  каталог»; (iii) «трішечки чекати» — це liveness, safety дає сам факт
  перечитування; (iv) drain-івським прапорцем у протоколі взяти саме наявний
  `markAttempted`/`.attempted`, а не плодити другу мітку drain, щоб не було двох
  різних прапорців drain. (Тестується T4.1/T4.4/T4.5 — розділ 7.)

  **НАСЛІДОК — batch-дир записи лишаються ПЛОСКИМИ (без tmp+rename).** Оскільки
  recovery зносить каталог з лишеним `.attempted-commit` і переробляє commit з нуля,
  торнутий/напівдописаний файл усередині ніколи не використається → **per-file
  атомарність там зайва**. Перевірено (2026-07): зараз `copyFileFromVault`
  (`push-queue.ts:630/633`) і так пише плоско (`adapter.write`/`writeBinary`) — тобто
  знижувати нема чого, вимога вже мінімальна. АЛЕ цим самим закриваємо **поточну
  діру**: сьогодні commit-крах посеред `enqueue` лишає побитий каталог **без**
  discard (мітки `.in-progress`/`.attempted` ставить лише drain у `processBatch`,
  `sync2-manager.ts:3476/3489`, а не commit; recovery для batch-дир немає). Новий
  `.attempted-commit` + delete-and-restart це лікує. `[I5]`

  > ### ⚠️ ВІДКРИТА ПРОГАЛИНА R3b — drain теж БУВАЄ appender (Phase B)!
  >
  > Протокол вище й доказ Пітерсона припускають РІВНО ДВІ ролі: commit = **єдиний**
  > appender у хвіст черги; drain = claimer найстарішого каталогу. Але
  > conflict-resolution ламає це припущення: **Phase B** drain-у
  > (`synthesizeResolutionSideBatches` → `enqueueSynthetic`,
  > `sync2-manager.ts:2762/3116`) робить **сам drain третьою роллю — appender-ом у
  > push_queue ПОСЕРЕД drain** (синтетичні side-batch-і резолюції). Тоді Пітерсон
  > «один appender» більше не покриває ситуацію:
  > - хто ставить `.attempted-commit` (чи інший маркер) на СИНТЕТИЧНИЙ каталог?
  > - що заважає коалесційованому commit-у (`mergeIntoLatestPending` /
      > `allocateUniqueId`) гоняти з синтетичним записом drain-у в той самий момент?
  >
  > **Це змінює R3b (не лише нову главу §8):** протокол claim треба переписати на
  > модель «≥2 appender-и + 1 claimer», або синтетичні батчі мусять іти окремим
  > неконкурентним шляхом. Детальніше — §8 (розв'язання конфліктів) + її підрозділ
  > «взаємодія з §6». Тест — T4.6 (див. §7).
- **R4 (з I6).** Усі ретраї/бекофи обмежені; недосяжна збіжність = чистий вихід зі
  збереженням стану, крутилка спиняється.
- **R5 (з I1, §40/§26).** Зберегти семантику, «що потрапляє в наступний коміт»:
  повна історія змін «як є», дедуп проти найновішої версії у черзі, tracked-конфлікт
  vs своя гілка.
- **R6 (сумісність з §7.10).** Зберегти захист від eventually-consistent READ
  (монотонний guard) — інакше воскресне «власні дані як конфлікт». Chaining як
  ОПТИМІЗАЦІЯ допустимий, але не ціною R1.

**Відкрите питання масштабу:** гейт тестів (розділ 7) на ПОТОЧНому коді покаже,
чи «per-batch-pull + guard» уже задовольняє весь контракт. Якщо так — розділ 3
стає реструктуризацією, а не переписуванням з нуля. **Не фіксуємо максимальний
обсяг, доки не існує контракт-тестів.**

## 8. Розв'язання конфліктів у drain (детально, простою мовою)

> Прочитано з КОДУ (Explore-агент, 2026-07) + звірено зі специфікацією
> `docs/PSEUDO-MERGE-MODE.md` §4–8. Де код і спека розходяться — позначено.
> Ця глава ОПИСОВА (як §3/§4/§5). Підрозділ 8.7 «взаємодія з §6» — це ВІДКРИТІ
> ПИТАННЯ для власника, а не рішення.

### 8.0. Навіщо ця глава

Наші зміни §6 (відновити per-batch pull заради дефекту A + бар'єр commit↔drain)
**не самодостатні**: вони напряму зачіпають механізм конфліктів. Головне —
per-batch pull означає, що `reconcileBatchAgainstHead` спрацьовує ЧАСТІШЕ, а це
рівно та функція, що реєструє конфлікти. Тож перш ніж чіпати pull/push, треба
розуміти всю машину конфліктів. Ось вона.

### 8.1. Велика картина — три «поверхи»

Конфлікт живе одночасно у трьох місцях:

1. **У vault (те, що бачить користувач)** — оригінальний файл `idea.md` (наша
   версія, НЕ чіпається) + **sibling-файл** поруч
   `idea.conflict-from-<пристрій>-<час>.md` (чужа версія). Користувач вирішує
   звичайними файловими операціями: видалити sibling / перейменувати sibling поверх
   оригіналу / зхендмерджити руками.
2. **На GitHub (щоб нічого не втратити)** — приватна **conflict-branch**
   `github-easy-sync-conflicts-<пристрій>-<час>`, куди йде НАША версія (і всі
   подальші правки, поки триває конфлікт). `main` не бачить нашої версії, доки ми
   не завершимо.
3. **У сховищі записів (`conflict-store`)** — один `ConflictRecord` на кожен
   sibling: `kind`, `oursBlobSha`, `theirsBlobSha`, base-кеш, шлях sibling-а.

Поки існує хоч один запис — шлях «у конфлікті».

### 8.2. Коли конфлікт НАРОДЖУЄТЬСЯ — auto-merge gate

Будь-яка розбіжність спершу проходить **ворота auto-merge**
(`reconcileBatchAgainstHead`, `sync2-manager.ts:3908-4251`, і той самий gate на
pull-стороні `applyRemoteAddOrModify`). Порівнюються три SHA — **base** (спільний
предок), **ours** (наша), **theirs** (на сервері):

| випадок           | що робить                                                    |
|-------------------|--------------------------------------------------------------|
| base==theirs      | сервер не чіпали → пушимо наше чисто                         |
| ours==theirs      | однакові → нічого не пушимо                                  |
| ours==base        | ми не міняли, сервер міняв → беремо theirs (атомарно)        |
| **усі три різні** | **справжня 3-стороння розбіжність** → пробуємо 3-way merge ↓ |

**3-way merge** (`three-way-merge.ts:23-44`, бібліотека `node-diff3`,
`excludeFalseConflicts:true`):

- **чисто** (правки не перетинаються) → змерджені байти йдуть на GitHub, користувач
  НІЧОГО не бачить (конфлікту не було по суті);
- **конфлікт** (перетин рядків) → **реєструємо конфлікт** (8.3);
- **розмір > 1 МБ** (`RECONCILE_AUTO_MERGE_LIMIT`, дефолт `maxAutoMergeSizeBytes`) →
  merge ПРОПУСКАЄТЬСЯ, наше пушиться as-is (node-diff3 ~85с на 4.6МБ на mobile).
  ⚠️ **Цей size-cap Є лише на push-стороні; на pull-стороні його НЕМА** (Explore
  ambiguity #2) — див. 8.7.

#### 8.2.1 ⚠️ Merge НЕ зберігає закінчення рядків — і це ламає байтову еквівалентність гілок

Знайдено 2026-08-09 при перевірці тези «чи завжди `diff3(A, B, A) == B`». Відповідь:
**семантично так, побайтово ні** — і другий бік має наслідки для SHA-first.

**Механізм** (`three-way-merge.ts:31-38`):

```ts
diff3Merge(ours, base, theirs, { stringSeparator: /\r?\n/ })  // ← закінчення рядків СТЕРТО
const sep = pickSeparator(ours, base, theirs);                 // ← CRLF, якщо він є в БУДЬ-ЯКОМУ вході
const joined = result.result.join(sep);                        // ← ОДИН роздільник на весь файл
```

Розбиття знищує оригінальні закінчення, зшивання ставить один роздільник, а
`pickSeparator` сканує **всі три** входи. Отже **старий `base` або чужий `theirs` може
нав'язати CRLF нашому LF-файлу**. Це навмисне («Windows-edited files preserve their
style»), але коментар у коді описує лише намір, не цей побічний ефект.

**Заміряно** на справжній обгортці (`node-diff3`, `excludeFalseConflicts:true`), 8
випадків `diff3(A, B, A)`: у **всіх** `conflict === false` і вміст рядків **завжди**
дорівнює `B`; побайтово збіглося **6 із 8**. Обидва промахи — суто закінчення рядків:

| випадок | `B` | результат |
|---|---|---|
| `A` має CRLF, `B` має LF | `"x\nz\n"` | `"x\r\nz\r\n"` |
| `B` зі змішаними закінченнями | `"x\r\nz\n"` | `"x\r\nz\r\n"` |

Відтворити: обгортка `mergeText` + `merge` з `node-diff3`, виклик `mergeText(B, A, A)`.

**Наслідок 1 — merge може перевернути закінчення локального файлу.** LF-ний файл
користувача після злиття поїде на сервер як CRLF, якщо CRLF був у базі або в чужій
версії. Окремого застереження про це в доках не було.

**Наслідок 2 — і він важливіший: short-circuit і виконаний merge НЕ дають однакових
байтів.** Гілка `base==theirs` пушить `ours` **дослівно**; той самий випадок, пропущений
крізь merge, віддав би `ours` із закінченнями, продиктованими `base`. Різні байти →
**різний blob SHA** → різний коміт. А оскільки в новому алгоритмі все прив'язане до SHA
(`baselineSha`, file-cache, детекція змін), неоднозначність тут коштує дорого.

➡️ **Правило для нового алгоритму:** short-circuit `SHA(theirs) == SHA(base) → пушимо
`ours` як є` — **НОРМАТИВНИЙ, а не оптимізація**. merge для цієї трійки не запускається
взагалі. Тоді два шляхи до одного результату не існують за побудовою, і питання «які
байти канонічні» не виникає.

**Роди конфлікту** (спека §5). **УВАГА: delete×modify — це ДВА РІЗНІ, ПРОТИЛЕЖНІ
випадки** (напрям вирішує все):

- **modify-vs-modify** — обидва правили → 3-way, при перетині sibling;
- **local:delete × remote:modify → КОНФЛІКТ `delete-vs-modify`** (реєструється!):
  ми видалили, сервер правив → sibling з theirs, `oursBlobSha:null`; користувач
  вирішує (видалити sibling = delete перемагає / перейменувати sibling = modify
  перемагає). Код: `sync2-manager.ts:2052`.
- **local:modify × remote:delete → АВТО «modify-wins»** (НЕ реєструється): сервер
  видалив, ми правили → `theirs===null` → файл ВОСКРЕСАЄ на repo. Код:
  `conflict-detection.ts:146-148`. (Логіка: наша правка — свіжіший, свідоміший
  сигнал, ніж старе видалення.)
- **бінарник** — merge не пробується взагалі → завжди sibling;
- **plugin-dir файл (§28)** — атомарна semver-резолюція, **НІКОЛИ** не sibling
  (інакше half-merged bundle кладе плагін); навіть local:delete×remote:modify тут
  → modify-wins, без sibling (`sync2-manager.ts:2043`).

### 8.3. Реєстрація конфлікту — три записи одночасно

`registerConflictAndDropPath` (`sync2-manager.ts:2519-2591`) робить ТРИ речі:

1. **Пише sibling у vault** (`conflict-store.ts:253-310`) — крок-tmp+meta+rename
   (тут атомарність Є, бо це видимий користувачу файл): у sibling ідуть **theirs**
   байти; оригінал не чіпається. Ім'я:
   `<stem>.conflict-from-<deviceLabel>-<isoTs>.<ext>`.
2. **Пушить НАШУ версію на conflict-branch** (`pushConflictPathsToBranch`,
   `2625-2747`): гілка **лениво створюється** на першій реєстрації сесії (base =
   поточний main HEAD); кожна реєстрація додає коміт «conflict (<пристрій>)». Дерево
   гілки завжди rebase-forward (`base_tree = main.tree`), щоб фінальний merge був
   тривіальний.
3. **Викидає шлях із черги** (з поточного + усіх пізніших батчів) — щоб main-side
   push не залив стару «ours»; вона тепер живе на гілці.

### 8.4. Хто РОЗВ'ЯЗУЄ — дві фази на СТАРТІ drain (не в циклі!)

Резолюція запускається **рівно раз** на початку drain (`sync2-manager.ts:3087-3117`),
НЕ в push-циклі:

- **Тригер (подія, read-only):** `ConflictWatcher` (`conflict-watcher.ts`) слухає
  `vault.on('delete'|'modify'|'rename')`; якщо чіпнули base або sibling — лише
  `counter.markDirty()`. Нічого не мутує. (Виняток з правила «двигун — це полінг»,
  див. memory.)
- **Phase A — `evaluateConflictState`** (`conflict-classifier.ts:108-253`): проходить
  записи (тільки якщо є записи + watcher каже «брудно»), для кожного дивиться sibling:

  | випадок | умова | рішення |
    |---|---|---|
  | 1 | sibling зник | **accept-ours** → викинути запис |
  | 2 | sibling є, base зник | noop (чекати) |
  | 3 | sibling==base (перейменували поверх) | **accept-theirs** → видалити sibling + викинути запис |
  | 4 | sibling≠base (частково) | noop (чекати) |

- **Phase B — `synthesizeResolutionSideBatches`** (`2762`, викл. з `3116`): для
  кожного шляху, де ВСІ записи зникли, `enqueueSynthetic({path, content, ...})` —
  кладе **синтетичний side-batch** у чергу. Далі `processBatch` пушить його на
  **main** звичайним комітом «resolve conflict (<пристрій>)».

### 8.5. Завершення — finalize-gate

Наприкінці drain (`finalizeConflictBranchIfReady`, `2823-2870`): **якщо store
порожній І conflict-branch існує** → ручний **merge-commit** на main
(`parents=[main.head, branch.head]`, `tree=main.tree` — зливає лише історію) →
`updateBranchHead` → `deleteReference` (мітку гілки прибрано, але коміти лишаються
досяжні через 2-го батька) → `lastSync` = merge-commit. Ідемпотентно (крах
самолікується re-finalize).

**Ключова властивість:** per-file резолюції публікуються на main як звичайні коміти
(по одному), а гілка живе всю сесію й зливається лише коли зник ОСТАННІЙ запис.

### 8.7. ⚠️ ВЗАЄМОДІЯ З §6 — ВІДКРИТІ ПИТАННЯ (не рішення!)

Ось де наші зміни §6 б'ються з машиною конфліктів. **Це список для обдумування,
свідомо без відповідей.**

1. **Per-batch pull → БІЛЬШЕ реєстрацій — це ЛІКУВАННЯ, не побічний ефект.**
   Важливо не переплутати: per-batch pull НЕ «виробляє» конфлікти. Конфлікт вимагає
   справжньої 3-сторонньої розбіжності (8.2, «усі три різні»); таймінг pull її не
   вигадує. Він лише міняє «виявити-й-показати» на «пропустити-й-затерти». Тобто
   ЗАРАЗ (дефект A) ті самі розбіжності **мовчки затираються** (G9); після фіксу
   вони стануть чесними sibling-ами. Це відновлення **I2**. **Вторинна ціна:**
   в сесіях активного паралельного редагування ЗРОСТЕ **обсяг** sibling-ів і комітів
   на conflict-branch. Це не баг — кожен зайвий sibling це реальний конфлікт, що
   сьогодні зникає. Але користувача варто попередити (UX-навантаження).

2. **⚠️ drain стає ТРЕТІМ appender-ом (Phase B) — ламає Пітерсона з R3b.**
   Наш протокол `.attempted-commit` (§6/R3b) моделює дві ролі: commit=appender,
   drain=claimer. Але Phase B (`enqueueSynthetic`) робить drain **appender-ом
   ПОСЕРЕД drain**. Питання: хто маркує синтетичний каталог? що заважає
   коалесційованому commit-у гоняти з `enqueueSynthetic` за `allocateUniqueId`?
   **→ протокол claim треба на модель «≥2 appender + 1 claimer».** (Продубльовано
   у §6/R3b як відкрита прогалина; тест T4.6.)

3. **⚠️ pull-side merge БЕЗ size-guard × частіший pull.** Per-batch pull ганяє
   pull-side merge ЧАСТІШЕ; а там немає 1 МБ-cap (push-side має). Отже >1 МБ файл,
   що конфліктує на pull, вішає головний потік — **частіше й на mobile**. Це удар по
   **I6 + mobile-обмеженнях**, не просто асиметрія. **→ pull-side теж потребує
   size-cap.** (Тест T6.5.)

4. **⚠️ finalize-gate × commit-during-drain.** «store порожній → merge+delete
   branch» (8.5) може вистрелити на ТРАНЗІЄНТНО порожньому store, поки
   коалесційований commit саме реєструє новий конфлікт → видалимо гілку, яка от-от
   знадобиться. Ймовірно самолікується (наступний drain створить нову гілку), але
   треба простежити — це наше вікно «commit під час drain», застосоване до
   conflict-стану. (Тест T6.6.)

5. **conflict-branch push читає RAW head (не guarded).** `pushConflictPathsToBranch`
   і finalize читають main head через `getBranchHeadSha` (raw), НЕ `getGuardedHead`
   (§7.10). Тобто монотонний guard там НЕ діє. Пом'якшення: гілка приватна
   (per-device) → контенція мінімальна, тож guard там значить менше. Але при нашому
   поверненні per-batch pull варто вирішити свідомо, а не лишати випадково. (T6.7.)

6. **Phase A пауза vault-подій × конкурентний commit.** `evaluateConflictState`
   на час свого проходу ставить `ConflictWatcher` на паузу. Наш commit-coalesce може
   крутитися паралельно — треба перевірити, чи commit посеред drain не збиває
   pause/resume sweep-у. (Відкрите; поки без окремого тесту — залежить від дизайну
   бар'єра.)

7. **History не бачить conflict-branch версій («петляння-вісімки»).** Наслідок пункту
   1: більше конфліктів → більше приватних conflict-branch-ів, кожна вливається в main
   TREESAME-merge-ом (`tree=main.tree`) → path-фільтр `listCommitsForPath` обрізає їх
   → in-conflict чернетки у History-UI **не видно** (лише магістраль main + push-queue).
   Це History-фіча, а не engine-баг; наші зміни її лише ПІДСИЛЮЮТЬ. Рекомендація —
   НЕ обходити DAG, а логувати conflict-branch-коміти у власні метадані (третє джерело
   History). **Повний розбір + продуктове питання «чи показувати чернетки» —
   `HISTORY-DELETED.md` §9 п.6.**

8. **History не слідує за rename (`git log --follow`).** Той самий корінь, що п.7 —
   `?path=`-фільтр без `--follow`. На push ми rename не детектуємо (`delete+add`,
   полінг), тож History під новим ім'ям не бачить пре-rename історії. git-дані цілі —
   губить лише UI. **Повний розбір + можливі шляхи (client-side реконструкція vs
   push-side rename-провенанс) — `HISTORY-DELETED.md` §9 п.7.**

9. **⚠️ DRAIN-side crash-gap: `cascadeRebase` пише знімки ПЛОСКО, без маркера й
   integrity-verify.** Drain-аналог commit-side діри §6/R3b — але тут **НЕ покрито**.
   - **Що добре (переживає крах ЛОГІЧНО).** `cascadeRebase` персистить переграні
     знімки (`overwriteFile`) **ДО** будь-якого push (усередині `reconcileBatchAgainstHead`,
     перед `createCommit`/`updateBranchHead`). Тож крах ПІСЛЯ push частини батчів лишає
     решту на диску вже переграними; resume reconcile-ить кожен проти записаної голови
     → збіжність (I3). Повторний прогін ідемпотентний (`excludeFalseConflicts` робить
     повторне накладання `r` no-op-ом).
   - **⚠️ Що НЕ добре (фізичний запис).** `overwriteFile` = **плоский**
     `adapter.write`/`writeBinary` (`push-queue.ts`), БЕЗ tmp+rename і БЕЗ drain-маркера.
     Крах САМЕ під час цього запису → **торнутий знімок**. Жоден наявний механізм його
     не ловить:
     - `uploadedBlobs` — кеш «не заливай двічі» (post-upload); на cascade ПОРОЖНІЙ →
       не рятує;
     - `computeGitBlobSHA` рахує SHA **наявних** байтів, **нема з чим звіряти** (per-file
       expected-SHA у meta немає);
     - `recoverPushInflight` — про head/ref, не про вміст знімка;
     - `AtomicWriteRecovery` (`.sync-tmp`) — тільки VAULT-записи, НЕ push-queue.
   - **Наслідок:** resume бере торнутий знімок → fast-path (Case 3, `expectedHead==
     currentHead`) пушить його **як є** → псування (I1/I5). Гірший підвипадок: знімок
     відкотився до оригіналу (без `r`) → fast-path затер чужу зміну `r` (сімейка G9,
     через крах).
   - **Фікс-кандидати (не вирішувати зараз):** атомарний `overwriteFile` (tmp+rename)
     АБО drain-маркер на час перезапису + SHA-verify знімка перед fast-path push. Той
     самий патерн, що `.attempted-commit` дає commit-стороні.
   - **Застереження:** доведено МІРКУВАННЯМ по вікну краху, не червоним тестом. Оракул —
     crash-тести T4.7/T4.8 (§7). Якщо тест покаже захист, якого я не побачив — впаду назад.

10. **💡 ВІДКРИТА ІДЕЯ — safe-supersede sibling-ів (зменшити захаращення).** Не баг, а
    можлива оптимізація; актуальна бо per-batch pull → більше конфліктів → більше
    sibling-ів.
    - **Що є зараз:** дедуп ЛИШЕ за точним вмістом — `findDuplicate` +
      `findOrphanSibling` по парі `(vaultPath, theirsBlobSha)` (`conflict-store.ts`).
      Ідентичне чуже → один sibling. Інший `theirsBlobSha` (навіть на байт) → **новий**
      sibling; старий НЕ заміщається.
    - **Ідея:** якщо нова чужа версія V2 **строго походить** від старої V1 (V1 —
      предок V2) **того самого пристрою** → V1-sibling надлишковий → замістити його V2
      (drop старий). Менше захаращення без втрати (V1 досяжний з V2 в історії пристрою).
    - **⚠️ Застереження — НАЇВНИЙ diff між sibling-ами НЕБЕЗПЕЧНИЙ.** За схожістю
      вмісту НЕ можна відрізнити «нащадка» від «незалежного розходження»: sibling-и
      часто з РІЗНИХ пристроїв (V1 від P, V2 від Q — дві незалежні версії). Здифати й
      викинути старий → **втрата реальної версії** (I1 / §4.4). Багато-sibling з різних
      пристроїв — навмисна фіча (§4.2).
    - **Безпечна умова:** треба **ancestry**, не diff. Тобто (1) зберігати в записі
      remote **commit-SHA** (не лише blob-SHA); (2) на новий sibling — `compare`-перевірка
      «новий коміт є нащадком старого ТОГО САМОГО пристрою» (1 API-виклик); (3) лише
      тоді — замістити. Потребує додаткового lineage-трекінгу. Наївний шлях — заборонено.

### 8.8. Послідовні remote-версії файлу в конфлікті — FOLD замість піл-апу

> Конкретизація ідеї §8.7 п.10 (safe-supersede) для випадку «той самий файл, той
> самий пристрій, кілька remote-версій підряд, поки триває конфлікт». Ідея власника
> (2026-07). **Відкрите — потребує UX-рішення (8.8.6) + тестів.**

#### 8.8.1. Контекст — конфлікт живе ДОВГО, дві незалежні доріжки

Файл може бути в конфлікті **як завгодно довго** (§7 спеки). Поки він у конфлікті,
розходяться **дві окремі доріжки**:
- **Наша (ours):** усі наші локальні правки цього файлу йдуть НЕ на main, а на
  **conflict-branch** (split-push), поки НЕ вирішено ВСІ конфлікти сесії (тоді merge).
- **Чужа (theirs):** інший пристрій тим часом може пушити на main **нові** версії
  того файлу — R0 → R1 → R2… Кожна — новий вміст на main.

Це 8.8 — **лише про доріжку theirs** (як тримати sibling актуальним). Доріжку ours
(conflict-branch) вона не чіпає.

#### 8.8.2. Проблема — піл-ап sibling-ів

Зараз дедуп лише за точним вмістом (`theirsBlobSha`). Кожна НОВА remote-версія
(інший SHA) → **новий sibling**. За довгий конфлікт з активним іншим пристроєм це
дає стос `A.conflict-from-*` файлів, хоча всі — послідовні версії одного джерела.

#### 8.8.3. Розв'язок — FOLD через ЛАНЦЮЖКОВИЙ diff3

Коли для вже-конфліктного шляху прилітає нова remote-версія R1 **від того самого
джерела**:

1. **Ancestry-guard (обов'язково ПЕРШИМ).** R1 — це нащадок поточної збереженої
   remote-бази R0 **того самого пристрою**? (перевірка через збережений remote
   commit-SHA + `compare`/ancestry). **Ні** → це незалежне розходження (інший девайс)
   → **новий sibling** (навмисна багато-sibling-фіча §4.2), fold НЕ застосовуємо.
2. **Так** → 3-way fold:
   ```
   BASE   = R0   (remote-версія, з якої народжено sibling; докачати getBlob)
   OURS   = S    (ПОТОЧНИЙ sibling на диску — уже з правками користувача!)
   THEIRS = R1   (нова remote-версія)
   diff3(BASE, OURS, THEIRS)
   ```
   - **clean** → замінити вміст sibling-а на merged; **старий sibling не плодимо**;
   - **conflict** → додати **новий** sibling для R1 (і тільки тоді).
3. **Chaining бази (на УСПІХ І НА НЕВДАЧУ):** збережена remote-база просувається
   R0 → R1. Наступна версія R2 порівнюється вже з базою **R1**, не R0.

#### 8.8.4. Чому BASE=R0 коректний

R0 — справжній спільний предок обох сторін, бо обидві від нього походять:
`S = R0 + правки-користувача-в-siblingʼі`; `R1 = R0 + нові-remote-правки` (R1 нащадок
R0 того ж пристрою — гарантовано кроком 8.8.3.1). Тож `diff3(R0, S, R1)` — це merge зі
справжнім merge-base. `OURS = поточний sibling на диску` — правильно ловить те, що
користувач уже наробив у siblingʼі.

#### 8.8.5. Доступність R0 — надійна (виправлення попередньої помилки)

R0 — вміст `A.md` на історичному коміті `C_R0` на **main**. main append-only →
`C_R0` не зникає → його дерево закріплює blob R0 → `getBlob(R0)` працює **нескінченно**
у підтримуваних сценаріях. Тобто BASE майже завжди доступний. Розрізняти:
- **offline / 5xx** → R0 на місці, просто зараз недоступний → **ВІДКЛАСТИ** на
  наступний sync (НЕ плодити sibling!);
- **справжній 404** (R0 реально зник) → лише force-push/rewrite main = **out-of-scope**
  (§7.10 «append-only assumption») → тоді новий sibling як belt-and-suspenders.

(NB: `safeFetchContents` зараз зливає offline і 404 в один `null` — для fold це треба
розрізняти, інакше offline дасть зайвий sibling.)

#### 8.8.6. Що зберігати + ⚠️ UX-рішення власника (ще НЕ вирішено)

**Зберігати:** `theirsBlobSha` (ВЖЕ Є — оновлювати на кожен fold) + remote **commit-SHA**
(нове, для ancestry).

**UX-питання (твій вибір, не технічний):**
- **Rug-pull:** користувач АКТИВНО зводить S до `A.md`; авто-fold міняє sibling
  «під руками». Може дезорієнтувати.
- **Повернення відкинутого:** якщо в S видалено theirs-рядки, а R1 їх знову вносить —
  fold частково скасовує роботу відкидання.
- **Виграш лише на успіху:** кількість падає, тільки коли fold вдався; на конфлікті —
  знову два файли.
- **Можливий компроміс:** робити fold **ЛИШЕ коли sibling ще не чіпали** (`S == R0`);
  якщо чіпали — не чіпати автоматично (додати новий sibling). Безпечніше для UX,
  дешевше в реалізації.

**Заборонено:** fold без ancestry-guard (8.8.3.1) — інакше злиття з базою від чужого
пристрою дасть сміття (та сама засторога, що §8.7 п.10: **ancestry, не наївний diff**).

## 10. Майбутнє: ланцюжковий cascade-rebase (rolling base) — НЕ для цього циклу

> Ідея власника (2026-07). **ПІДНЯТО** з «майбутнє» до **провідного кандидата на новий
> алгоритм**: парадигма crash-атомарності (I7) вирішує «зірка vs ланцюг» на користь
> ланцюга. Стосується `cascadeRebase` (`sync2-manager.ts:4440`), розібраного у §8.

### 10.0. Парадигма I7 ВИРІШУЄ на користь ланцюга — і прибирає crash-gap як клас

Раніше (10.3) ланцюг обґрунтовувався лише «менше false-conflict». Парадигма I7
(«очікуємо крах після/під час кожного батча») дає **сильніший, вирішальний** аргумент:

- **«Зірка» МУСИТЬ наперед-переписати знімки C2,C3** (`overwriteFile` у `cascadeRebase`)
  — саме цей плоский запис торниться при краху (§8.7 п.9 / T4.8).
- **«Ланцюг» reconcile-ить кожен батч у свою чергу, зливає В ПАМ'ЯТІ → `createBlob` →
  push.** Знімок на диску лише ЧИТАЄТЬСЯ, ніколи не переписується наперед. **Немає
  `overwriteFile` → торнутий-знімок зникає ЯК КЛАС.** Парадигма не «обирає» ланцюг —
  вона видаляє машинерію, що породжує gap.

**Уніфікація:** R1 (per-batch pull, дефект A) + ланцюг + I7 — це ОДИН алгоритм:
```
для кожного батча (найстаріший першим):
  head = getGuardedHead()                       # §7.10 guard проти replica-lag
  if head == база_батча:  push як є (fast, нема remote-руху)
  else:                    reconcile(base=власна база батча, theirs=head) → merge в пам'яті
  push → record head → видалити батч з черги      # <- crash-safe точка
```
«Зірка» була МЕРЕЖЕВОЮ оптимізацією, що (а) породила дефект A (fast-path на
ланцюжковій голові маскує remote-рух), (б) крихка на краху (наперед-обчислені знімки).

**Ціна ланцюга мала:** база спільна (всі батчі мають `parentCommitSha=BASE`) →
фетчиться раз; `theirs` для наступного = те, що щойно запушили (в пам'яті); реальний
фетч лише коли справді прилетіла нова remote-зміна. «Зайва мережа» = дешеві guarded
head-reads на батч — а це і є те, що ловить G9. Турбота про погану мережу дотримана.

### 10.1. Що робить ПОТОЧНИЙ cascade — «зірка»

Після розв'язання C1 (base=BASE, ours=C1, theirs=R1 → D) кожен пізніший батч
переграється **від тієї самої точки** `(C1_pre, D)`:
```
C2:  diff3(base=C1_pre, ours=C2, theirs=D)          → D2
C3:  diff3(base=C1_pre, ours=C3, theirs=D)          → D3   ← той самий base=C1, theirs=D!
```
Тобто «зірка»: усі пізніші від одного пивота C1→D.

### 10.2. Пропозиція — «ланцюг» (rolling base)

Переграти кожен від **безпосередньо попереднього** розв'язаного стану:
```
C2:  diff3(base=C1_pre, ours=C2, theirs=D)          → D2
C3:  diff3(base=C2_pre, ours=C3, theirs=D2)          → D3   ← base=C2, theirs=D2!
```
Це **підручниковий послідовний rebase** (як `git rebase` реально переграє коміт за
комітом). Реалізаційно — **той самий один прохід**, лише з **кочівною** парою
`(oldOurs, newOurs)`: після переграшу C2 оновити `oldOurs := C2_pre`,
`newOurs := D2`, і C3 бере вже їх. Не дорожче за зірку.

### 10.3. Ланцюг ≡ зірка за ЯКІСТЮ merge — ЕМПІРИЧНО доведено (гіпотезу спростовано)

> **Виправлення попередньої позиції.** Раніше я припускав, що ланцюг «надійніший /
> менше хибних конфліктів» (менша diff-поверхня). **Це спростовано прогоном на
> РЕАЛЬНОМУ `node-diff3`** (`scratchpad/chain-vs-star.ts`, 2026-07, 4 кейси).

| кейс | CHAIN | STAR | |
|---|---|---|---|
| рознесені зміни (3 коміти + remote) | ✅ вірний | ✅ вірний | ідентично |
| **реверт** (X: base→A→B→base) | ✅ вірний | ✅ вірний | ідентично |
| суміжні рядки (без якоря між) | конфлікт | конфлікт | ідентично |
| ті самі + 1 якір між змінами | ✅ | ✅ | ідентично |

**Висновок:** ланцюг і зірка дають **однаковий** результат у ВСІХ кейсах, включно з
реверт-випадком і суміжним. Конфлікт на суміжних рядках — це консервативність
**самого node-diff3** (порядковий merge без незмінного роздільника зливає сусідні
зміни в один хунк), і вона б'є **обидві** стратегії однаково; один якір-рядок між
змінами прибирає її теж для обох.

**Отже «якість merge» — НЕ аргумент за ланцюг.** Ланцюг обираємо ВИКЛЮЧНО через
**I7 / crash-атомарність** (§10.0): він прибирає `overwriteFile`-торн-знімок (§8.7
п.9). Це самостійний, доведений аргумент; «менше хибних конфліктів» — відкинуто як
непідтверджене. (Диференційні тести §10.5 тепер мають підтвердити РІВНІСТЬ на ширшій
вибірці, а не шукати перевагу ланцюга.)

### 10.4. Два варіанти «ланцюга» — обираємо (B)

Важливо не сплутати:
- **(A) ланцюг-усередині-cascade:** лишити наперед-обчислення (`overwriteFile`), лише
  змінити базу на кочівну. Crash-профіль ТОЙ САМИЙ, що зірка (торнутий-знімок лишається).
- **(B) ланцюг-як-per-batch (парадигма I7, §10.0):** ВІДМОВИТИСЬ від cascade зовсім;
  кожен батч reconcile-иться у свою чергу проти живої голови, злиття В ПАМ'ЯТІ →
  push. **Немає `overwriteFile` → торнутий-знімок зникає** (§8.7 п.9 / T4.8).

**Обираємо (B).** Саме вона реалізує I7 і прибирає gap; (A) — ні.

### 10.5. Застереження (дисципліна лишається)

- **Це ЗМІНА АРХІТЕКТУРИ (crash-профіль), не якості merge.** За результатом (вмістом)
  ланцюг≡зірка (§10.3), тож «переписати заради кращого merge» — НЕ підстава. Підстава —
  I7 (прибрати `overwriteFile`-торн-знімок). Дисципліна CLAUDE.md: це зміна поведінки
  на краху → лише з crash-тестами (T4.7/T4.8), не мимохідь.
- **Диференційні тести підтверджують РІВНІСТЬ (не шукають перевагу).** Розширити T3.5
  (§7) на ширшу вибірку «зірка vs ланцюг» (реверт, суміжні, багатослотні) → зафіксувати,
  що вміст ідентичний. Якщо десь РОЗІЙДУТЬСЯ — це нова інформація, требе розібрати ДО
  переписування. (Стартова вибірка з 4 кейсів — `scratchpad/chain-vs-star.ts` — рівність
  показала.)
- **Мережа:** (B) вимагає guarded head-read на батч + фетч theirs лише при реальному
  remote-русі (§10.0). Треба ПЕРЕВІРИТИ на поганій мережі, що це не деградує UX (база
  кешується, theirs попереднього — в пам'яті).

**Диспозиція:** ланцюг-(B) — **провідний кандидат на новий алгоритм** (не «колись»),
бо його диктує I7 і він прибирає §8.7 п.9. Але рухати лише після диференційних тестів
(10.5) + гейту §7.10 (own-data-as-conflict + guard) — бо це серце модуля.

### 10.6. ЗАГАЛЬНА формула reconcile — base = parentCommitSha БАТЧА (не lastSync!)

> Виведено + доведено на реальному node-diff3 (`scratchpad/second-round.ts`, 2026-07).
> Відповідає на «а якою буде формула для 2-го раунду (нові C4 + R4 після каскаду)».

**Немає окремих «remote-раундів» і «local-раундів».** Одне правило на КОЖЕН батч:
```
base   = parentCommitSha ЦЬОГО батча   (= lastSync у момент його локального коміту)
ours   = сам батч (кумулятивний знімок)
theirs = ЖИВА голова сервера зараз
D      = diff3(base, ours, theirs) → push → lastSync = D
```

**Чому не lastSync поточний, а parentCommitSha батча:**
- **C1,C2,C3** закомічені ДО пушу → усі мають `parent=BASE`. Коли їх пушать після руху
  голови — база кожного це BASE (або кочівна C_{n-1} для мінімальної diff-поверхні,
  §10.2). Каскад — саме цей випадок.
- **C4** закомічений ПІСЛЯ того, як `lastSync` став D3 → його `parent=D3` **з коробки**.
  Тому 2-й раунд — простий ОДИН крок: `diff3(base=D3, ours=C4, theirs=R4)=D3+c4+r4`.
  D3 — новий спільний предок (обидві сторони від нього походять: ми — бо vault=D3 після
  write-back; інший пристрій — бо підтягнув main=D3).

**Двоступенева спроба (base=R1 / base=C3) — надлишкова.** Емпірично дає той самий
результат, але лише завдяки `excludeFalseConflicts` (повторно накладені c1..c3,r1
згортаються). «Важкий шлях» до того, що `parentCommitSha` дає безкоштовно.

**⚠️ ІНВАРІАНТ-передумова (I5-суміжне): merge-результат МУСИТЬ писатись назад у vault.**
Підтверджено `sync2-manager.ts:4211-4212` (`overwriteFile` snapshot + `writeRemoteText`
vault). Якби vault лишався C3 (без write-back), наступний C4=C3+c4 виглядав би як
**скасування r1** → тиха втрата чужої зміни. Тобто write-back не деталь, а умова
коректності формули base=parent. **Тест:** двораундовий (каскад → новий C4+R4 →
перевірити, що r1 не скасовано) — додати до T3.5.

### 10.7. CRASH-RESUME посеред ланцюга — base = persisted parentCommitSha (НЕ lastSync!)

> Доведено на реальному node-diff3 (`scratchpad/crash-resume.ts`, 2026-07): крах на
> C3 (C1,C2 запушені → server=D2, lastSync=D2, C3 у черзі), два сценарії появи R4.

**Модель:** кочівна база ланцюга (`C_{n-1}`) — IN-MEMORY, гине при краху. Персистується
лише `parentCommitSha` кожного батча (=BASE для C1,C2,C3, закомічених до пушу) + lastSync
+ черга + vault. Тому **resume НЕ МОЖЕ відновити кочівну базу** — має rebuild з persisted.

**⚠️ ПАСТКА (доведена):** якщо resume візьме `base=lastSync=D2` → `diff3(base=D2,
ours=C3, theirs=D2)`: base==theirs → тривіально → результат=C3 (сирий, без r1) →
**push затирає r1** (баг класу G9 через крах). Тест TRAP це відтворив: `SR'`→`SR`.

**✅ ВИМОГА:** resume reconcile-ить кожен лишковий батч із `base = його persisted
parentCommitSha` (докачати вміст з GitHub через `getContentsAtRef(path, parentSha)`),
theirs = жива голова. Для C1..C3 це BASE + false-collapse спільних c1,c2. Це «зірка
від BASE» — і саме тому рівність зірка≡ланцюг (§10.3) є ПЕРЕДУМОВОЮ коректності resume,
не косметикою.

**🔑 УНІФІКАЦІЯ (доведено `scratchpad/uniform-base.ts`, 2026-07) — ВИКИДАЄМО кочівну
базу зовсім.** Якщо вести І in-flight, І resume з `base=parentCommitSha` (не з кочівної
`C_{n-1}`), то in-flight-C3 і resume-C3 — це **буквально той самий виклик**
`m(C3, parentCommitSha, liveHead)`. Отже:
- **restart ≡ resume ЛІТЕРАЛЬНО** — немає окремого коду відновлення, немає ефемерного
  стану; черга + persisted `parentCommitSha` описують геть усе.
- **Кочівна база (`C_{n-1}`) — червона оселедчина.** Тест показав: вона дає ТЕ САМЕ
  рішення clean/conflict, що й base=parentCommitSha (поверхня «лише-наші vs лише-чужі»
  однакова після false-collapse спільного префікса). Різниться лише ТЕКСТ
  конфлікт-маркерів — косметика (на конфлікті реєструємо sibling, марковане не пушимо).
  Тобто кочівна база не дає переваги → викидаємо заради уніфікації.
- **`parentCommitSha` НЕ треба зберігати окремо** — він кладеться при `enqueue`
  (`push-queue.ts` meta) і переживає крах. Жодного нового persisted-стану.

**Дії наприкінці КОЖНОГО батча (повний список):** (1) `record lastSync`; (2)
`delete батч із черги`; (3) push-inflight маркер навколо `updateRef→record` (§7.9,
єдина справді додаткова дія — для однієї неоднозначної межі «ліг чи ні»). Бази
зберігати НЕ треба.

**Happy-path без фетчу:** якщо `liveHead == батч.parentCommitSha` (remote не рухався)
→ fast push без merge/fetch. base/theirs фетчаться лише коли голова зрушила (BASE —
раз, кешується між батчами). Турбота про погану мережу дотримана.

**Збіжність (обидва доведені):**
- **R4 з'явився ПІЗНО** (при C4): resume-D3 = точно no-crash-D3; далі C4+R4 звичайно.
- **R4 з'явився РАНО** (голова вже E=D2+r4): C3 при resume вбирає r1 І r4 одним merge;
  фінал ідентичний. Різні проміжні кроки, той самий кінець (I3/I7).

**Тест:** T4.9 (§7) — крах на C3 × {R4 пізно, R4 рано} × перевірка «фінал == no-crash
І r1 не затерто». Плюс негативний під-кейс: resume з base=lastSync МУСИТЬ провалити
тест (охоронний оракул проти пастки).

## 11. Новий drain — принципи побудови

> Кристалізація рішень §6/§10 в один набір принципів, на яких будується новий
> `drain`. Кожен виведений з інваріантів (§2) і/або доведений емпірично (scratchpad-
> тести 2026-07). Це НЕ готовий код — це «конституція» алгоритму.

### П1. Транзакція = ОДИН БАТЧ, не весь drain

drain — це цикл над чергою, а не одна велика транзакція. Атомарна одиниця —
один батч: `createBlob* → createTree → createCommit → updateRef → record`. Немає
відкату, немає «проміжного стану drain». (§I7)

### П2. Черга — довговічний журнал незробленого

Успішно запушений батч **видаляється з черги**. Тому «залишок роботи» = «вміст
черги». Стан, потрібний для продовження, весь персистований: `lastSync` + `черга`
(кожен батч зі своїм `parentCommitSha`) + `vault`. Жодного in-memory стану, що
мусить пережити крах. (§I5, §I7)

### П3. 🔑 УНІФІКОВАНА БАЗА: `base = parentCommitSha БАТЧА` — завжди

> ### ⚠️⚠️ СПРОСТОВАНО (2026-07) — П3 і П4 зламані для same-line у ДЕФОЛТНІЙ конфігурації
> **Емпірично** (`scratchpad/same-line.ts` + PushQueue-юніт): коли кілька батчів того
> самого файлу мають спільний `parentCommitSha=BASE` і правлять ТОЙ САМИЙ рядок
> (наша послідовність v1→v2→v3), `base=BASE` дає **SELF-CONFLICT** `<<< v2 === v1 >>>`
> (і v1, і v2 ≠ BASE-ового v0). Абсурд — «конфлікт із самим собою».
>
> **Це ДЕФОЛТНИЙ шлях, не край:** `consolidateCommits` дефолт = **false**
> (`sync2-manager.ts:656`, preserve-all-commits §4.4). Перевірено: 4 `enqueue` того
> самого файлу без drain → **4 окремі батчі, усі parent=BASE** (з `true` — фолд у 1,
> але це не дефолт). Тобто same-line ланцюг зі спільним BASE — звичайна поведінка.
>
> **КОЧІВНА база `C_{n-1}` ПОТРІБНА** (дає чисто v2, бо відображає справжню
> content-lineage). Твердження нижче «кочівну викинуто — косметика» ХИБНЕ: воно вірне
> лише коли сусідні батчі правлять РІЗНІ рядки (false-collapse) або сконсолідовані.
>
> **Справжнє правило (advisor):** `base = справжній content-lineage родич батча`, НЕ
> `parentCommitSha`. Вони збігаються для окремих sync-ів (`parentCommitSha=D_{n-1}`,
> персистовано, працює) і **розходяться** для same-generation ланцюга, де
> `parentCommitSha=BASE` — **брехня** (вміст будувався на v1, не v0). Це і є весь баг.
>
> **П4 теж спростовано** (він спирався на П3): in-flight — кочівна база (чисто), але
> crash-resume має лише persisted `parentCommitSha=BASE` → self-conflict. Отже крах
> МІНЯЄ результат. restart ≢ resume для same-line.
>
> **Тяжкість (обмежує редизайн):** self-conflict → sibling, обидві версії збережені,
> **втрати немає** (I2 тримається). Абсурдний UX, не корупція.
>
> **НЕ вертатись до «зірки»** (pre-compute у майбутні батчі → воскрешає торн-знімок
> §8.7 п.9). **Кандидат (advisor, НЕ вердикт):** зберігати pre-merge знімок щойно
> запушеного батча як базу для наступного same-path батча → персистує кочівну базу
> БЕЗ pre-compute майбутніх (П6 цілий). Оцінити після тріажу.
>
> **Це найчистіший RED-контракт (§7):** закодувати, прогнати, дати тріажу визначити
> розмір фікса (§9-порядок). Решта §11 нижче — НЕ settled, доки цей тест не зелений.

Кожен батч reconcile-иться проти **власного persisted `parentCommitSha`**, НЕ проти
`lastSync` і НЕ проти ефемерної кочівної бази. Правило одне для кожного батча,
кожного drain:
```
head = getGuardedHead()
if head == батч.parentCommitSha:  push як є            # happy: без merge/fetch
else:  D = diff3(base=parentCommitSha, ours=батч, theirs=head); push D
```
- `parentCommitSha` кладеться при `enqueue` → **нового persisted-стану не треба** (§10.7).
- ⚠️ `base=lastSync` — ЗАБОРОНЕНО (пастка: `base==theirs` → затирає remote, §10.7 TRAP).
- Кочівну базу викинуто — вона давала те саме рішення clean/conflict, лише інший
  текст маркерів (косметика, §10.7 доведено `uniform-base.ts`).

### П4. restart ≡ resume — ЛІТЕРАЛЬНО один код

> ⚠️ **ПІД РЕВІЗІЄЮ разом із П3** (див. ⚠️-блок вище): для same-line ланцюга це НЕ
> тримається — in-flight використовує кочівну базу (чисто), а crash-resume має лише
> persisted `parentCommitSha=BASE` → self-conflict. Тобто крах МІНЯЄ результат.
> Вірно лише для different-line / consolidated / separate-drain випадків.

Бо база кожного батча персистована (П3), in-flight-обробка батча і crash-resume того
ж батча — **той самий виклик** `m(батч, parentCommitSha, liveHead)`. Немає окремого
recovery-коду для щасливого ланцюга. (§10.7)

### П5. Дії наприкінці КОЖНОГО батча (повний список)

1. `record lastSync` (новий head);
2. `delete батч із черги`;
3. **push-inflight маркер** навколо `updateRef→record` (§7.9) — ЄДИНА справді
   додаткова дія, для однієї неоднозначної межі «ліг чи ні». Бази зберігати НЕ треба.

### П6. Жодного наперед-обчислення майбутніх батчів

Не переписувати знімки лишкових батчів (`overwriteFile`) — це створює проміжний
стан «ні зроблено, ні ні» → торнутий знімок при краху (§8.7 п.9). Кожен батч
чіпається лише коли до нього дійшла черга. (§I7, §10.4-B)

### П7. Per-batch pull + монотонний guard (лікування дефекту A + сумісність §7.10)

Голова читається `getGuardedHead()` **перед кожним** батчем (§7.10 guard проти
replica-lag). Ніякого fast-path, що пропускає reconcile, коли `head ≠ parentCommitSha`.
Це прямо закриває G9 (§4.3) і зберігає захист «власні дані як конфлікт» (§I2, R1, R6).

### П8. Write-back merge → vault (умова коректності П3)

Злитий результат МУСИТЬ писатись і в snapshot, і в живий vault
(`sync2-manager.ts:4211-4212`). Інакше наступний локальний коміт, збудований на
застарілому vault, виглядатиме як скасування чужої зміни (§10.6). (§I5)

### П9. Merge-якість = node-diff3 як є (без ілюзій)

3-way merge має «сліпу пляму» суміжних рядків без незмінного роздільника (§10.3):
consecutive-зміни зливаються в один хунк → консервативний конфлікт. Це властивість
рушія, однакова для будь-якої стратегії бази. Не намагатись «перехитрити» —
конфлікт безпечний (sibling, не втрата). (§I2)

### П10. 422 = «м'який крах» одного батча → той самий per-batch retry

**Крах, 422 і нормальна обробка згортаються в ОДНУ операцію** — «взяти наступний батч
із черги, злити проти живої голови, запушити». Це наслідок П1–П4: черга-журнал робить
«перезапуск drain», «повтор батча» і «resume після краху» семантично **тотожними**.

422 «not a fast forward» = голова зрушилась між нашим read і updateRef. Наш коміт
збудований на застарілому батьку → **не можна** його запушити (force заборонено —
затре чуже). Обробка:
```
піймали 422 на C_n:
  head = getGuardedHead()                              # перечитати з guard (§7.10)!
  D_n' = diff3(base=parentCommitSha(C_n), ours=C_n, theirs=head)   # re-merge (та сама операція)
  push D_n'                                              # старий коміт-на-застарілому → dangling, GC
```
- **Ідемпотентно, без стану:** base=parentCommitSha не змінилась, ours=C_n у черзі,
  theirs=свіжа голова → це БУКВАЛЬНО нормальний per-batch крок, лише тригернутий 422.
- **Re-merge МОЖЕ дати конфлікт**, якого не було (чужа зміна перетнула шлях) — це
  правильно (I2, sibling), і йде нормальним шляхом.
- **⚠️ guarded re-read обов'язковий:** сирий `getBranchHeadSha` після 422 може віддати
  replica-lagged стару голову → знову застарілий батько → **вічний 422-цикл**.
- **⚠️ ОБМЕЖУВАЧ (I6):** guard + bounded retries (§7.10 `REF_STALE_MAX_RETRIES` + backoff).
  Не збіглося після cap → чистий вихід, наступний sync добіжить (I3).
- **Ефективність:** буквально re-entry всього drain (Phase A sweep + повний pull) на
  кожен 422 — марно; роблять ТІСНИЙ per-batch retry (та сама семантика, дешевше).
- Це вже існує (§7.10 422-retry), новий алгоритм ЗБЕРІГАЄ, але спрощує: викидає
  ефемерний `chainedHead` (база завжди parentCommitSha, П3). (§I2, §I6, §I7)

### П11. Жодних порожніх комітів — per-file byte-identical drop (ЗБЕРЕГТИ наявне)

Перед push результат треба звіряти з головою; якщо нічого не змінилось — **не пушити**
(інакше порожній коміт-шум у історії).

- **⚠️ GitHub API це НЕ ловить.** git-data plumbing (`POST /git/commits`) радо створює
  коміт із `tree == tree батька`; `updateRef` пересуне голову → порожній коміт. На API
  покладатись НЕ можна — guard на нас.
- **Уже реалізовано, на рівні ФАЙЛУ (тонше за «whole-D_n»):** reconcile Branch 2
  (`sync2-manager.ts:4050`, `oursSha === theirs.sha` → drop), Branch 3 (`:4064`,
  `ours === base` → theirs wins → drop), + empty-batch skip (`:3697`,
  `entries.length === 0` → пропустити createTree/Commit, delete батч).
- **Теорема (чому Branch 2+3 ДОСИТЬ):** «merge-результат == голова» ⟹ «ours == голова»
  (→Branch 2) АБО «ours == base» (→Branch 3). Тож навіть після 3-way (Branch 4)
  результат НЕ може дорівнювати голові — Branch 2 викинув би файл ще ДО merge.
- Покриває випадок власника: однакові версії файлу в сусідніх батчах (C_{n+1} бачить
  свій вміст уже в голові після push C_n → Branch 2 → drop).
- **Не порушує preserve-all-commits** ([[feedback-preserve-all-commits]]): порожній
  коміт не несе вмісту; той принцип — про незлиття ЗМІСТОВНИХ комітів, не про шум.
- **Вимога до нового алгоритму:** per-file byte-identical drop + empty-batch skip
  МУСЯТЬ лишитись; per-file (не whole-tree), бо в багатофайловому батчі пушимо лише
  змінені файли. Тест — T3.5 під-кейс: c_n == r (та сама зміна) → жодного порожнього
  коміту. (§I1)

> **Порядок реалізації** цих принципів — §9. Гейт — §7 (усі RED→GREEN, GREEN лишаються;
> плюс §7.10 own-data + guard). Оракули — scratchpad-тести → T3.5/T4.7/T4.8/T4.9.

## 12. Content-addressed blob-store замість копії дерева Vault у батчах

> **Рішення власника, 2026-08-16.** Змінює те, ЯК зберігається вміст батчів і завантажені
> з GitHub версії. НЕ змінює алгоритм drain — на нього посилається §11 і опис нового drain.
> Синтетичні батчі (§8, Phase B) у новій системі **скасовано**, тож відкрита прогалина R3b
> «drain теж appender» цим закривається окремо.

### 12.1 Модель зберігання

**Сьогодні:** кожен батч тримає файли як копію дерева Vault — `<batchDir>/vault/<path>`
(`copyFileFromVault`, `push-queue.ts:630/633`).

**Стає:** батч тримає **лише метадані** — на кожен шлях `{path, sha, size}`. ⚠️ `size`
обов'язковий, а не «на всяк випадок»: без нього двоступеневе порівняння (§12.9) не має з чим
звіряти розмір, і кожна перевірка деградує до повного хешування. Байти живуть в окремому
сховищі, іменованому за вмістом:

```
file_cache/{sha}        ← ім'я файлу = git blob SHA його вмісту
```

Одне сховище обслуговує **всі три сторони** merge-у: `ours` (вміст батча), `base` і
`theirs` (завантажені з GitHub). Отже окремих полів під base-blob / remote-blob не
потрібно — є `getBlobFromCache(sha)`, і якщо файл із такою назвою є, він одразу наш.

**Ім'я саме себе доводить:** `SHA(вміст) == назва файлу`. Жодних додаткових метаданих для
перевірки цілісності.

### 12.2 Що це дає — і чого НЕ дає

| випадок | виграш |
|---|---|
| **`ours` стає `theirs` для наступного батча** | **так, і це постійно** — після пушу батча N його вміст І Є віддалений вміст, отже `theirs` для N+1 уже в сховищі → **зникає мережевий запит** |
| revert до попереднього вмісту (`A→B→A`) | так — один blob замість двох копій |
| той самий вміст за різними шляхами (копія, rename) | так |
| **послідовне редагування `v1→v2→…→v17`** | **НІ** — 17 різних вмістів = 17 блобів |

⚠️ Головний виграш — **не економія диска, а зникнення мережевих запитів**. Сценарій «файл
2 МБ+ у 17 батчах» від дедуплікації не виграє нічого; не варто на це розраховувати.

### 12.3 ⚠️ Усередині ДВІ породи — і слово «cache» бреше

| порода | що це | чи можна втратити |
|---|---|---|
| **локальні версії** | старі версії файлів Vault, які існують **тільки** тут; проміжні результати diff3 між комітами | **НІ** — єдина копія; втрата = неможливо завершити ці коміти |
| **віддалені blob-и** | `base`/`theirs`, завантажені з GitHub | так — перекачаються |

Слово «cache» означає «похідне, відновлюване, можна викинути». Половина вмісту цим не є.
Ризик конкретний: хтось колись напише «ну це ж кеш» і зачистить сховище під тиском місця.

**Наслідок:** якщо колись знадобиться звільняти місце примусово — безпечно скидати можна
**лише другу породу** (заплатите мережею). Першу — ніколи. Варто або відбити це в назві
(`blob-store` / `drain-store`), або розділити на дві теки, щоб різниця була видима, а не
трималась на пам'яті автора.

### 12.4 🔑 Порядок запису: метадані ПЕРЕД блобами

```
commit:  1. записати metadata батча (список шляхів + SHA)
         2. і ЛИШЕ ПОТІМ покласти blob-и у сховище
```

Це не стиль, а умова коректності двох механізмів одразу:

- **sweep (§12.5)** ніколи не забере щойно записаний blob, бо посилання на нього з'явилось
  раніше за сам blob. Зворотний порядок дає вікно «blob уже є, посилання ще нема».
- **відновлення (§12.6)** отримує маніфест раніше за вміст, тобто завжди знає, що саме
  мало бути записано.

### 12.5 Час життя і sweep

**Модель:** сховище прибирається **тим самим sweep-ом за посиланнями** — і на **початку**, і
в **кінці** drain. Одна операція, жодних окремих випадків.

```
1. list(file_cache/)              → candidates      ← ЗНІМОК того, що існує ЗАРАЗ
2. зібрати referenced (нижче)
3. видалити candidates \ referenced
```

**Множина посилань — три джерела, усі обов'язкові:**

```
referenced = { SHA з metadata батчів, ЩО ЛИШИЛИСЬ у черзі }        ← ours
           ∪ { SHA з журналу drain: baseSha по кожному шляху }     ← база, зокрема «ours став theirs»
           ∪ { SHA всього, що drain тримає В ОБРОБЦІ }             ← завантажені remote + проміжні diff3
```

⚠️ **Третє джерело — вимога до ЖУРНАЛУ, а не побажання.** Завантажений `theirs` і проміжний
результат diff3 не належать жодному батчу, тож жодне інше джерело їх не прикриває. Отже
**журнал мусить записувати SHA кожного блоба, на який drain зараз спирається** — інакше
sweep на старті відкладеного drain знищить роботу, вже зроблену попередньою спробою. Це
частина того, навіщо журнал існує, а не побічний ефект.

⚠️ **Журнал у множині — те, що рятує «ours став theirs».** Після пушу батча N його вміст
більше не в черзі, але ще потрібен як `theirs` для N+1. Sweep лише за чергою видалив би
рівно найкорисніше й купив зайві мережеві запити (§12.2).

**Чому «завершено = видалити все» — окремого правила не потребує.** Коли drain завершився
(«завершено» = у черзі не лишилось батчів), усі три джерела порожні → `referenced` порожня →
sweep забирає все. Тобто беззастережне вичищення — це просто **окремий випадок** sweep-у, і
формулювати його окремо не треба. Усі інші випадки (отруйний батч, зникла мережа, відкладений
батч) — **незавершений** drain: черга й журнал непорожні, отже потрібне виживає само.

Те, що sweep справді забирає, — або старі версії з уже оброблених батчів, або віддалені
blob-и, які **перекачаються**. Нічого незамінного.

#### 🔒 Конкурентність із `[commit]` — лока НЕ потрібно

`file_cache/` — **глобальний** ресурс, тож R3b (§6) його **не покриває**: там протокол
`.attempted-commit`/`.attempted` claim-ить *конкретний каталог батча*. Два вікна, де commit і
sweep стикаються, закриваються **порядком, без блокувань** — що зберігає принцип R3b «commit
ніколи не блокується» і не створює завислих локів при краху.

**Достатньо двох правил порядку:** §12.4 (метадані ПЕРЕД блобами) + `list` ПЕРЕД читанням
посилань (крок 1 перед кроком 2). Перебір чергувань для блоба `C`, який commit пише
паралельно зі sweep-ом:

| коли записано blob `C` | `C` у `candidates`? | чому вцілів |
|---|---|---|
| до кроку 1 | так | метафайл записано ще раніше (§12.4) → крок 2 його бачить → `C ∈ referenced` |
| між 1 і 2 | ні | у знімку його не було |
| після 2 | ні | те саме |

Жодного вікна на **обох** кінцях drain. І батч, що вклинився під час фінального sweep-у,
природно виживає й стає **першим батчем наступного drain** — без очікування.

#### Третя точка запуску — onload плагіна

Той самий sweep запускається ще й **на старті плагіна** (рішення власника) — як підмітання
за крахом: процес міг померти будь-де, лишивши блоби, на які вже ніхто не посилається.

Безпечно й нічим не відрізняється від інших двох точок: черга й журнал на диску, отже
`referenced` обчислюється повністю, а drain у цей момент не працює, тож стану «в обробці» не
існує. Місце в послідовності — та сама onload-фаза, де вже стоїть `AtomicWriteRecovery.sweep`
(`main.ts:1001`), тобто **до** будь-якої sync-операції; порядок має бути визначений явно, а
не випадковим.

⚠️ **Sweep вирішує ЛИШЕ за посиланнями, не за придатністю.** Побитий блоб, на який хтось
посилається, він **лишає** — виявити й полагодити це робота §12.6. Змішувати дві перевірки в
одну не можна: sweep, який почне видаляти «зіпсоване», знищить саме те, що §12.6 уміє
відновити з Vault.

> **Свідома відмова від складності:** пік диска під час drain тримається довше, ніж
> сьогодні (сьогодні оброблений батч зникає разом зі своїм вмістом). Для drain на кілька
> хвилин це неістотно, і ускладнювати заради цього алгоритм — не варто.

### 12.6 Відновлення після краху — ЛАГОДИТЬ; відкат лише коли полагодити нічим

Побачили метафайл батча → перевіряємо, чи всі його blob-и на місці й цілі. **Двоступенево:**

```
1. stat(file_cache/{sha}) — існує? розмір збігається з метафайлом?     ← безкоштовно
2. хешувати — лише де розмір збігся, але є сумнів (або параноїдальний режим)
```

Торнутий запис майже завжди дає обрізаний файл, тож крок 1 ловить майже все. Хешування
недешеве: 2 МБ → 6.3 мс, 50 МБ → 107 мс, тож батч із десятком великих вкладень перевірявся б
секундами. Перевірка **per-blob, не per-batch**: той самий SHA у двох батчах перевіряється
один раз.

**Blob відсутній або побитий → спершу РЕМОНТ, і в типовому випадку він удається:**

```
для кожного (path, sha) з метафайлу, чий blob відсутній/побитий:
    файлу path у Vault немає?          → ремонт неможливий
    SHA(Vault[path]) == sha?           → ТАК → копіюємо у file_cache/{sha}  ✅ полагоджено
                                       → НІ  → ремонт неможливий
```

🔑 **Чому це надійно, а не «сподіваємось, що файл не змінився»:** у метафайлі лежить **SHA**.
Тобто ми не припускаємо, що Vault усе ще тримає заморожену версію — ми це **доводимо**,
звіряючи хеш. Content-addressing окупається тут удруге.

І це не рідкісний шлях, а **звичайний**: крах одразу після коміту застає Vault рівно з тим
вмістом, який щойно заморозили — користувач ще не встиг нічого змінити. Тобто типовий крах
лагодиться повністю, без втрат.

⚠️ **Відкат — тільки коли ремонт неможливий**, тобто файлу у Vault немає **або** його SHA
змінився. Тоді заморожена версія справді втрачена (існувала лише у сховищі) — і батч
відкочується, як `delete-and-restart` із R3b (§6). Наслідок для користувача той самий, але
тепер він настає **лише в цьому вузькому випадку**, а не при будь-якому пропущеному blob-і:
коміт понесе ПОТОЧНИЙ стан файлу, а не той, що фіксувався до краху.

**Відкат ПОШЛЯХОВИЙ, не всього батча** (рішення власника, 2026-08-16). З батча вилітають
**лише нерепарабельні шляхи**; решта зберігає свої заморожені версії й комітиться як була.
Якщо випали всі шляхи, батч стає порожнім і зникає наявним механізмом empty-batch skip
(`entries.length === 0` → пропустити createTree/Commit, видалити батч, `sync2-manager.ts:3697`;
§11 П11).

**Обґрунтування власника: батчі в нас НЕ тематичні.** Батч — це зріз у часі над тим, що
змінилось, а не смислова група. Тому викидання одного шляху не руйнує жодної цілісності, яку
батч ніс би, — на відміну від, скажімо, коміту, що свідомо об'єднує пов'язані правки.

Наслідок для викинутого шляху: його поточний вміст у Vault відрізняється від `baselineSha`,
тож наступна детекція змін підхопить його й закомітить наново. **Дані не гинуть — гине лише
та одна проміжна версія**, яку відновити нема звідки. Відкат усього батча натомість убивав би
й ті дев'ять заморожених версій, що були цілі, — а це рівно те, що бережуть
[[feedback-preserve-all-commits]].

**Торнутий метафайл деградує правильно:** `JSON.parse` падає → трактуємо як «метафайлу
немає» → на його blob-и ніхто не посилається → sweep їх забирає, батч зникає повністю.
Отже **ні метафайл, ні blob-и не потребують атомарного запису** — плоского досить.

### 12.7 Відкрите питання

**З чим порівнює `[commit]`, поки drain відкладений?** `baselineSha` заморожений до
завершення drain, а оброблені батчі з черги вже зникли. Тоді `queuedSha ?? baselineSha`
падає на до-drain значення → файли, вже запушені в цьому drain, знову виглядають зміненими
→ черга й сховище ростуть щокоміту. Варіанти: `[commit]` теж дивиться в журнал drain
(`baseSha` свіжіший), або приймаємо churn. Не вирішено.

### 12.8 Взаємодія з §11

⚠️ **§11 П1 каже «Транзакція = ОДИН БАТЧ, не весь drain».** Новий drain будується на
протилежному — весь drain як одна транзакція з фіксацією `baselineSha` в кінці. Ця секція
описує сховище під НОВУ модель; П1 у своїй теперішній редакції їй суперечить і має бути
переглянутий разом з описом нового drain.

§11 П2 («черга — довговічний журнал незробленого», запушений батч видаляється) — сумісний.

### 12.9 Двоступеневе порівняння — спершу `size`, потім SHA

Правило власника, наскрізне для всього §12: **ніколи не хешуємо, поки розмір не звірено.**
`stat` безкоштовний, хешування — ні (2 МБ → 6.3 мс, 50 МБ → 107 мс). Саме тому §12.1 вимагає
`size` у метаданих: без збереженого розміру звіряти нема з чим.

⚠️ **Але сила кроку РІЗНА, і плутати їх не можна.** Розбіжність розміру доводить
відмінність — це висновок. Збіг розміру не доводить нічого — це лише запрошення хешувати.

| навіщо порівнюємо | що дає збіг розміру | чи можна пропустити SHA |
|---|---|---|
| **чи файл дописаний до кінця** (валідація blob-а у сховищі, §12.6 крок 1) | сильний сигнал — торн-запис майже завжди обрізає файл | так, крім параноїдального режиму |
| **чи це той самий ВМІСТ** (ремонт із Vault §12.6; детекція змін) | нічого — правка одного символу розмір не змінює | **НІ, хешування обов'язкове** |

Тобто в §12.6 обидва кроки виглядають однаково, а вимоги протилежні: валідацію блоба можна
завершити на розмірі, а `SHA(Vault[path]) == sha` — **не можна ніколи**.

⚠️ **Розмір мусить бути надійним.** SYNC-FIX §5.4 уже провів цю межу: небезпечний не «розмір»
взагалі, а **розмір-як-збережена-копія, що може розійтися з дійсністю** (саме тому там
вирішено НЕ оптимізувати гілку `conflictRef`). Тут проблеми немає: `size` у метаданих
записується в один момент із `sha` і описує той самий незмінний вміст, а розмір блоба
береться живим `stat`-ом. Але правило лишається чинним для будь-якого нового споживача.
